# P66.C22：热构建耗时归因

## 冻结范围

C21 已证明普通 Actor/Component 源码可以命中双缓存并保留正确身份；当时约 9 秒的探针计时还包含构建之后的读取与核对。本节单独计时正式构建调用，再确定优化位置；不以跳过准入、复用可变对象或缩减玩法样例换取更快结果。

诊断入口复用 C21 的同源 producer 报告、绑定包、类型清单和缓存。正式构建器源码与缓存键保持原样，通过独立 PowerShell 进程中的源码断点 action 测量函数入口与 return 边界；不暂停用户 Editor，也不改写生产函数。嵌套记录包含父调用身份，inclusive 时间不能直接相加。

同一 BelowNormal 进程串行执行基线与观测两组，各一轮 warmup 和三轮样本。每轮都核对双缓存命中、四个正式工具计数为零、worker 未启动、无 fallback，以及六份原始产物与 producer 相同。全部轮次复用本次新建的一个输出目录，不能为每个样本复制一套约 37 MiB 的 Semantic。C21 中被自动审批拒绝删除的目录仅作为既有缓存和报告输入，不重试清理。

报告记录 Git commit/tree、受保护工作树状态、SDK/PowerShell、输入哈希、机器配置、原始样本、median/P95 和函数事件。观测与基线的差异只用于评估测量扰动；三轮诊断不作为竞品基准或领先性证明。主构建计时不包括观测器的后续产物哈希比较。

## 优化约束

只有成本证据明确后才修改对应 owner。语言定义继续由 C# 提供；DLL、源码、Semantic 字节、模块与配置变化必须使复用失效。若引入构建内复用，必须明确作用域、不可变返回与失败处理，不能把任意调用者提供的 Profile 对象当作可信缓存。

P66.C/D、结构热重载、完整调试、真实 Windows 游戏闭环及跨框架对测仍未完成。本节不改变既有批次或长期目标。

## 实际结果

入口为 `Build/MeasureCSharpCachedBuild.ps1`。输入 C20 未改写的 Actor/Component 源码、正式生成 facade、类型清单和 C21 的缓存；指定 `ExistingProbeOutputRoot` 时，只允许复用已核对身份与六份产物的 `Saved/AvidScript/CachedBuildProbe/<run-id>`。其他命名空间在启动构建、创建输出目录之前拒绝。

2026-10-04 的最终诊断通过 **8/8**：两组各一轮 warmup、三轮样本。全部双缓存命中，四个编译工具调用为零，没有 worker 启动或 fallback；frontend、Semantic、IR、debug map、state schema、WASM 六份原始字节与 C20 一致。用户与机器 PATH 未变，串行 BelowNormal，SDK 8.0.416。

| 正式构建调用 | 三样本中位数 | nearest-rank P95 |
| --- | ---: | ---: |
| 无函数观测 | 5,993.54 ms | 6,033.23 ms |
| 有函数观测 | 6,662.79 ms | 6,721.85 ms |

三样本 P95 是最大样本，只用于定位。观测增加了约 669 ms 的中位开销；不能用观测组替代真实基线，也不能把 C21 的约 9 秒和这里的约 6 秒解释为已经实现的加速。

Semantic 原始文件约 36.83 MiB；观测 PowerShell 进程峰值 working set 为 1,060.48 MiB，未包含子进程总和。本节只定位编译链成本，没有运行新的 VM 或 Editor 验收。无显式 return 的原子发布 helper 没有单独计时，其成本包含在父函数中。

首次尝试在提交之后遇到工具身份变化产生的缓存 miss，按合同拒绝计为热样本；成功构建重新发布缓存后再测。编译 owner 源码指纹与六份执行字节保持一致；工具 assembly 含当前 Git informational version，但未保留旧 DLL 哈希，因此 DLL 变化的具体归因仍是推断，不能删掉 DLL 身份来强行命中。

结果与逐轮日志位于 `%LOCALAPPDATA%/AvidScript/Verification/CachedBuildLatency/20261004T112754866Z-b5fb1d2b/`。`results.json` 记录输入与产物哈希、Git commit/tree、脚本哈希、机器、统计和父子调用事件；`verification-audit.json` 补充开发工作树、语法检查及命名空间拒绝。拒绝路径的原有文件清单、长度与写入时间保持不变。Harness 确认七个受保护路径满足基线；本节仍是带保护修改的开发工作树诊断，不是 clean Gate。

下一步先优化最大路径的重复 JSON 读取与对象物化，同时保留完整语义准入、源码身份、绑定授权、产物哈希与原子发布；若无法保持等价合同，保留现有路径，再处理工具链指纹和工具准备成本。
