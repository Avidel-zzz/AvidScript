# P66.C5：`Task<int>` 的语言错误与跨 `await` 清理

状态：实现中。受限的 `async Task<int>` 生产者 `throw new` 已能在 Win64 生成并执行；同方法 `await` 后捕获和异步 `finally` 已有内部 Semantic 42 → IR 22 → WASM 编译路径，尚未进入正式构建或双 VM 运行验收。Android/iOS 验收暂缓。

## 要跑通的源码

```csharp
static async Task<int> LoadAsync()
{
    await AvidContinuations.NextTickAsync();
    throw new InvalidOperationException();
}

static async Task<int> ReadAsync()
{
    try
    {
        int value = await LoadAsync();
        return value;
    }
    catch (InvalidOperationException)
    {
        return 7;
    }
    finally
    {
        CleanupCount++;
    }
}
```

`LoadAsync` 的错误必须成为其任务的 `Faulted(language error)` 终态；`ReadAsync` 恢复时按类型进入 `catch`，执行一次 `finally`，最终以值 `7` 成功。不同类型的 `catch` 不得吞掉错误。成功任务走正常返回；取消不是 C# 语言异常；Host import 拒绝、VM trap、fuel 和越界都不得被脚本 `catch` 捕获。

## 现有边界

- [Async CFG](../../Tools/AvidScript.CSharpSemantic/Analysis/SemanticAsyncControlFlowProjector.cs) 只有 goto、branch、await、return；带 `catch` 的 `try` 和 `try/finally` 中的 `await` 被 `ASCS5420` 拒绝。[异常流程验证器](../../Tools/AvidScript.CSharpSemantic/Validation/SemanticExceptionFlowContractValidator.cs) 不允许同一方法同时拥有 async 与异常计划。
- 被拒绝的异步方法现在可在 `RejectedAsyncExceptionFlows` 诊断 sidecar 中保留 Roslyn 的 `try`、`catch`、`finally` 区域、块和分支。它不参与 Semantic 版本选择、不进入同步 `ExceptionFlows`，也不放行原有 `ASCS3002`/`ASCS5420`；普通 Guest 与同步异常编译器都拒绝携带 sidecar 的输入。受限预览的区域成员已由 CFG 构建时的 draft 身份确定，裁剪与排序后绑定到 Roslyn 区域 ordinal；遇到无法唯一配对的隐式清理区域便不发布预览。这个关联仍是诊断证据，不能作为可执行 schema 42。
- 对 `Task<int>` 的受限源码，sidecar 还保存 `AsyncContinuationPreview`：`await` 语言故障后继指向按源码顺序的 `catch_match` 决策，取消后继绕过 `catch` 并沿独立 `finally` 路由到取消传播；匹配返回、重抛、不匹配传播和 `finally` 替换异常有独立 draft segment 与清理路径。故障与取消分支都参与活跃变量和词法作用域入口分析，预览的 await 状态帧保留 catch/finally 所需的局部值及调用入参；同一编译器返回槽允许不同返回分支写入。预览不处理 catch 变量/过滤器、catch 或 finally 内再次 `await`，也不伪造会跳过 `finally` 的 try/catch 内新建异常；这些源码继续只保留 Roslyn 区域。预览的状态帧尚无在途 Task owner，也没有 Guest lowering，始终不可执行。
- Semantic 41 的 `ASCS5422` 诊断计划保留同文件同步方法的 control-flow graph；正式样例同时导出 `BeginPlay` 和 `Tick`。其他支持错误仍阻止这条受限构建路径，不能借此放行无效 C# 源码。
- [Task await lowering](../../Tools/AvidScript.CSharpGuest/Lowering/CSharpTaskAwaitLowerer.cs) 能将未处理的 `async void` 语言错误交给 Session 错误报告路径；它仍没有脚本 `catch/finally` 处理目标。[组合编译器](../../Tools/AvidScript.CSharpGuest/Lowering/CSharpLanguageErrorCompiler.cs) 仍只接受互不调用的同步异常方法和 Task 方法。
- 原生结果槽能保有语言错误载荷，并在 `avid_task_propagate_failure_v1` 时共享根租约。IR 21 的受控 C# 路径调用 `avid_task_fault_language_error_v1`；未处理的 `async void` 等待还会读取 `avid_task_language_error_meta_v1` 和 `avid_task_language_error_root_v1` 后上报。两者仍未接入脚本 `catch` 路由。

## 版本化表示

1. 首个 Semantic 合同使用 schema **41** / semantic **1.50**：记录 `async Task<int>` 中受支持的 `throw new`，将 segment ordinal、源码 span、实际异常类型和零参构造器身份绑定在 `SemanticAsyncMethod.ErrorPlan`。投影继续发出源码位置的 `ASCS5422`；默认编译拒绝该诊断产物，只有显式的 `-LanguageErrors bounded` 路径验证计划后降级为可执行 IR。旧版本夹带错误计划或 `throw` 转移必须拒绝。
2. 后续 `await` 失败路由、`catch` 和跨挂起 `finally` 必须再升 Semantic 版本，记录 Roslyn 异常区域、正常/错误/取消目标、由内到外的清理顺序与异常变量的状态帧所有权。验证器须重算 segment/region 归属、handler 优先级、局部类型和来源，拒绝伪造跳边与悬空 segment。同步 [SemanticExceptionFlow](../../Tools/AvidScript.CSharpSemantic/Model/SemanticExceptionFlow.cs) 继续服务同步方法，不把其 CFG 冒充 async 执行图。
3. 首个 Guest 执行合同使用 schema **21** / IR **1.20**，provenance 只接受配对的 Semantic 41/1.50；当前覆盖 `async Task<int>` 生产者的 `throw` fault lowering 与未处理的 `async void` 等待错误报告。`catch/finally` 路由再升 IR 版本。已有 Task 和语言错误 Host import 保持 v1 签名；旧 IR 20/1.19 继续读取和执行原有的互不重叠组合产物。

### 下一版本：跨挂起异常区域

目标合同为 Semantic **42/1.51** 与 Guest IR **22/1.21**。两者目前仅能通过工具链内部显式开关生成；CLI 与正式构建未启用，尚无 Win64 执行证据。Semantic 为每个 async 方法保存以下源自 Roslyn 的信息：

- 每个 `try` 的父区域、受保护 segment 集合、源码 span，以及按源码顺序排列的 `catch` 类型和入口。过滤器和不能静态确定类型的处理器继续在源码位置拒绝。
- 每个 `await` 的正常、语言故障、取消目标；每条离开区域的边记录由内到外的 `finally` 路由和完成清理后的目标。`return` 值在进入第一条清理边前求值并存入调用状态。
- 恢复帧的在途结果为正常返回、语言故障或取消三种互斥状态。语言故障记录类型与源码令牌，并保留一个独立的源 Task 租约作为错误对象的持久根 owner；每次恢复后从该 Task 重新取得当前调用帧根。完成、重抛、替换、取消、reload 和 teardown 对源 Task 租约只能释放一次。这个方案复用现有 Task 根租约，不在 WASM 帧里保存一个失去根所有权的裸对象 token。

当前投影器会按源码位置重新排列并裁剪 draft segment，且不同退出路径可能复制同一段 `finally` 源码。因此区域成员和清理目标必须先绑定 draft 身份，再与控制流目标一起重映射为最终 ordinal；不能用源码 span 推断恢复入口或把复制的清理块当成一个块。验证器重算区域嵌套、成员、出口顺序、handler 优先级、目标可达性和状态帧槽，并拒绝旧版本夹带新路由。

Guest 的故障分派先判断任务终态，再在被等待任务引用仍有效时读取 meta 和 root。匹配处理器获得当前调用帧根，并为跨后续 `await` 的在途错误保留源 Task 租约；不匹配时保留该租约直至内层 `finally` 完成，之后才向外传播。`catch` 中 `throw;` 保留原对象与来源；`finally` 再抛出语言错误则替换在途错误。普通 Host/VM 失败不进入脚本 `catch`，失效 Session 的取消和 teardown 不重新进入脚本。IR 22 必须验证每条 fault/cancel 边及租约的最后一个 owner，且只接受 Semantic 42/1.51 的 provenance。

## 执行规则

| 位置 | 必须执行的动作 |
| --- | --- |
| `async Task<int>` 中 `throw new` | 仅接受当前同步语言错误子集中的零参框架异常。创建有当前 VM 调用帧根的错误对象，按模块目录取类型/源码令牌，调用 `avid_task_fault_language_error_v1` 终结当前生产者任务。检查 Host 接受结果，然后按任务 owner 释放本次调用的 token 与局部根；拒绝时走不可捕获的失败路径。 |
| `await` 读到 `Succeeded=1` | 读取值并继续正常目标；不访问错误 import。 |
| `await` 读到 `Faulted=2`，且存在脚本处理区域 | 在释放被等待任务引用之前调用 `avid_task_language_error_meta_v1` 和 `avid_task_language_error_root_v1`。两者验证任务身份、故障载荷和当前调用帧根；普通 Host/VM 故障在这里被 Host 拒绝，不能进入 `catch`。按类型与源码计划选择第一个匹配 handler，先运行应执行的内层 `finally`。未匹配时把原错误及根租约传播给生产者任务。 |
| `async Task<int>` 的 `await` 读到 `Faulted=2`，且无脚本处理区域 | 沿现有 `avid_task_propagate_failure_v1` 传播，保留语言错误载荷；普通故障仍为普通故障。 |
| `await` 读到 `Cancelled=3` | 不读取语言错误 import，不进入 `catch`。仍有效的 Session 可以沿明确的取消清理边运行 `finally`，然后传播取消；Object/World teardown 不重新进入已经失效的脚本。 |
| 未处理的 `async void` 等待读到 `Faulted=2` | 先读取错误目录令牌与当前调用帧根；释放直接持有的 Task 引用后，调用 `avid_language_error_report_v1`。Session 返回 `language_error_uncaught`，包含异常类型和源码位置。普通故障仍失败，但不得伪报为 C# 语言异常；取消不读取错误 import。 |

错误对象从 Task 租约读取并置入当前调用帧根后，才能在本次调用内使用。若 handler 在另一个 `await` 后继续，状态帧必须保留源 Task 的独立租约；恢复后重新读取根，直到处理结束才释放。现有 `FAvidScriptSessionTaskResults` 已证明 Task 的持久根能在原调用帧退出、源引用释放、错误传播及 GC 后保持对象存活，并在最后一个 owner 释放后回收；跨挂起的 Guest owner 转移仍需单独实现和验收。`finally` 自身抛错按 C# 规则替换在途语言错误；普通 Host/VM 失败不执行脚本 `catch`，由 Session 负责回收。`async void` 边界不得把未捕获语言错误静默改为成功返回，须交给现有 Session 错误报告路径。

源 Task 租约的聚焦原生探针已补上“处理器 retain → 原调用者 release → GC → 错误传播 → 处理器 release → 源 Task 失效”顺序。当前树的 Win64 Editor no-clean 构建 `Result: Succeeded`，`AvidScript.Runtime.Continuation.TaskLanguageError` 过滤器的 Automation **2/2** 成功、失败 **0**、队列完整结束且进程以 **0** 退出；日志位于 `Saved/Logs/AvidScript_TaskLanguageErrorLease_20260925T120221750Z.log`。该证据只验证 Host 租约基础，不代表 Guest 已实现跨 `await` 的 handler。

4. 未处理的 `async void` 等待在 IR 21 中调用错误 meta、root 和 report import。Task 语言错误的类型、来源和当前调用帧根现在由同一读取 helper 提供；Guest 回归验证立即完成与恢复执行两条路径都从同一个仍持有的 Task 读取，再上报。完整 Guest 回归 **553/553** 通过。此前 Win64 no-clean Editor 构建及 Automation **1/1** 在 Wasmtime JIT 和 WAMR Interpreter 都报告 `language_error_uncaught`，错误消息包含 `InvalidOperationException` 与源码文件名，引用与堆根在结束后归零；该原生证据早于此次 helper 抽取，阶段 Gate 需按最终 tree 重跑。日志：`Saved/Logs/AvidScript_CompiledTaskLanguageError_20260925T112256685Z.log`。
5. 控制流状态分析现同时计算 `await` 正常与未来故障后继所需的局部槽，并保留赋值目标在失败边上的旧值；缺失的故障目标会被拒绝。词法作用域入口也把未来故障后继视为真实跳边，避免恢复时漏建闭包环境。此时生产投影仍只生成正常后继，故障路由尚未发布。

7. 工具链内部现在可显式生成 Semantic **42/1.51** 的 `SemanticAsyncExceptionPlan`：已绑定的 Roslyn 区域、处理器与 continuation segment 一起进入 `AsyncMethods`，故障和取消目标分别编码。固定的 [`AsyncExceptionFlow.cs`](../../Fixtures/Phase66/AsyncExceptionFlow.cs) 保留四个异步方法和两个处理区域；旧默认分析继续给出拒绝诊断。读端验证会拒绝旧 schema 夹带计划、伪造 catch 区域、取消进入 catch 以及缺失目标。复制的 `finally` 共用同一个源码词法作用域 ID，合并 segment 成员后再计算进入边。Semantic **405/405** 通过；现有 Guest IR 21 明确拒绝 Semantic 42。此切片只确认正式 Semantic 表示，不证明 Guest 能执行，也不满足 P66.C5 的 Windows 运行时验收。
8. Semantic 42 的读端现对 continuation 图进行 owner 状态传播：正常、在途语言故障、已捕获但仍需保留原错误的故障、取消分别进入各自后继。`catch_match` 只能接收故障；未匹配故障不得跳到正常 `return`，取消不得进入故障传播。状态集合允许正常返回与已捕获故障共用同一段 `finally`，因此 Guest 不能仅凭 segment 身份决定是否释放源 Task，而要检查运行时 owner。固定样例和伪造跳边回归后 Semantic **405/405**、Guest **553/553** 通过。
9. 内部 Guest lowering 现将 Semantic 42 的受保护 Task await 编为 IR **22/1.21**：即时和恢复路径分别判断成功、语言故障、取消；故障先从仍持有的 Task 读取 meta/root，再 retain 源 Task 为处理器 owner，按类型进入 `catch_match`，最终返回、重抛、故障/取消传播或替换错误时释放。IR 22 的版本化路由元数据绑定 await 块、三个目标和 owner/type 槽；验证器拒绝旧 IR 夹带路由、缺失路由、改写故障目标或伪造 owner。固定样例完成规范化序列化往返并生成 WASM，Guest 回归 **553/553** 通过。此处仅为受限内部编译证据；尚需最后 owner 路径验证、正式 CLI/构建入口和 Win64 Wasmtime/WAMR 对照运行。
