## 配置 owner

`CSharpLanguageProfile` 位于 C# Semantic 工具层，定义 `gameplay-v1`：八项已有语言分析全部开启，Guest 使用 bounded 语言执行、data lane fusion，关闭现阶段不兼容的运行时调试插桩。调试 sidecar 继续生成。未知版本或冲突参数明确拒绝，不自动降级。

Semantic CLI 和 Guest CLI 都接受一个选项：

```text
--language-profile gameplay-v1
```

未指定 profile 时保留现有 CLI 行为与显式分析参数。指定 profile 后，Semantic 不允许另传八项分析开关；Guest 的显式执行参数必须与 profile 一致。profile 只决定分析与执行策略，产物仍按实际源码投射能力，不能补空 token、catch、owner 或静态计划。相同源码和相同有效选项的 API、CLI、worker 必须生成相同规范字节。

配置身份由 owner 的规范 JSON 与 SHA-256 给出，包含源语言、版本、全部分析项及执行策略。Worker 的新 profile 请求采用协议 2，携带精确名称与合同哈希；响应回传经验证的身份。协议 1 保留原行为，不能携带新字段取得新执行权限。PS 客户端按请求版本与身份校验响应，不能只检查常驻进程或 pipe 名称。

Semantic CLI 的 `--describe-language-profile gameplay-v1` 返回 owner 的定义及合同哈希，不需要源码文件。PS 编译包装器接受 `-LanguageProfile gameplay-v1`；worker 客户端在请求携带 `language_profile` 时选择协议 2。Semantic 的源诊断退出码仍保持真实值，合法 bounded 执行源也可能返回 1；身份检查覆盖这类响应，不把它伪装成 `succeeded=true`。Guest 的成功发布仍要求完整验证。

## 集成顺序

1. 统一 owner、CLI、worker 和 PS 转发，验证单一 profile 的完整同源矩阵、常驻 workspace 复用、命名管道通信、错误请求及旧协议兼容。
2. Semantic cache、Guest cache 与 prepared 共享 profile 身份。身份进入键与报告，读取重新核对来源、选项、版本、实际能力及 bytes。不能放宽旧 prepared 的 31 / 45 范围就宣称新合同受支持，也不能依靠修改 `succeeded` 或过滤错误得到缓存准入。
3. 普通 Build And Bind、live reload 和脚本定义类型使用同一配置决策，逐步替换现有默认链。正式默认配置交付需要冷构建、命中、改源码/引用/配置、worker 故障回退、候选失败和实例生命周期验证。

本批完成第一项；第二项在 P66.C16 完成，第三项仍是默认构建交付的必要工作。当前 profile 也不代表完整 C# 语义或默认 Editor 流程已经交付。
