# P66.C3：语言错误通道

状态：底层结果槽和新版 IR 的结果类型布局已验证。Semantic 可以生成版本化的异常流诊断记录；工具层已能把同一份源码中的多个受限 `throw new System.Exception()` 方法、直接调用者、跨方法 `catch`，以及同方法的直接 `throw`/`catch` 组成 IR 17/WASM。普通方法中直调错误跨越线性同步 `finally` 时，已能按内层到外层执行清理，再由外层处理器捕获。每个抛出点有独立源码令牌，错误对象及类型/源码目录保留。UE Runtime 已在加载 canonical WASM 时校验并保存目录；受影响的 `void` 导出在未捕获时报告错误。命令行发布入口仍拒绝异常产物；catch 变量、清理再次抛错、重抛及跨 `await` 清理尚未执行。本文不把专用入口算作已开放的语言功能。

## 可执行底座

Guest IR 已有结构体返回的 SRet 路径：调用者为每次 `call` 提供独立的线性内存结果槽，WASM 函数把结构体写回该槽。[WasmOutcomeSlotTests.cs](../../Tools/AvidScript.WasmBackend.Tests/WasmOutcomeSlotTests.cs) 用两个连续的嵌套调用模拟正常值、错误传播和 `finally` 抛出新错误覆盖旧错误。探针结构体为五个 `int32` 字段：`status`、`error_type`、`source`、`value`、`cleanup`；它只是测试布局，`cleanup` 是可观察计数，不属于拟定的生产 ABI。

固定 SDK 8.0.416 下 WasmBackend 测试 **323/323** 通过；[RunOutcomeSlotWasm.cjs](../../Tools/AvidScript.WasmBackend.Tests/RunOutcomeSlotWasm.cjs) 在 Node WASM 上检查五组结果，**5/5** 通过。Win64 no-clean Editor 构建通过；[TestAvidScriptLanguageOutcomeSlot.ps1](../../Build/TestAvidScriptLanguageOutcomeSlot.ps1) 把同一 WASM 放进 Editor，在 Wasmtime JIT 和 WAMR Interpreter 上检查五组结果，Automation **1/1** 通过。该证据说明现有 SRet 能承载逐次调用结果，不证明 Roslyn 异常已经可执行。

Guest IR **15/1.14** 可选地声明 `language_outcome_types`，但不能用这些类型作为函数返回值。每个结果结构按规范顺序包含 `status`、`error_type`、`source`、`error_root` 和可选的 `value`；前三项为 `i32`，错误根为带 payload 的 `managed_ref`，偏移和大小由 `GuestDataLayout` 计算。`source` 是留给后续源码位置表的令牌，不直接充当源码 span。验证器拒绝字段乱序、错误根形态、重复声明和降版伪装；旧产物省略该字段，原有序列化字节不变。

Guest IR **16/1.15** 允许内部函数返回上述结果结构。直接和间接调用后必须立即读取 `status` 并按其分支；`value` 只能在成功专属路径读取，错误字段只能在错误专属路径读取。生产者在每条返回路径上必须写入常量状态 `0` 或 `1`；正常状态需要 `value`，错误状态需要 `error_type` 和 `source`。状态常量必须支配写入点，不能经可变局部或地址别名伪装。调用结果与生产者结果均不能通过普通操作数或地址别名绕过检查。Host import 不能返回语言错误结果；原始结果函数不能直接导出给 UE。

固定 SDK 下 Guest IR 回归 **67/67** 通过；[GuestLanguageOutcomeFlowTests.cs](../../Tools/AvidScript.GuestIr.Tests/GuestLanguageOutcomeFlowTests.cs) 的手工模块经 WASM backend 编译后，[Node 测试](../../Tools/AvidScript.GuestIr.Tests/RunLanguageOutcomeFlowWasm.cjs)验证单次调用以及两层函数间的正常结果和错误字段，**4/4** 相符。这组底座测试导出的标量探针只读取字段便于断言，不是 UE 错误适配器；其中的 Host heap import 仅为无对象分配的测试桩。

`CSharpLanguageOutcomeRewriter` 能把已正常 Lower 的 C# 内部函数转换为 IR **16/1.15** 结果函数：正常返回写入 `status=0` 与可选 `value`，每次调用受影响函数后立刻按状态分支，错误原样返回或在返回值类型不同时复制错误类型、源码令牌与错误根。它拒绝未转换的直接调用者、原始 Host 导出、函数引用、语义来源不匹配，以及未由清理路由规划器检查的 `try`/循环/异步方法。由真实 C# 普通方法 Lower 后改写的 WASM，在[Node 探针](../../Tools/AvidScript.CSharpGuest.Tests/RunLanguageOutcomeRewriteWasm.cjs)中分别得到正常值 `8` 和注入错误后的 `99`，**2/2** 相符。这组早期传播探针的错误生产者和导出探针由测试注入；专用同源编译入口及 UE 适配器见下文。

`CSharpThrowProducerLowerer` 单独读取真实 C# 的 Semantic 34/1.43 异常记录，只接受静态无参方法内的单个 `throw new System.Exception()`。它按异常类型和源码 span 确定性分配临时令牌，分配受管错误对象根并返回 `status=1`、类型及位置。带参数或自定义构造器、`catch`、`finally` 等路径继续拒绝，避免跳过构造副作用或清理。[Node 探针](../../Tools/AvidScript.CSharpGuest.Tests/RunThrowProducerWasm.cjs)在生产者返回后强制触发一次 GC，再读回类型、位置和错误对象根，结果为 `3`；调用结束后再次收集，确认帧、根和对象均已释放，**1/1** 通过。单独生产者测试仍将该函数接到另造的模块和标量导出，不代表标准 C# 构建路径或 UE Runtime 已能处理异常。

`CSharpLanguageErrorCompiler` 从通过异常合同校验的 Semantic 34/1.43 产物提取普通方法 CFG、多个受限抛出方法，以及无过滤器、变量或清理的 catch 方法。同方法的 `throw new System.Exception()` 被临时投影为内部 CFG 返回块，结果通道改写后再替换为带错误对象根的抛出块；源自 Semantic 的处理器决策决定跳转到本地 catch 或继续返回错误。跨方法调用仍在返回后检查状态，匹配的处理器按目录类型令牌执行，未匹配则传播。最终模块保留原始 34/1.43 来源和 Guest IR **17/1.16** 身份。`FailA()` 与 `FailB()` 的不同源码位置在同一目录获得连续令牌；两个调用者分别捕获并返回 `11` 和 `22`。[Node 探针](../../Tools/AvidScript.CSharpGuest.Tests/RunThrowProducerWasm.cjs)验证内部传播、UE 入口未捕获报告、处理器源码顺序、多生产者捕获、本地捕获返回 `7`、两个本地抛出点分别返回 `11`/`22`、不匹配继续传播，以及调用结束后对象根释放。带参数构造器、catch 变量、复杂清理和重抛仍拒绝。受限抛出方法目前仍须静态、无参、返回 `int32`；默认 CLI 尚未调用此专用入口。

`CSharpLanguageCleanupRoutePlanner` 对已正常 Lower 的普通方法读取原始 `try/finally` 与 CFG。受影响直调返回语言错误时，结果通道沿清理作用域复制已 Lower 的线性 `finally` 块，按内层到外层执行后才传播原错误；正常路径继续使用原 CFG。分支清理、异步清理、清理中的语言错误调用与处理器自身的清理继续拒绝。两份同源 C# 在 CLR 和 Node WASM 上分别得到 `1`（单层清理）和 `11`（嵌套清理），且受管帧、根与错误对象在调用结束后释放。C# Guest 全量回归 **505/505**，9 份语言错误 WASM 探针全部通过。Win64 no-clean Editor 构建通过；[聚焦 UE Automation](../../Build/TestAvidScriptLanguageErrorCatalog.ps1) 在 WAMR Interpreter 和 Wasmtime JIT 上加载两份新产物，执行 BeginPlay 并检查目录与遗留根，**3/3** 通过。UE 测试没有直接读取清理计数；计数的执行断言来自同一产物的 Node 探针。

Guest IR **17/1.16** 的 `language_error_catalog` 将类型令牌映射到语义类型 ID，将源码令牌映射到 Source ID、源码长度及 UTF-16 span/行列。目录随 Guest IR 规范序列化；验证器要求令牌从 1 连续编号、按类型及位置排序、源码 span 在范围内，并验证错误结果生产者写入的字面令牌都存在且目录无闲置项。旧版 14–16 的 JSON 字节形态不变，不能携带该目录；17/1.16 缺目录、缺结果类型或绕过状态检查均拒绝。固定 SDK 下 Guest IR 测试 **79/79** 通过；WasmBackend **323/323** 通过。

WASM 编译器把 IR 17 目录写入唯一的 `avidscript.language_errors` 自定义段，JSON `schema_version=1`，包含 `guest_ir_schema_version`、`guest_ir_version`、`module_id`、`source_sha256`、按令牌排序的 `types` 和 `sources`。段长上限为 4 MiB；旧版 IR 不生成该段。同源 C# 测试从编译后的 WASM 读回类型 ID、Source ID 与完整 UTF-16 span/行列，并确认重复编译字节一致；C# Guest 回归 **498/498** 通过。将同源 Guest IR 文件交给 WasmBackend CLI 重新编译，Node 探针仍 **2/2** 通过。

UE Runtime 从待执行的 canonical WASM 读取目录，并与 `avidscript.provenance` 的模块 ID、源码 SHA-256 和 IR 17/1.16 身份交叉校验。类型令牌和源码令牌连续、有序且有界；格式错误、缺失目录、重复段、越界 span 或不匹配身份均在 VM 加载前拒绝。已验证的目录只在加载成功后保存，卸载、重载或失败不会遗留旧目录。专用编译入口对受影响的 `void` 导出保留原签名，在错误分支通过 `avidscript.avid_language_error_report_v1` 上报类型令牌、源码令牌与受管对象引用；Host 校验目录和本次调用帧中的对象根，报告 `language_error_uncaught` 并终止调用。无效令牌或对象根走 `language_error_invalid_report`。已有 Session 失败路径接收此类别和含源码位置的错误消息，Host 拒绝与 VM trap 仍分别处理。[TestAvidScriptLanguageErrorCatalog.ps1](../../Build/TestAvidScriptLanguageErrorCatalog.ps1) 从真实 C# 源码生成 WASM，执行 Node 探针，再让 Wasmtime JIT 和 WAMR Interpreter 加载并调用同一产物；聚焦 Automation **2/2** 通过。异常语法仍不是公开的构建能力。

Semantic **34/1.43** 仍只用于含异常语法的失败诊断产物。记录按方法保存 Roslyn 的 `try`、`catch`、`finally` 区域、分支的离开/进入/清理区域、带源码 span 的 `throw`/`throw;` 和 catch 类型，以及按序的异常基本块、块所属区域、块内运算及分支值。每个 catch 处理器指向对应的 Roslyn catch 区域。一个源码单元同时含普通方法和异常方法时，普通方法的 CFG 现在保留在产物中，异常方法仍只发布上述诊断记录；两者的方法身份不能重叠。它目前**不发布异常方法的可执行 CFG**。新版本校验序号、区域归属、类型、源码 span 和运算预算；旧版 32/1.41、33/1.42 不能冒充新版。原有成功产物仍为 31/1.40，序列化时省略 `exception_flows`。C# Guest 即使收到伪造成功标志或降版的异常记录，也会拒绝输入。固定 SDK 下 Semantic 测试 **387/387** 通过；过滤器保留在记录中并给出源码位置诊断，尚未实现。

`SemanticExceptionDispatchPlanner` 可从上述区域树为每个基本块推导语言错误路由：内层 `finally` 先于外层 `catch`，未匹配处理器后才继续外层清理；`throw;` 跳过当前 catch，`finally` 自身的新错误不会再次进入同一个 `finally`。同一规划器也给 `try` 内的调用块生成 catch 候选。`SemanticExceptionDispatchResolver` 在通过异常流和类继承合同校验后，用已注册的异常类型沿路由选择第一个匹配的处理器，并返回其前需要执行的 `finally` 区域；基类 catch、同类型内外层 catch、catch-all、未匹配传播和重抛均有源码级回归。未注册类型、非异常类型和伪造继承环拒绝解析。固定 SDK 下 Semantic 测试 **387/387** 通过。专用编译入口现消费无清理的处理器决策；另由普通方法 CFG 规划器执行受限线性同步 `finally`。异常方法自身的清理、变量绑定和重抛仍只是编译期规划。含过滤器的处理器不能生成路由。

`SemanticLanguageErrorEffectPlanner` 从含异常语法的方法向直接调用者做传递闭包，列出需要结果通道签名的方法；无关方法不进入闭包。属性访问器和显式转换等潜在调用一并保守计入。尚不能完整枚举目标的虚调用、接口调用和委托调用会使规划失败，不能据此输出部分结果。专用 `CSharpLanguageErrorCompiler` 已消费该闭包改写受限同源直接调用、无清理 catch 和受影响的 `void` UE 导出；其他异常方法与导出签名仍不能使用。

## 待落地的版本化合同

1. **Semantic。** 已有 34/1.43 的异常区域、分支、基本块运算及同源普通方法 CFG；多个受限抛出方法、跨方法 catch、同方法直接 catch 与普通方法的线性同步 `finally` 能经专用工具层入口执行。下一步要让异常方法自身的清理及一般异常退出路径执行，并让不支持的异常对象、过滤器、异步清理或动态分派在源码位置失败；旧版本产物不能冒充新图。
2. **Guest IR。** 16/1.15 已约束结果生产者、direct/indirect 调用后的状态分支和字段读取路径；17/1.16 增加有界、可校验的错误令牌目录。受限同源 C# 直接调用已使用这些规则；一般异常方法仍需结果槽、清理和对象根所有权合同。正常值只在正常状态可读，异常类型、源码位置及异常对象根只在错误状态可读。实际字段布局由版本化类型和 `GuestDataLayout` 计算，不能把早期探针中的常数 7/9、31/44 或 20 字节写成产品 ABI。受限 `void` UE adapter 已检查结果状态，其余入口继续拒绝异常语法。
3. **清理。** 普通方法中的受影响直调已能在错误返回时按内外顺序执行线性同步 `finally`。仍需覆盖异常方法自身的 `finally`、枚举器 `Dispose`、循环控制流，以及清理本身抛错替换待传播错误的规则；普通返回值在错误路径失效。异常对象及其捕获环境在传播、重抛和清理期间必须有明确的 managed-heap 根，调用结束不留根。
4. **UE 边界。** 受限 `void` 导出已有入口适配器，保持现有 `avid_on_*` 签名；生成的 UFunction 回调和其他签名仍需逐类接入。未捕获语言错误以类型和源码位置交给 Runtime/Session 报告并终止本次调用。Host import 拒绝、WASM trap、fuel/超时和越界仍走致命故障路径，脚本 `catch` 不得捕获它们；不能用模块全局错误变量传递语言错误。
