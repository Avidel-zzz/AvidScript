# P66.C7：异步取消的语言语义

状态：显式预览已通过正式 CLI / 构建入口生成 Semantic **44/1.53**、Guest IR **24/1.23** 与 WASM。正式产物在 Win64 Wasmtime / WAMR 执行 **48/48** 通过；同源码 .NET 参考 **20/20** 覆盖共享业务方法。Task 局部变量与别名可在捕获取消后跨帧重复等待，未捕获取消报告原异常类型和源码位置。不同 owner 集合的分支汇合、更多异步组合及新合同下的 Editor/reload 验证仍未完成，P66.C 继续实现。

## 问题与目标

Semantic 42/43 把取消直接送到清理入口，跳过所有 `catch`。这足以执行 `finally`，但不符合以下 C# 代码的预期：

```csharp
try
{
    int result = await LoadAsync();
}
catch (OperationCanceledException)
{
    // 取消已处理，方法可以继续执行或返回结果。
}
finally
{
    Cleanup();
}
```

本项的完成目标包括：直接 Timer await 与 Task await 的类型匹配、取消的重新抛出、`finally` 顺序、捕获后的继续执行、未捕获取消的语言诊断，以及 Task/取消对象/状态帧的生命周期回收。实现必须通过同源码 .NET 对照和 Win64 双后端执行，不能用 Semantic 测试代替运行结果。

## 取消对象与所有权

- Timer 的显式取消采用 `TaskCanceledException`；其继承关系为 `TaskCanceledException → OperationCanceledException → SystemException → Exception`。这与本仓库 .NET `Task.WaitAsync(token)` 适配器的实际结果一致。
- Task 传播取消时保留取消异常的类型、来源和对象身份；同一 Task 被重复等待不能生成不同的异常对象。Task 终态仍为 `Cancelled`，不得为了进入 `catch` 改成 `Faulted`。
- 有匹配的 `catch` 时，源顺序中的第一个匹配分支执行。正常离开 `catch` 消费当前异常 owner，允许后续再次 `await`；`return` 经过必要清理后完成 Task。
- `throw;` 保留当前异常，离开当前 handler，执行当前层 `finally`，再进入外层分派。不得重新进入同级 handler。
- `finally` 抛出的新语言异常替换原取消；该情况仍需接入新合同。现有 43/23 的清理抛错回归继续保留。
- Host 错误、VM trap、非法 completion 状态不可被语言 `catch` 捕获。World/Object teardown 与退休实例不恢复 Guest，由 Session owner 回收。

Guest 侧接续实现必须使用下述独立接口；不能复用仅接受 `Faulted` 的读取接口，也不能用一个类型编号代替实际拥有的异常对象。

## Runtime 与 Host ABI

Runtime 的 language-error catalog 已为 **Guest IR 24/1.23** 接入取消合同。C# lowerer 在显式 bounded language-error 模式下接受 Semantic 44，并通过正式 WASM backend 生成取消处理控制流；默认模式仍以 **ASCG1004** 拒绝。

| 新导入 | WASM 签名 | 行为 |
| --- | --- | --- |
| `avid_task_cancel_language_error_v1` | `(i64, i32, i32, i64) -> i32` | Task、类型 token、源码 token、对象 token；成功后 Task 为 `Cancelled` |
| `avid_task_terminal_error_meta_v1` | `(i64) -> i64` | 读取 `Faulted` 或 `Cancelled` 的异常元数据，高 32 位类型、低 32 位源码；不新增根 |
| `avid_task_terminal_error_root_v1` | `(i64) -> i64` | 返回原异常对象，并在当前 VM 调用帧中持有它，直到该帧退出 |

这三个接口仅接受具有配对 catalog/provenance 的 IR 24/1.23 模块，且只注册在 `avidscript` 模块。旧 IR 17、20–23 调用时返回 `task_language_error_version`；旧的 fault 接口与仅限 `Faulted` 的读取接口在 IR 24 中仍保持原语义。

取消提交依次验证 Session、Task 类型、catalog token、取消异常类型和当前调用帧的根。支持的取消类型为 `TaskCanceledException` 与 `OperationCanceledException`；普通 `Exception` 不能冒充取消。提交成功后 Task 持有 persistent root，重复完成失败时释放本次尝试的临时租约。`avid_task_propagate_failure_v1` 在两个 Task 间共享该租约，保留 `Cancelled`、原类型、源码位置和对象身份。旧的无载荷取消仍可传播，新读取接口不会为它凭空生成异常。

最后一个 Task/等待者释放后回收异常对象；读取方已取得的调用帧根可继续存活至帧退出。prepared 丢弃只释放候选，提交会退休旧代次，teardown 清除排队的取消等待者且不重新进入 Guest。

## Guest IR 与 WASM 接口校验

[`GuestTaskCancellationErrorValidator`](../../Tools/AvidScript.GuestIr/Validation/GuestTaskCancellationErrorValidator.cs) 是 IR 24 的版本与取消接口 owner，诊断码为 `ASIR1032`。新版本必须配对 Semantic 44/1.53、非空异常 catalog、三个新接口，以及原有完整 Task 和 fault 接口。旧的 fault-only 读取接口仍可成对声明，语义不变。

取消生产者必须传入 catalog 中的 `TaskCanceledException` 或 `OperationCanceledException` 类型常量和源码常量。两者均须在调用前于同一基本块定义，且不可被重复定义、赋值或取地址。异常对象必须刚在当前调用帧中分配，`field:code` 与提交类型相同。普通异常、名称相似的用户类型、未知 token、未持有的对象、`env` 别名、缺失/重复接口及降版产物均被拒绝。托管引用只能通过规定的取消与终态读取接口跨边界，不能借新版本导入任意对象指针。

ABI 夹具由 [GuestTaskCancellationFixture.cs](../../Tools/AvidScript.GuestIr.Tests/GuestTaskCancellationFixture.cs) 构造，供 IR 与 WASM backend 测试共同使用。它包含取消、故障和重复读取函数；正式 backend 保留类型目录、源码位置和 `guest_ir=24/1.23` 身份，规范化序列化前后产生相同 WASM。该夹具不是 C# 编译产物，也没有实现 handler 路由。现有 IR 22/23 的路由元数据不能直接改版本后冒充新取消分派。

## C# 控制流与资源释放

IR 24 新增 `async_exception_transfers`，记录 `end_catch`、`rethrow`、`propagate_exception` 的方法、基本块、后继以及异常 owner/type 局部槽。直接 Timer 路由增加 `cancellation`，绑定取消类型和源码 token。旧版本序列化不输出这些可选字段。

- Timer 取消恢复时创建一个持有异常对象的 Task，将其置为 `Cancelled` 后进入类型分派。创建或提交失败进入 trap，不能执行正常后继。
- Task await 的即时失败与回调恢复都读取真实终态异常，保留源 Task owner，再进入同一个 handler 分派入口。
- 正常离开 `catch` 时检查并释放 owner，同时清空 owner/type 槽；捕获后再次等待不会重复释放旧 owner。
- `throw;` 保留 owner，经过当前层 `finally` 后进入外层处理。方法边界通过 Task failure propagation 保留取消状态和原异常对象。

Task 局部变量和别名使用同一份所有权分析：普通后继、await 成功/故障/取消后继、catch 分派、`end_catch`、`rethrow` 与传播出口都必须纳入控制流。捕获异常消费的是 handler 持有的引用，不消费源码局部变量；后者可以跨后续挂起，再次等待同一个 Task。

受保护的局部 Task await 先获取独立的临时引用，沿用现有 IR await 路由的释放合同。即时完成时释放临时引用，挂起时由 continuation 接续持有；恢复进入 handler 前重新持有源码局部变量和别名，避免 callback 结束释放保存帧后留下悬空 token。本增量没有新增 Semantic 字段、IR 字段或 Host 导入，版本仍为 44/1.53 和 24/1.23。

当前仍要求汇合路径上的存活 Task owner 集合一致。若一个受保护 await 之后才声明新 Task，前一个 await 的失败路径可能没有该 owner；这种汇合仍以 `ASCS5403` 拒绝，不能直接取两条路径的并集并释放未初始化 token。

`ASIR1030/1031` 检查 await 路由、取消生产者和恢复状态；`ASIR1033` 检查消费、重新抛出和向外传播。遗漏整个方法的 Task 路由、缺失取消 owner、伪造类型、取消跳转到成功代码、缺失槽清零、错误 rethrow 和反向传播均拒绝。

## 已实现的 Semantic 合同

Semantic CLI 通过 `--async-cancellation-flow enabled` 启用本预览，同时要求 `--async-exception-flow enabled`；直接 Timer await 还需 `--direct-await-cleanup enabled`。内部 API 保留对应的 `enableAsyncCancellationFlow`、`enableAsyncExceptionFlow` 和 `enableDirectAwaitCleanup` 参数。关闭新开关时沿用 Semantic 43 的清理语义，不会自动启用取消 handler。

正式构建入口使用 `-LanguageErrors bounded -AsyncExceptionFlow -DirectAwaitCleanup -AsyncCancellationFlow`。只有成功的 Semantic 44/1.53 和非空异常计划才能授权新的取消导入；最终产物必须为 IR 24/1.23，并具有异常 catalog 和 owner 转移元数据。三个新接口逐项检查身份、签名、模块、调度类别与 ordinal，绑定包的同名声明不能绕过预览授权。

本预览沿用 bounded 模式的限制：关闭 Semantic/编译缓存与常驻编译 worker，拒绝预处理 Semantic 复用和 required worker，不向旧缓存发布新合同。构建报告记录三个预览开关及各编译阶段的实际调用次数；这不表示带新开关的缓存或 worker 已实现。

`SemanticAsyncExceptionPlan` 新增：

| 字段 | 用途 |
| --- | --- |
| `cancellation_type_id` | 取消的默认异常类型，由 Roslyn 注册完整父类链 |
| `exception_scopes` | 每个 try 的 Roslyn 区域、handler 顺序、父区域、分派入口与向外清理入口 |

新增三种控制转移：

| 转移 | 行为 |
| --- | --- |
| `end_catch` | 消费已处理的异常 owner，然后进入正常后继 |
| `rethrow` | 将已处理状态恢复为未处理状态，保留故障/取消种类并向外转移 |
| `propagate_exception` | 在方法边界传播未处理异常，保留 Task 的故障/取消终态 |

Task 的故障和取消进入同一个有序分派入口；直接 Timer await 只有正常和取消出口，仍不声明语言故障出口。reader 根据独立 scope 元数据核对入口、handler 类型、清理顺序和父区域，并检查所有权状态：未处理取消不能进入正常返回，已处理异常不能带着 owner 进入下一次 await。空 catch 也有明确的消费节点。

旧 42/43 合同、默认编译路径和已有 WASM 行为保持原定义。旧版本夹带新字段或转移、新版本缺失 scope/类型、伪造成功入口、跳过 handler、绕过 finally、错误 rethrow 均拒绝。内部调用需同时对 Guest lowerer 设置 `enableAsyncLanguageErrors: true`，才能生成 IR 24。

### Task 局部变量与别名的重复等待

共享源码新增 `RepeatedAsync(mode)`：先创建 Task 及别名，在 `try/catch` 中等待，捕获取消后通过普通 NextTick 挂起，再在另一个 `try/catch` 中等待同一 Task。四种模式覆盖首次等待尚未完成、首次等待已经完成、handler 提前返回，以及 handler 重新抛出。

- 正常重复等待得到 `16 + 16 = 32`；两次捕获取消得到 `20 + 20 = 40`。提前返回得到 `21`，重新抛出仍为原 `TaskCanceledException`，入口诊断保留内层 await 的源码 span。
- 两个 handler 的 `finally` 顺序为 `12`；提前返回和重新抛出只执行第一个，为 `1`。第二次等待已结束的 Task 不新增 callback。
- 每次 callback finalization 后执行托管 GC；在下一次等待中仍可读取原取消，最终 teardown 前 Task、continuation、managed roots、active frames 和 live objects 全部为零。
- 去掉别名的重复等待也通过 Semantic；遗漏别名清单，以及在可能失败的 await 之后才声明新 owner、再汇合到同一 handler 的源码均被拒绝。
