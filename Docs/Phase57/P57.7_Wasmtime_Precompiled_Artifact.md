# P57.7 Wasmtime 预编译制品纵向闭环

## 1. 状态

`WasmtimeSerialized` 的运行时消费路径已经打通，并通过 UE 5.8 Win64 Editor 构建与
Automation 验证。本批次完成的是可执行纵向切片，不代表 Editor 构建时预编译器、签名
包清单或移动端 AOT 已完成。

Phase 57 的 `P57-D06-ControlledLeadership` 继续保持 `Fixing`。预编译制品将编译成本
移出游戏启动路径，并为使用自定义 Wasmtime 编译配置提供入口，但本批次没有改变冻结

## 2. 实现范围

### 2.1 双执行路径

Wasmtime backend 现在按制品格式创建两种稳定执行路径：

| 制品 | 执行模式 | Stable backend id | 用途 |
| --- | --- | --- | --- |
| `WasmBytecode` | `Jit` | `wasmtime.cranelift.jit` | Editor 快速迭代、调试 |
| `WasmtimeSerialized` | `Aot` | `wasmtime.cranelift.precompiled` | PC 预编译发布制品 |

`Load(Bytecode)` 保持原有 JIT 行为。预编译 backend 必须使用 `LoadArtifact`，直接传入
WASM 会返回 `artifact_format_mismatch`，从接口层避免把 cwasm 与 canonical WASM 淆。
普通 `WasmBytecode` artifact 还要求 execution bytes 与 canonical bytes 逐字一致，确保
被 import/layout 合同验证的模块就是实际交给编译器的模块。

### 2.2 Canonical 与 execution 分离

`FAvidScriptVmArtifactView` 同时携带：

- `ExecutionBytes`：Wasmtime serialized module，实际用于反序列化执行；
- `CanonicalWasmBytes`：原始 WASM，只用于导入、ABI、内存布局与绑定合同检查；
- 两份字节各自的 SHA-256；
- Wasmtime/Cranelift 编译器 build identity；
- target triple；
- 包信任状态。

这使 backend 不需要解析 Wasmtime 私有制品格式，也不会因为采用预编译执行而绕过现有
WASM import/layout 合同。

### 2.3 Fail-closed 来源合同

调用 `wasmtime_module_deserialize` 前依次验证：

1. backend 与 artifact format 一致；
2. execution/canonical 字节均非空；
3. trust 必须为 `VerifiedPackage`；
4. target triple 与当前 Win64 backend 完全一致；
5. execution/canonical SHA-256 与清单身份完全一致；
6. canonical WASM layout 与 import contract 有效；
7. compiler build identity 与当前加载的 Wasmtime DLL、版本和配置完全一致。

当前 compiler identity 绑定 `Wasmtime 45.0.0`、Cranelift、`speed_and_size`、稳定 4 GiB
wasm32 内存策略和 DLL SHA-256。版本、DLL 或配置漂移时，旧制品会以
`artifact_compiler_mismatch` 拒绝，不进行兼容性猜测。

Wasmtime 官方明确说明 serialized module 不能接收任意不可信输入。因此
`VerifiedPackage` 不是 UI 标签：后续 Editor/package producer 必须只在签名清单、摘要和
构建来源均验证后创建该 artifact。SHA-256 本身只能证明字节完整性，不能证明发布者身份；
canonical WASM 与 serialized module 的语义配对也必须由同一个可信 manifest 绑定。当前
原生 VM 接口假定调用者是可信 package loader，不能直接暴露给脚本或网络内容。

## 3. C shim 与生命周期

C shim 新增 `module_serialize`、`module_deserialize` 和 serialized byte buffer 释放接口，
继续隐藏 Wasmtime C 类型和内存所有权。backend 反序列化后复用原有 store、linker、
import、instance、export cache、prepared call、guest memory、trap 与 unload 生命周期，
没有复制第二套执行框架。

Automation 使用生产配置完成真实闭环：

```text
canonical WASM -> module_new -> module_serialize
-> VerifiedPackage artifact -> LoadArtifact/module_deserialize
-> resolve avid_on_begin_play -> call
```

同一用例还验证 JIT 双字节视图分离、raw WASM、Untrusted、错误 SHA-256 和错误 compiler
identity 均在执行前稳定拒绝。

## 5. 剩余工作

1. 在 Editor/Build 层实现受控 precompiler，生成 serialized bytes 与 canonical WASM
   的统一 manifest，不让 Runtime 承担编译职责。
2. 为 manifest 增加签名与发布者验证，只有验证器能够产生 `VerifiedPackage`。
3. 构建支持 compiler inlining 的 Wasmtime 工具链，并把全部编译配置纳入 build identity。
4. 测量 cold load、module load 与首帧启动收益，再决定磁盘映射和制品缓存策略。
5. 继续使用冻结 12-kernel Gate 验证 steady-state 性能；预编译启动收益不能替代
   Wasmtime/V8 的 p95 与 kernel win-rate 门禁。
6. 移动端采用无运行时 JIT 的独立 AOT lane，不能直接复用 Win64 serialized artifact。

下一批优先实现 Editor precompiler 与 manifest provenance，使 C# 游戏脚本从“运行时可以
消费手工制品”进入“项目构建可自动生产、校验并选择制品”的完整工作流。
