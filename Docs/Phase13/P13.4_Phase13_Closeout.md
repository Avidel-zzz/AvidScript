## What Works Now

The UE side can already do this when the WASM module has the expected ABI:

- load a module with `avid_on_begin_play`
- call BeginPlay during activation
- call Tick through `TickLive`
- allow the module to call `env.actor_set_location`
- move an Actor from both lifecycle callbacks

## What Does Not Work Yet

The checked local C# toolchain does not produce a direct ABI module:

- .NET 8 `wasi-experimental` emits `dotnet.wasm` with exports `memory` and `_start`.
- .NET 8 `wasi-wasm` rejects `PublishAot=true` with `NETSDK1203`.
- .NET 9 rejects `wasi-experimental`.
- The Program Files .NET 9 workload installer fails in `Microsoft.DotNet.Installer.Windows.InstallerBase`.

## User-Facing Answer

You cannot yet start gameplay authoring by dropping in a C# WASM file. You can read and shape the intended C# API now, and the UE runtime is ready for a direct ABI artifact, but Phase 14 must solve the C# compiler/output strategy.

## Recommended Phase 14 Target

Phase 14 should choose and implement the real C# execution path:

- Option A: find or build a C# NativeAOT/direct WASM compiler path that exports `avid_on_begin_play` and `avid_on_tick`
- Option B: use a managed C# runtime embedding strategy in UE and keep WASM for sandboxed languages
- Option C: introduce an AvidScript C# source-to-WASM adapter that generates the proven direct ABI from a constrained C# subset

Option A is the cleanest if a stable toolchain can be made to work. Option C is the fastest controlled path if direct .NET export support remains unavailable.
