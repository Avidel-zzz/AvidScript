# P13.0 C# Direct WASM Binding Scope

## Status

- Status: Done
- Date: 2026-07-06
- Owner: Codex

## Goal

Phase 13 targets the shortest honest path to C# gameplay scripting on top of the existing AvidScript WASM runtime:

- show the C# source shape for BeginPlay and Tick
- keep the runtime ABI as `avid_on_begin_play` and `avid_on_tick(float)`
- use the current host import surface, starting with `env.actor_set_location`
- validate that UE can drive a module with C# ABI metadata through BeginPlay and Tick
- report whether the local .NET toolchain can emit a direct AvidScript-compatible WASM module

## Current Toolchain Finding

- `C:\Program Files\dotnet\dotnet.exe` is .NET 9.0.306, but `dotnet workload list` fails in `Microsoft.DotNet.Installer.Windows.InstallerBase`.
- .NET 9 rejects `wasi-wasm` with `The 'wasi-experimental' workload is not supported in .NET 9.`
- `C:\Users\user0\.dotnet\dotnet.exe` is .NET 8.0.416 and can install `wasi-experimental`.
- .NET 8 `wasi-experimental` can produce `dotnet.wasm`, but without AOT it exports only `memory` and `_start`; it does not export `avid_on_begin_play` or `avid_on_tick`.
- .NET 8 `wasi-wasm` reports `NETSDK1203` when `PublishAot=true`, so it is not currently a direct ABI compiler for this runtime.

## Acceptance

Phase 13 is complete when:

- the C# sample is checked in and readable
- `BuildCSharpActorLifecycle.ps1` writes a deterministic report
- `AvidScript.Guest.CSharp.SampleShapeSmoke` passes
- `AvidScript.Guest.CSharp.DirectAbiContractLifecycleSmoke` passes
- `AvidScript.Guest.CSharp.ToolchainReportSmoke` passes or warns only when the report has not been generated
- docs state clearly whether C# direct WASM is ready for user scripts

## Phase 13 Decision

Phase 13 does not mark C# direct WASM as ready for gameplay authoring. It proves the UE/WAMR lifecycle contract is ready, and it proves the current local .NET WASI route is not yet a direct ABI producer.
