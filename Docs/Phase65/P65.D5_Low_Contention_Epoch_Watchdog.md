# P65.D5 低竞争 Epoch Watchdog

## 问题

旧 watchdog 在每次顶层 guest call 的 `Arm` 和 `Disarm` 中都获取全局 critical section，并按 token
查询 `TMap`。高频 Tick/event callback 因此把实例本地调用串行到全局锁上，即使脚本从未超时也要
支付两次锁竞争和两次容器查询。

## 设计

- 注册时为每个 VM 实例创建 thread-safe shared entry，预计算 timeout cycles。
- `Arm` 以 release store 发布绝对 deadline，并唤醒共享 watchdog；`Disarm` 只用 release store 清零。
- watchdog 以 acquire load 扫描 deadline，到期后通过 CAS 领取该次超时，再递增对应 Wasmtime
  engine epoch。重入或重新武装改变 deadline 后，旧扫描不能误取消新调用。
- 注册、注销和后台扫描仍在同一 critical section 内。注销返回后，后台线程不可能继续访问即将释放的
  engine；entry 的 shared lifetime 只解决存储生命周期，不替代这一同步边界。
- `Disarm` 不再唤醒线程。线程最多在已经安排的旧 deadline 提前空醒一次，不影响超时上界，也避免
  正常成功路径的第二次内核事件通知。

这项改动只移动同步位置，没有关闭 fuel、epoch deadline、100 ms watchdog、memory limiter 或
Host-call budget。

- UE5.8 `AvidTPSTemplateEditor Win64 Development` no-clean 增量构建成功。
- `AvidScript.VM.Wasmtime.ExecutionBudget`：发现 1 项，1/1 Success，Automation queue 正常完成。

正式 callback 收益将在 hot-result 批次合并后使用冻结的 Phase56 profile 测量；本小节不以结构变化
代替性能证据。
