# Phase 65.D31：Wasmtime 代码生成归因

## 目标

定位 identical-WASM 门禁中 `scalar_float`、`simd128`、`mixed_gameplay` 与
`data_branch` 的剩余差距。D31 不通过放宽门禁、修改 workload 或关闭通用安全边界制造领先，
而是先把编译器代码质量与执行期 containment 成本分开测量。

## 当前事实

Win64 性能 profile 已使用 Wasmtime v45、Cranelift `speed`、backtracking register allocator、
全量 compiler inlining、x86-64-v3、alias analysis、固定 4 GiB wasm32 reservation、关闭 NaN
canonicalization，并使用 `fastest-runtime` 构建。D9 已移除无预算执行的 fuel 插桩，但保留 epoch
interruption 和 Spectre mitigation。常规“打开优化等级”路径已经用尽。

D29 的正式结果仍是唯一公开基线：12-kernel P95 几何均值 `1.131x`，胜率 `33.3%`；主要差距为
`scalar_float 2.096x`、`simd128 1.334x`、`mixed_gameplay 1.329x` 和
`data_branch 1.137x`。D30 没有形成合格的新性能样本，因此 README 暂不更新。

## 架构冻结

1. 新增轻量 native profile probe，直接加载仓库中的同一份 WASM，并链接项目锁定的 patched
   Wasmtime DLL；不启动 Editor，也不复用正式 benchmark 目录。
2. probe 只改变一个编译配置变量，至少覆盖 production baseline、关闭 epoch、关闭 Spectre、两者均
   关闭四种组合；运行顺序轮换，输出机器可读 JSON，并校验每种配置的结果一致。
3. probe 数据是 diagnostic attribution，不能写入 README、不能替代 freezer 组装的正式宿主，也不能
   与不同 attempt 的样本拼接。
4. 如果 epoch 是主要成本，后续只允许为经过 compiler provenance 与完整性证明的 C# 产物设计
   cooperative-safepoint profile；原始 WASM、第三方模块和不可信 mod 继续使用 epoch fail-closed。
5. 如果 Spectre 只影响内存 workload，不以关闭 mitigation 作为生产默认优化；先优化生成代码和内存
   访问形态。
6. 如果配置差分无法解释缺口，后续转向 Cranelift 反汇编、版本对照和 C# Guest IR lowering，不继续
   堆叠手写 UE API 特例。

## 批次

- D31.A：实现 native profile probe、构建脚本和输出合同。
- D31.B：运行四个落后 kernel，形成配置成本归因。
- D31.C：根据归因选择 production 优化，并在批次末集中执行 UE build、focused Automation 与正式
  performance gate。

## D31.A/B 结果

native probe 已从提交 `b088af47` 构建，使用锁定的 patched Wasmtime DLL、相同 kernel WASM、
`5` 次预热和 `30` 个轮换计时样本。baseline 自动校准到每个样本至少 `5 ms`；四种配置在每个 kernel
上的 checksum 完全一致。原始 diagnostic artifact 为
`d31-native-profile-full-b088af47.json`，SHA-256 为
`d5440751857ac888bdd36dd31a4f079986adec4bf76ccbf2818837f0425ac10d`。

| Kernel | production P50 | epoch off P50 | epoch off / baseline | Spectre off / baseline |
| --- | ---: | ---: | ---: | ---: |
| `scalar_float` | `2.480 ns` | `1.188 ns` | `0.479x` | `1.004x` |
| `simd128` | `1.554 ns` | `1.192 ns` | `0.767x` | `1.000x` |

结论很明确：四个正式落后项的共同主要成本是 epoch interruption 在循环安全点上的检查，不是 Spectre

Gate 数据。

## D31.C 决策

后续不关闭 production 默认 epoch，也不关闭 Spectre。优化方向确定为“可信编译产物的协作式安全点”：

1. C# compiler 在循环与递归边界生成有界、可验证的 safepoint metadata 和 polling；
2. package/cook 阶段签名该 metadata，并把 compiler identity、schema 与代码哈希纳入 artifact provenance；
3. VM 只有在验证器证明所有回边与递归环都被覆盖时，才选择无 epoch 的 trusted-cooperative profile；
4. 原始 WASM、缺少证明、证明失配或第三方模块继续使用 epoch profile，任何不确定性都 fail-closed；
5. trusted profile 仍保留 ObjectHandle、host-call budget、线性内存限制、stack budget、Spectre 与所有
   Runtime 生命周期栅栏。

这条路径把每次 loop backedge 的通用 VM 检查替换为编译器可批处理的显式安全点，同时不把无限循环
风险转嫁给游戏线程。D31.C 的下一实现单元先定义 proof schema、验证器和 profile selection，不立即
改变默认运行行为。

## D31.C2：编译器协作式安全点

提交 `fef8bcd2` 为 C# Guest IR 到 WASM 的编译链加入 opt-in 的 cooperative safepoint 生成器，默认编译
结果保持原有 epoch-only 形态。启用 `--cooperative-safepoints` 后，编译器会：

- 对 CFG 的每条 DFS feedback edge 在源 block 终止符前插入计数式 poll；
- 对直接递归和互递归调用环中的函数在入口插入 poll；
- 以共享 mutable global 进行批量计数，默认每 `256` 个安全点调用一次内部 host import；
- 写入 `avidscript.safepoints` custom section，记录 schema、模式、间隔、循环覆盖数、递归覆盖数与
  Guest IR 版本；
- 将内部 `avid_cooperative_safepoint_poll` 放入静态 Host ABI，但不暴露给 `env` 兼容层，也不计入
  游戏脚本的公开 host-call budget。

CLI 支持 `--safepoint-interval <1..65536>`，非法区间 fail-closed。WAMR 和通用 Runtime dispatcher 仅提供
ABI 兼容的空 poll；Wasmtime 同样先保持空 poll，因此本单元只建立确定性编译产物与可解析证明，尚未
切换 production profile，也尚未形成 wall-clock deadline。下一单元必须由 runtime verifier 解析并核验
custom section、代码覆盖与 package provenance 后，才允许 no-epoch profile 执行。

## D31.C3：Runtime Proof 冻结

`avidscript.safepoints` 只是一份可伪造的模块声明，字段齐全不等于结构已经安全。C3 禁止用 metadata
存在性直接关闭 epoch，并按以下顺序落地：

1. VM module inspector 严格解析唯一 proof section，限制大小、字段、数值范围和内部 poll import；未知、
   重复或不一致内容 fail-closed；
2. artifact compiler 把 canonical WASM hash、受控 C# backend 身份、proof schema 与 compiler profile
   绑定到 attestation/cache identity，no-epoch request 不接受调用方裸布尔值；
3. verifier 必须确认生成代码中的循环回边与递归环均受 poll 支配，不能只相信 section 内的计数；
4. Runtime poll 使用调用级 deadline/cancellation 状态并产生稳定错误类别，超时后终止当前入口；
5. 只有 Win64 `WasmtimeSerialized + VerifiedPackage + verified proof` 可选择 trusted-cooperative；JIT、
   WAMR、Android、第三方 WASM、旧 schema 和验证失败产物继续走 epoch 或显式 fallback。

C3.1 仅交付只读 parser 与一致性检查，不改变 profile selection。C3.2/C3.3 完成结构验证和 deadline 后，
才允许 Editor publisher 请求 no-epoch artifact；这条顺序防止优化途中出现不可中断的游戏线程。
