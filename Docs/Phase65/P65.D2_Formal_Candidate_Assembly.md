## 已修复的阻断

校准请求原先使用旧版 `Get-SidecarWasmtimeCompilerIdentity`，缺少 compiler profile、target、
最大 WASM 栈、fuel 与 epoch interruption，并使用旧字段名 `dll_sha256`。运行时 C++ backend
返回的是完整新身份，二者因此在计时前正确地 fail closed。

修复后，PowerShell runner 按 lock 验证所有安全和性能开关，并生成与
`BuildAvidScriptWasmtimeCompilerIdentity` 字节一致的身份字符串。契约测试固定完整字符串，后续
改变编译配置时必须同步更新两侧，禁止通过模糊比较或删除字段绕过来源校验。

第二次 diagnostic 进一步发现 native gameplay oracle 将 32 次属性写入实现为
`NativeSetScalar()` 调用，因而把一次 small frame 错计为 78 次 fixture function call；冻结合同和
所有脚本 lane 的真实语义都是 46 次函数调用加 32 次属性写入。native baseline 已改为直接写入
`ScalarValue`，保留相同 checksum/final state，同时避免把属性成本伪装成 UFunction 成本。契约测试
要求四次 batch 写入均为直接字段赋值，并禁止该 helper 再调用 `NativeSetScalar()`。

同一轮还暴露出旧 adaptive oracle 只把 scalar/property/event 计入 native hit，仍把 vector/object
假定为 ProcessEvent fallback；当前 prepared reflection receiver 已经覆盖 gameplay frame 的全部五类
操作。C++ runner 和 PowerShell Gate evaluator 现统一按 `logical_operations_per_frame` 计算 gameplay
adaptive native hit，small frame 为 78、fallback 为 0。correctness 错误也新增 expected native/fallback
字段，后续矩阵漂移可以直接定位，不再从无关的 data-oriented 诊断字段反推。

第三次候选 `fa58c38d2f7f1d64bd07` 已通过 gameplay diagnostic，但 Phase56 micro formal 在校准阶段
触发 `execution_fuel_exhausted`。原因是生产 Session 的每次入口 `50,000,000` fuel 适合普通游戏脚本
防失控，却不足以覆盖正式基准为达到 5 ms 计时下限而放大的单次确定性循环。

修复采用开发基准专用的加载前预算注入：仅在 `WITH_DEV_AUTOMATION_TESTS` 下开放，且存在 live runtime
后不能修改。Perf Harness 将 fuel 提高到 `2^32` units、Host-call 上限提高到 `uint32` 最大值，同时继续
强制 100 ms epoch watchdog 和 64 MiB 线性内存上限。生产 Session 默认值保持不变，正式矩阵仍保留
超时、内存与 Host crossing 的 fail-closed 边界，不以关闭安全门禁换取成绩。
