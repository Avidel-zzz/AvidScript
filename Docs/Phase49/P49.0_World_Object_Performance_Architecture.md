# P49.0 世界、对象创建与性能架构

> 状态：已批准并进入实施
>
> 日期：2026-07-23
>
> 主线：C# -> Roslyn Semantic -> Guest IR -> WASM -> WAMR -> UE5.8

## 1. 阶段目标

Phase 49 将 Phase 48 的“控制预放置 Actor”扩展为“脚本能够创建、操作并销毁世界对象”的闭环，同时建立可重复的性能合同。

完成后，项目 C# 脚本应当能够：

- 使用生成式、类型安全的 class reference 引用原生类和 Blueprint class；
- 从当前 Runtime Session 获得可信 World Context，而不是传递宿主裸指针；
- 通过一个通用对象生命周期 ABI Spawn 和 Destroy Actor；
- 对项目 UCLASS/UFUNCTION 生成 facade，不为普通 API 新增手写 VM enum、WAMR wrapper 或 Runtime switch；
- 对类约束、对象句柄和 World 生命周期失败关闭；
- 在 UE5.8 Win64 Editor 中运行一个动态生成对象的真实 C# Demo；
- 产出 Native、Binding、WASM 路径的可重复 benchmark 和结构性性能计数。

## 2. 非目标

以下内容不进入 Phase 49 的必达范围：

- 任意 UStruct 的递归封送、FHitResult 完整读写；
- TArray、TMap、TSet；
- Delegate、多播事件、异步任务和网络 RPC；
- 脚本声明真正的 UCLASS、UPROPERTY 或 Blueprint 基类；
- NewObject 的通用 GC 强所有权模型；
- Cook、Shipping、Android、iOS；
- 与 Puerts 或 Unreal AngelScript 的未经同机同负载验证的绝对性能结论。

这些能力分别进入后续通用类型、脚本类、工具链和平台阶段。

## 3. 设计原则

### 3.1 广覆盖和高性能分层

普通 UFunction 使用现有 descriptor、reachability slice 和缓存 invocation plan。对象创建属于跨 World、类约束、句柄和副作用的核心能力族，使用固定通用 ABI，不伪装成逐函数手写绑定。

### 3.2 热路径禁止名称解析

以下工作只能发生在生成期或 package load：

- class path 和 Blueprint asset path 解析；
- UClass 继承约束验证；
- UFunction、FProperty 和静态 CDO 定位；
- 参数布局、frame 对齐和 marshalling plan 构建；
- World Context 元数据判定；
- class reference ordinal 分配。

Spawn、Destroy、Tick 和动态 binding dispatch 不得按名称搜索 UClass/UFunction/FProperty。

### 3.3 成功路径不构造诊断

成功路径只传递固定布局值、ordinal、slot/generation 和预分配 scratch。FString 错误详情、对象路径和源码诊断只在失败路径创建。

### 3.4 对象能力不暴露裸指针

Guest 只能持有：

- package-relative class reference ordinal；
- UObject slot/generation handle；
- 固定布局的 value struct。

WASM 不接收 UClass、UObject、UWorld 或 FProperty 地址。

### 3.5 性能结论必须可重放

性能改动必须同时提供：

- 行为正确性测试；
- 相同进程内的 Native 对照；
- warmup、sample count、P50、P95；
- host crossing、名称查找、类加载和 registry resolve 计数；
- 引擎版本、Target、配置和提交身份。

## 4. 项目 API Profile

新增项目级 binding profile specification，与现有已经解析完成的 `FAvidScriptBindingSelectionProfile` 分离。

Profile 输入包含：

- package name；
- 允许扫描的 `/Script/<Module>`；
- 显式原生 class path；
- Blueprint class asset path 和脚本名称；
- class base constraint；
- include/exclude member；
- editor-only 和 runtime policy；
- asset load policy。

Profile resolver 将 specification 转换为现有 selection model。后续 descriptor generator、C# renderer、binding slice 和 Runtime package 继续复用，不建立第二条普通 UFunction 管线。

Profile 的选择哈希至少包含：

- UE BuildId 和引擎版本；
- module/class/member 规则；
- Blueprint class path 和 base constraint；
- generator schema/version；
- 反射成员 canonical identity。

输入哈希不变时复用 descriptor 和 facade，避免每次保存 C# 都重新扫描完整反射表面。

## 5. Class Reference 合同

### 5.1 Descriptor

Binding package 增加排序稳定的 `class_references`：

| 字段 | 含义 |
| --- | --- |
| `stable_id` | class path、base constraint 和 load policy 的稳定身份 |
| `ordinal` | package-relative 连续序号 |
| `script_name` | 生成 C# 成员名 |
| `class_path` | 原生或 Blueprint generated class path |
| `base_class_path` | 必须满足的 UClass 继承约束 |
| `load_policy` | EditorLoad 或 CookRequired |

ordinal 按 stable id 排序后生成，不能依赖 UObject 枚举顺序。

### 5.2 Runtime

Package load 时：

1. 解析 class path；
2. 加载或定位 UClass；
3. 验证 `IsChildOf(BaseClass)`；
4. 将 UClass 指针写入不可变 class plan；
5. 记录 Cook 依赖和 package hash；
6. 任一项失败则拒绝整个 candidate package。

运行时 Spawn 只使用 ordinal 对 class plan 做 O(1) 索引，不读取字符串。

### 5.3 C# Facade

生成 facade 使用只包含一个 `int Ordinal` 的 readonly class reference value：

```csharp
public readonly struct TSubclassOfAActor
{
    internal int Ordinal { get; }
}

public static class ProjectClasses
{
    public static TSubclassOfAActor PlayableProjectile => new(3);
}
```

class reference 构造只发生在 Guest 内，不产生 host crossing。

## 6. World Context

`FAvidScriptBindingInvocationContext` 扩展只读 World Context，来源必须是当前 Runtime Session 的 owner：

```text
Session owner -> GetWorld() -> validated UWorld weak reference -> invocation context
```

规则：

- World 在 Session load/start 时缓存为弱引用；
- 每次对象生命周期调用只做有效性检查，不重新遍历 GEngine world contexts；
- Guest 不传 World 指针或可伪造 world id；
- static Blueprint Function Library 的 `WorldContext` 参数由 invocation plan 注入，不出现在 C# 方法签名和 WASM ABI；
- World teardown 后调用以稳定错误分类失败，不尝试回退到任意 Editor World。

## 7. 对象生命周期 ABI

新增一个生成式对象生命周期 capability family：

```text
avid_object_spawn_actor(class_ordinal, transform_address, collision_mode, result_address) -> status
avid_object_destroy_actor(slot, generation) -> status
```

### 7.1 Spawn

- class ordinal 从当前 Binding Package 的缓存 class plan 解析；
- transform 从 Guest Memory 固定布局读取；
- World 来自 Invocation Context；
- Spawn 成功后注册进 `FAvidScriptObjectRegistry`；
- 返回 slot/generation，不返回裸 Actor 地址；
- UE Spawn 失败不留下有效 handle；
- class mismatch、无效 World、越界 ordinal 和坏 Guest Memory 全部失败关闭。

### 7.2 Destroy

- 先通过 slot/generation 解析 Actor；
- 验证 Actor 属于当前 World 且未处于销毁状态；
- 调用 Destroy；
- 成功后释放 registry handle 并推进 generation；
- 重复 Destroy 和 stale handle 返回稳定失败，不误伤复用槽位的新对象。

### 7.3 所有权

Phase 49 的 SpawnActor 由 UWorld 持有，registry 只保存弱引用。Session stop 默认不销毁已经提交到世界的 Actor。

NewObject、强引用 lease、脚本所有对象随 Session 自动回收不在本阶段实现。

### 7.4 Reload

Spawn 和 Destroy 当前不是可逆 host effect：

- 初次 load 和 active runtime 事件允许执行；
- candidate reload 持有 HostEffectJournal 时拒绝 Spawn/Destroy；
- 返回 `binding_reload_effect_unsupported`；
- candidate 失败时旧 runtime 和世界状态保持不变。

后续只有在建立对象身份迁移和 spawn intent reconciliation 后才允许 candidate 执行该能力。

## 8. 安全类型转换

对象 handle 的 C# wrapper 可以向已知基类进行零 crossing 的句柄复制，但 Runtime 在实际调用目标 API 时仍使用缓存 OwnerClass 校验对象。

动态向下转换使用一个通用 class ordinal 检查：

```text
avid_object_is_a(slot, generation, class_ordinal) -> bool
```

检查只执行 registry resolve 和 `IsA(CachedClass)`，不按名称解析。组件查找继续通过普通 reflected binding 或后续批量 capability，不在 Phase 49 建立按组件类型手写 API 表。

## 9. 性能架构

### 9.1 两层调用

- Tier 0：普通 reflected UFunction，ordinal -> immutable invocation plan -> ProcessEvent。
- Tier 1：对象生命周期、批量 Transform 等高频或跨所有权能力，使用固定 capability family。

Tier 1 只能服务可泛化的能力族，不能退化成按 UFunction 逐项维护的快速通道。

### 9.2 结构性预算

| 操作 | 预算 |
| --- | --- |
| class reference 获取 | 0 host crossing、0 名称查找 |
| SpawnActor | 1 guest-to-host crossing |
| DestroyActor | 1 guest-to-host crossing |
| class ordinal resolve | O(1) 数组索引 |
| UObject resolve | O(1) slot/generation |
| warm Spawn/Destroy wrapper | 0 class load、0反射扫描 |
| 普通 reflected dispatch | 0 UFunction/FProperty 名称查找 |
| 成功路径诊断字符串 | 0 |

### 9.3 时间预算

- 现有 typed binding microbenchmark 不得比冻结基线回退超过 5%；
- 对象生命周期 benchmark 以 Native Spawn/Destroy 为同进程基线；
- 首次 Phase 49 只建立 baseline，不用跨机器绝对毫秒作为硬失败；
- 后续提交对 wrapper overhead 的 P50/P95 回退超过 5% 时失败；
- 噪声大于 5% 时增加 sample，禁止放宽门槛掩盖抖动。

### 9.4 编译与生成预算

记录 cold/warm 两种 profile generation：

- 反射 profile resolve；
- descriptor generation；
- facade render；
- reachability slice；
- C# Guest build。

warm 输入未变化时必须命中缓存，重复反射扫描和 facade 写盘次数为 0。

## 10. Benchmark 矩阵

| 维度 | Native 对照 | AvidScript 路径 | 指标 |
| --- | --- | --- | --- |
| class resolve | cached UClass 指针 | class ordinal plan | P50/P95、查找次数 |
| handle resolve | Actor 指针 | registry slot/generation | P50/P95 |
| Spawn | UWorld::SpawnActor | WASM capability | P50/P95、crossing |
| Destroy | AActor::Destroy | WASM capability | P50/P95、crossing |
| reflected call | direct C++ | cached ProcessEvent plan | P50/P95 |
| package load | 手工准备 | descriptor/class plan load | load time、class count |
| warm build | 无 | unchanged profile rebuild | elapsed、cache hit |

所有数据标记为 UE5.8 Win64 Development Editor/NullRHI，不外推为 Shipping 或移动端结论。

## 11. 与成熟方案比较的证据标准

AvidScript 可以对外陈述已经验证的结构性优势，例如 reachability slicing、WASM 隔离、slot/generation handle、candidate reload fail-closed 和 crossing batch。

只有满足以下条件后才能声称性能领先 Puerts、UnLua 或 Unreal AngelScript：

- 同一机器；
- 同一 UE 版本或等价引擎构建；
- 同一玩法和对象数量；
- 相同 Development/Shipping 配置；
- 相同 warmup、sample 和统计方法；
- 公开 benchmark 源码与原始报告。

在参考框架无法安装到同一 UE5.8 工程时，只报告 AvidScript 相对 Native C++ 和自身历史基线，不编造横向结论。

## 13. 完成定义

Phase 49 只有在以下条件全部满足时关闭：

- 项目普通 UFunction 不需要手写 wrapper；
- Blueprint class reference 在 package load 时解析并验证；
- C# Demo 动态 Spawn、操作、Destroy Actor；
- stale handle、wrong class、invalid world、candidate reload 均失败关闭；
- warm hot path 的名称查找和 class load 计数为 0；
- Spawn 和 Destroy 分别保持单次 host crossing；
- 性能报告包含 Native 对照、P50、P95 和结构计数；
- 代码冻结后完成一次集中审查和一次完整 AvidScript Gate；
- 没有 Blocker、Critical 或 Important 阶段债务。
