# P49.4 动态投射物 Gameplay 实现结果

## 结论

P49.4 gameplay 已经把 Phase 49 的 class reference、World Context、对象生命周期 ABI 和普通生成式反射调用串成一条真实 C# 游戏逻辑链路。脚本可以在一次性 Timer 中创建项目 Blueprint 投射物，在 Tick 中调用生成的 Actor API，并在后续 Timer 中销毁对象。

这不是为投射物手写的一组 UE wrapper。`SpawnActor`、`DestroyActor` 和 `IsA` 来自共享对象生命周期能力族；`K2_GetActorLocation` 与 `SetActorScale3D` 仍由项目 profile、reflection descriptor、C# facade 和缓存 `ProcessEvent` plan 生成。

## 游戏逻辑闭环

脚本执行顺序如下：

1. `BeginPlay` 只注册一次性创建 Timer，不直接修改 World；
2. Timer 使用 `ProjectClasses.TwinStickProjectile` 与 `FTransform` 调用 `UE.SpawnActor`；
3. 脚本保存返回的 `AActor` generational handle，并用 `UE.IsA` 验证动态类型；
4. `Tick` 调用生成的 `GetActorLocation` 与 `SetActorScale3D`；
5. 后续 Timer 调用 `UE.DestroyActor`，随后清除脚本侧活动状态；
6. Runtime registry 释放 handle，旧 slot/generation 再解析时得到 `generation_mismatch`。

`Projectile` 与活动计时字段标记为 `[AvidTransient]`，避免把 World 对象句柄错误地迁移到新 runtime。对象生命周期资源需要候选脚本重新获取，而不是复制旧 runtime 的局部句柄。

## 热重载防御

自动化构建了同一逻辑 `ModuleId` 的候选脚本。候选 `BeginPlay` 故意直接调用 `SpawnActor`，Runtime 因存在 host-effect journal 而以 `binding_reload_effect_unsupported` 拒绝该候选。

用例确认：

- reload transaction 与 rollback 路径均被执行；
- 候选没有创建第二个投射物，也没有改变 registry 数量；
- 旧 runtime 和旧投射物继续有效；
- 旧 runtime 后续 Tick 仍能修改 scale；
- 最终销毁后旧 handle 失效，owner handle 保持有效。

当前策略是明确失败关闭，不宣称已支持 Spawn/Destroy 副作用的事务补偿。

## 端到端证据

聚焦自动化从真实源码开始，经过：

```text
C# source
-> project profile
-> descriptor / generated facade
-> Roslyn semantic
-> Guest IR
-> WASM
-> WAMR
-> UWorld
```

测试在真实 game `UWorld` 中验证：

- 创建对象的动态类是目标 Blueprint，而非仅验证 native base；
- 初始位置为 `(300, 0, 150)`，初始 scale 为 `(1, 1, 1)`；
- 两次旧 runtime Tick 将 scale 依次更新为 `1.1` 和 `1.2`；
- Spawn 后 registry 包含 owner 与 projectile 两个 live handle；
- Destroy 后只保留 owner，保存的 projectile handle 被 generation 防护拒绝。

首轮脚本构建暴露了一个正式 C# lowering 边界：把 `Projectile.HasHandle && UE.IsA(...)` 的结果直接写回字段时，Roslyn CFG 会产生可写 `flow_capture_reference`，当前 Guest IR lowerer 只支持读取 capture value，不能把 capture register 当 lvalue。样例改为等价的显式分支后，真实构建和自动化均通过。该限制已记录，后续应扩展 location-aware lowering，而不是错误放宽 capture register 写入。

- 与外部脚本框架的跨机器性能优越性。
