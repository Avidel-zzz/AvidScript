# P64.D 原生分配追踪

状态：架构 v13，采集与四组离线查询已验证；D07 保持 Fixing，完整长稳与平台目标不变。

## 范围与依据

[引擎内存归因](P64.D_Memory_Attribution.md)发现：显式 LLM 的第 50～100 轮进程提交量增加
3.109 MiB，而 LLM Platform 只增加 0.125 MiB。Trace 与 FName 容量稳定，不能再仅用这些
计数判断原生堆/JIT 所有权；本批获取分配栈和存活区间，不重复只延长采样时间。

当前终端不是管理员。Windows WPR 的 VirtualAllocation/Heap 路径需要额外系统权限及可选注册表
配置，本批不修改这些设置。改用源码 UE5.8 的进程内 Memory Trace 与 Unreal Insights 离线导出。
引擎 WindowsMemoryTrace 已通过 Detours 记录 VirtualAlloc/VirtualFree 等调用；不自行实现 hook。

## 合同

- `InvokeAvidScriptUiSaveDemo.ps1 -Mode VerifyWorld -TraceMemory` 在进程启动时附加
  `-trace=memory,bookmark` 与唯一 `-tracefile`，其他模式拒绝此开关；默认行为不变。
- trace 文件仅写入本次 RunRoot，与报告、日志和隔离 UserDir 共同归属一个运行。
  请求采集时文件缺失或为空则失败；最终记录字节数、SHA-256，不能复用旧文件。
- Editor 私有 WorldMemory 在每轮 GC 采样末尾发出 `AvidScript.WorldGC.<cycle>` 书签。
  未开启追踪时不保存额外历史，不改 VM/Runtime/Guest ABI 或游戏流程。
- World 动作通过与 trace 采集成功不代表离线分析成功。分析必须找到指定书签、导出完整查询结果，
  保留工具日志、查询窗口和符号解析边界；不把空文件或 exit 0 单独当成分配栈证据。
- 先执行 50 次切图，保留第三轮预热及中点/终点查询；开启追踪有观测开销，不与既有无追踪
  运行的绝对内存/耗时直接比较优化幅度。资源限制或工具失败时如实记录，不静默降低数据范围。

## 重要限制

UE5.8 Windows hook 主要记录 reserve，以及 Address=null 的 commit；在已有预留区内的 commit/
decommit 不构成完整事件。因此 System memory 大小不能等同进程 commit，也不能把 WASM 4 GiB
预留地址空间当成实际内存泄漏。普通 Windows HeapAlloc 的每个小块也不保证由该路径覆盖。
分析应分别检查 UE 分配与系统预留的保留栈，必要时继续补充系统级或 allocator 专项证据。

## 模块与验证

主线修改 Build 入口/World runner、Editor 私有书签和中文文档；独立写集检查 Wasmtime 生命周期，
不与采集代码交叉编辑。集中完成一次受影响 Editor no-clean UBT、World 合同与真实 trace 采集，
复用官方 Insights 查询，不新建通用规则引擎。仅对有明确来源的产品问题实施优化，再做一小时复验。

### 下一步定位

1. 可见 Wasmtime 调用链的净增全部来自 `SetUtf8Value → FStrProperty::SetPropertyValue`：
   3→50 为 329 项/9776 字节，25→50 为 175 项/5200 字节，均为每轮 7 项/208 字节。
   优先检查通用反射参数帧的构造/析构及失败路径，不先归咎于 Wasmtime 内部缓存。
2. Blueprint 引脚创建每轮净增 43 项；引擎 `FPinDeletionQueue` 在 WITH_EDITOR 下继承
   FTickableEditorObject，DestroyImpl 将引脚放入队列，由 Tick/Purge 真正删除。
   当前使用 Editor 二进制的 `-game` 流程，这为延迟删除队列未消费提供了具体线索，仍需验证。
   不手动 Purge 或清缓存来制造较低结果，也不把此编辑器路径直接等同于 packaged Game。
3. 同期进程提交量在第 25→50 轮增加 0.941 MiB，trace 净分配约 1.492 MiB；两者不是相同口径。
   保留全部既有基线，修复明确的产品保留问题后，再区分 Editor 工具开销与包内持续运行结果。

## 所有权审查发现

Wasmtime 适配层的 engine/module/linker/store、C 包装、trap/error 和回调 context 有对应释放路径；
epoch 线程与 DLL 是复用的常驻资源，不随每次切图新增一份。这些源码路径不能证明第三方内部无泄漏。

另外发现两处同一 backend 长期重用时的无界保留，记为 `P64-D08-BackendReloadRetention`：

- `AvidScriptWasmtimeBackend.cpp`：ResolveExport 追加 ExportEntries；PerformUnload 释放 function
  包装并清空名称索引，但旧 Entry 及其名称保留至 backend 析构。Prepared call 的 Target 指向 Entry，
  不能直接 Reset 数组，否则会把当前的 stale-call 检查变成悬空指针访问。
- AdvanceBackendInstanceIdentity 每次卸载向 OwnedBackendInstanceIdentities 追加身份，空卸载也会
  增长；历史集合用于区分 stale/foreign handle。修复应使用有界的 owner/代际表示并保留拒绝语义，
  不能简单删掉身份验证或保留无限历史。

此前 100 次 LLM 切图和本次 50 次追踪中，backend 创建/销毁计数都在变化，不能只凭 live=2
断言始终是同两个对象。
上述长期重载保留机制已由源码证明，是否参与本次 World 增长及贡献字节仍须运行证据。
在分配追踪候选冻结期间不修改 VM，避免污染对照；下一集中修复批处理有界句柄/身份生命周期。
