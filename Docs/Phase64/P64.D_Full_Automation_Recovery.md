# Phase 64 完整 Automation 隔离恢复

## 背景

首次冻结候选 `cb808b9` 的完整 `AvidScript.*` Automation 实际执行 461 项，其中 451 项成功、
10 项失败。该候选及其 `C:\tmp\AvidScript\P64Gate\cb808b9-20260906-001` 证据永久保留为失败记录，
不得用于 attestation。失败集中暴露的是测试前置制品、全局 Generated Type package 状态和回调授权窗口
之间的隔离问题，不是单个业务样例的随机波动。

## 修复

- 自动创建的 `UWorldSubsystem` 与 `UGameInstanceSubsystem` 在未安装 Generated Type package 时静默休眠；
  package 存在时仍沿用统一 Runtime Host 激活，不引入 Demo 专用分支。
- `GameplayEvent.ObjectHandle` 仅在对应 typed callback epoch 内加入 Session capability，回调结束立即恢复
  原授权视图。Guest 仍只接触 generational handle，不暴露原始 `UObject*`。
- stale generation 导致 Session fault 时，按既有隔离合同回收该 Session 拥有的 Actor；测试不再要求故障对象
  脱离 Session 存活，非本 Session 的 sentinel 仍保持有效。
- 新增 `Build/PrepareAvidScriptAutomationFixtures.ps1`，固定 `.NET SDK 8.0.416`，在一次入口中生成
  Release ActorLifecycle 与启用 instrumentation 的 DebuggerPIE fixture，并写出机器可读报告。

没有修改 Wasmtime/WAMR backend。`GeneratedCSharpLifecycle` 中空 RootComponent 的
`binding_target_invalid` 是故意构造的负例；历史成功矩阵也包含同类日志。另用独立 WebAssembly import
探针确认 root/location handle 传输顺序正确，因此不把预期告警误判为后端缺陷。

## 流程教训

- 本轮曾误用 PATH 中的系统 `dotnet`，被 `global.json` 固定的 8.0.416 正确拒绝；之后所有托管命令均
  显式使用固定 host。fixture 准备入口现在会先校验精确 SDK，避免环境漂移进入昂贵 Automation。
- 读取证据时曾把多个命令用 `;` 或 `&&` 串联，导致退出码和输出域不清晰。后续保持一个命令只产生
  一个证据域，并由 Harness/报告聚合结果。
- 完整 Automation 前必须先准备显式 fixture，再启动唯一 Editor 进程；不依赖此前某项测试留下的文件
  或全局 package 状态。失败候选不就地修补后继续 attestation，必须重新冻结新提交。
