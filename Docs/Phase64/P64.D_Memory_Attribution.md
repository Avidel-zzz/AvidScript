# P64.D World 内存归因

状态：诊断接口与 100 次切图归因已交付，D07 仍在修复中；不缩小既定长稳目标。

## 问题与口径

既有一小时样例完成 877 次切图；UObject、Session、订阅与对象句柄有界，但相对第三轮的
进程 physical/virtual 内存增加约 306/73 MiB。代码包含释放路径不能证明没有 native 泄漏，
探针保留 JSON 也不能解释全部增长。原始证据见 [World 连续运行](P64.D_World_Soak.md)。

Win64 的 `FWindowsPlatformMemory::GetStats` 将 `WorkingSetSize` 写入 UsedPhysical，
将 `PagefileUsage`（commit charge）写入 UsedVirtual；后者不是 WASM 预留地址空间。
工作集、提交量、UE 容器容量和 JSON 估算是不同口径，不能相加或直接相减。

本批先执行相同 `VerifyWorld` 的 100 次切图，保留三轮预热、真实 GC、存档哈希链和原有动作验收。
不清缓存、不换轻量地图、不关闭安全机制。短运行只定位增长来源，不替代一小时或真实游玩验收。

## 冻结接口

- VM 新增 `AvidScriptVmDiagnostics.h`，导出值类型 `FAvidScriptVmMemorySnapshot` 和
  `CaptureAvidScriptVmMemorySnapshot()`。无 Runtime/Editor 依赖，无后端指针，无 Guest API/ABI 改动。
- 实例字段为 `uint64 BackendCreatedCount / BackendDestroyedCount / BackendLiveCount`；在
  `IAvidScriptVmBackend` 构造/析构处计数，拒绝隐式复制。并发读取必须得到一致的生命周期三元组。
- 缓存字段为 `int32 ArtifactCacheEntries / ArtifactCacheCapacity / AttestationEntries / AttestationCapacity`，
  `uint64 ArtifactCacheAllocatedBytes / AttestationAllocatedBytes`。在既有 compiler lock 内读取，
  累加容器容量及其自有数组/字符串容量，不复制制品、不触碰 LRU、不清缓存或登记新授权。
- 字节数仅覆盖 UE 自有容器的 `GetAllocatedSize`，不等于 Wasmtime 内部堆、代码页、线性内存、
  OS 虚拟地址保留或总进程内存。BackendLiveCount 仅是 C++ backend 对象，不声称证明所有 C/Rust 资源释放。
- 创建/销毁计数只发生于实例生命周期冷路径；快路径 Host crossing、Tick、执行指令不增加探针代码。

## World 报告

每轮 GC 后 `gc.attribution` 增加版本 1 的值快照：

- `backend_created / backend_destroyed / backend_live`。
- `artifact_cache_entries / artifact_cache_capacity / artifact_cache_allocated_bytes`。
- `attestation_entries / attestation_capacity / attestation_allocated_bytes`。
- `observer_retained_cycles / observer_retained_actions / observer_json_estimated_bytes`。

JSON 估算复用 UE 的 `FJsonValue::GetMemoryFootprint`，每个已完成周期只计算一次，再累计外层数组容量。
标明 `observer_estimate_kind=ue_json_memory_footprint`；该估算不含 shared pointer 控制块、分配器保留页
和最终报告序列化临时空间，不与进程内存作严格减法推导“剩余泄漏”。既有 physical/virtual、实际
backend mode、资源计数保持原义；旧报告缺少 attribution 时不伪装成零，新 CLI 默认要求完整字段。

### 首轮结论

本批交付的是可重复使用的冷路径诊断与一轮真实归因，不是内存优化结果，也不声明性能领先或无泄漏。
当前还不能用 JSON 估算解释全部增长，D07 保持 Fixing。

据此冻结以下引擎侧测量，其实施和结果见后文；不继续只增加切图时长：

- 当前日志确认 UE allocator 为 Mimalloc；记录其已分配/保留页口径，不通过强制 trim 改变测量对象。
- UE5.8 `UE::Trace::GetStatistics` 已提供 MemoryUsed、FixedBufferAllocated、CacheAllocated 等读数；
  后续将与同一 GC 时点关联，不关闭 Trace 或清缓存来制造较小结果。
- 若 UE 自有存活分配不足以解释提交量，再获取原生堆与 JIT 映射的分配栈；C++ backend 计数稳定
  不能替代 C/Rust 内部资源的释放证据。确认增长来源、完成必要优化后再跑一小时复验。

## 引擎侧归因合同

架构 v12 新增 Editor 私有 `AvidScriptUiSaveDemoWorldMemory.cpp` 承接采样，VM、Runtime、
Bindings 和 Guest ABI 不变。Editor 私有依赖 TraceLog，不引入 Mimalloc 私有头或修改引擎。
`gc.attribution.engine_memory` 自带 schema_version=1，包含 allocator_name（平台选定的基础 allocator，
Mimalloc 以名称输出，其他选择以 platform_allocator_编号输出）、sample_frame、
`sample_consistency=owner_snapshots_not_atomic`，以及以下固定对象：

- `trace.available`：编译支持时读取 UE Trace 统计；字段为 memory_used_bytes、block_pool_bytes、
  fixed_buffer_bytes、shared_buffer_bytes、important_cache_allocated_bytes、important_cache_used_bytes、
  thread_registry_bytes。不支持时各数值为 null，不以零表示未测量。
- `names`：entry_bytes、table_bytes、ansi_count、wide_count，来自 FName 公共统计接口。
- `llm.enabled` 与 `llm.sample_origin=live_totals_and_aggregated_tags`：通过 GetTotalTrackedMemory 读取
  Default/Platform 总量，通过 GetTagAmountForTracker 读取 Platform 的 FMalloc/PlatformOverhead，
  以及 Default 的 FMallocUnused、UObject、FName、Untagged、EngineMisc。
  JSON 字段分别为 default_total_bytes、platform_total_bytes、platform_fmalloc_bytes、
  platform_overhead_bytes、default_fmalloc_unused_bytes、default_uobject_bytes、default_fname_bytes、
  default_untagged_bytes、default_engine_misc_bytes；未启用时全部为 null。

`VerifyWorld -MeasureLlm` 仅在显式指定时附加 `-llm` 和探针要求标记；原生入口与外层报告均确认 LLM
实际启用，不接受静默降级。其他模式拒绝此开关。LLM 数值保留有符号读数，不把估算/异步聚合中的负值
夹为零；各 owner 快照不是原子整体，不强制相加等于 RSS/commit，也不主动刷新 LLM 或 trim 分配器。
总量可能含 UE 派生的未使用分配统计，不能直接称为纯活跃业务堆；TrackedTotal/UntaggedTotal 属于报表
聚合标签，不能用普通 tag getter 代替上述总量接口。基础 allocator 选择通过 FPlatformMemory 读取，
不访问已弃用的全局 GMalloc，也不使用 UE 私有全局变量。
按相同地图、脚本、100 次切图及三轮预热执行一次 LLM 诊断，保留上一轮原始基线，分别解释两种运行条件。
主线负责原生采样、启动开关和文档；独立写集负责 PowerShell 报告验证与合同，统一构建/执行。

### 归因结论与后续

本轮未观察到 Trace 缓存或 FName 容量累积；后半段 UE LLM 已跟踪的平台总量接近平稳，进程提交量
仍增长。下一步采集原生堆、JIT 分配与映射的分配栈，并区分活跃分配与分配器保留空间。
当前只能缩小排查范围，不能把差异全部归因于 Wasmtime，也不能宣称无泄漏或获得性能提升。
`P64-D07-WorldSoakMemoryAttribution` 保持 Fixing；明确来源并完成必要修复后才执行一小时复验。
后续已获取 GC 书签与四组分配栈查询，具体净增长和修复线索见[原生分配追踪](P64.D_Native_Allocation_Tracing.md)。
