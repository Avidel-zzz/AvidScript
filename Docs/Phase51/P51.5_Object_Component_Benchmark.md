# P51.5 UObject/Component 性能基准

## 结论

Phase 51 的对象/组件闭环已具备可重复的 Native、Binding 与真实 WAMR 对照基准。64 个 Actor Component 条件下，WAMR 每次 Tick 真正执行一次 `Construct -> Find -> Attach -> Release`，四个操作各发生一次 Host import；20 个正式样本共观察到 5888 次 import，与预期值完全一致。

本机 UE5.8 Editor Commandlet 结果中，完整 WAMR 四操作周期 P50 为 `0.009683 ms`，P95 为 `0.010223 ms`。Binding 热路径没有新增 class load，也没有 reflected-name lookup。

## 测试口径

| 项目 | 值 |
| --- | --- |
| 引擎 | 源码版 UE5.8 |
| 配置 | Win64 Development Editor、NullRHI、Multiprocess Automation |
| 预热 | 3 轮 |
| 正式样本 | 20 轮 |
| 每样本迭代 | 64 次 |
| Actor Component 数量 | 64 |
| Factory 类型 | `UStaticMeshComponent` |
| WAMR 每次迭代 crossing | Construct 1、Find 1、Attach 1、Release 1 |

Native 与 Binding 的计时只包含对应操作；夹具创建和清理放在计时区间外。WAMR 周期计时包含一次 guest Tick、四次动态 Host dispatch、组件创建/查询/挂接/释放及必要的 handle 管理。

## 实测结果

单位均为毫秒/操作；数值越低越好。

## 冷热路径与 crossing

| 指标 | 结果 |
| --- | ---: |
| package load class load | 7 |
| package load reflected-name lookup | 0 |
| warm loop class load | 0 |
| warm loop reflected-name lookup | 0 |
| WAMR 实际 import 总数 | 5888 |
| WAMR 预期 import 总数 | 5888 |
| 每次 WAMR 迭代 import 数 | 4 |

7 次 class load 对应 descriptor v7 中完整、按 ordinal 缓存的 UObject 类型图。进入热循环后，factory、object type 与 handle 均通过不可变 ordinal plan 或 registry slot 解析，没有按名称反射。

## 实现边界

- 基准通过真实 `FAvidScriptBindingPackage::Dispatch` 测量 Binding，不绕过 dynamic raw ABI。
- WAMR 模块只导入当前 package 已授权的四项能力，加载前仍受 import identity 和 package authorization 校验。
- 每次 WAMR 迭代结束后 registry 必须回到两个固定 fixture handle；任何组件 handle 泄漏都会直接使基准失败。
- Construct 与 Release 使用 Session ownership domain，Release 同时验证 authority、handle generation 与 UE Component 清理。
- Attach 使用固定 rules bit-field 和 `NAME_None` socket，不在成功热路径生成 object path。

## 解读限制

该结果是当前开发机上的 Editor Commandlet 微基准，用于发现 AvidScript 自身回归，不等同于 Shipping 包、移动设备或 Puerts/UnLua/AngelScript 的同机横向成绩。Phase 51 能确认热路径架构没有退化为字符串反射，并建立了后续跨版本、跨平台和竞品对照的稳定测量入口；在获得同硬件、同场景数据前，不声明对其他框架的绝对性能领先。
