# P43.2 Gameplay Binding 包发布与默认构建接入计划

## 目标

把 P43.1 已经能够稳定发现的 UE5.8 Gameplay Profile 从“可生成 descriptor”推进到“普通 C# 游戏脚本默认可消费的内容寻址绑定包”。本阶段完成后，自定义 C# 脚本不再自动落回八函数兼容包，而是直接获得 Actor 与 SceneComponent 当前支持的完整反射 API 面。

## 探针结论

在源码版 UE5.8 上，真实 Gameplay Profile 的 115 个接受函数已经能够一次性生成完整 C# facade：

- descriptor 生成成功；
- C# reference source 生成成功；
- package manifest 生成成功；
- 115 个 binding 全部保留；
- 当前没有 C# 类型名、固有 handle 成员或重载签名冲突。

因此本阶段不提前引入会改变公开 API 名称的自动别名规则。未来发现真实冲突时，生成器继续以稳定错误类别失败关闭；别名方案必须同时定义兼容性、可发现性和迁移规则后再进入公共契约。

## API 契约

`FAvidScriptEditorCSharpBindingEmitter` 新增两组高层入口：

- `EmitEngineGameplay()`：从内置 Gameplay Profile 生成 descriptor、C# facade 与 manifest；
- `PublishEngineGameplay()`：将上述三件套原子发布到内容寻址目录。

原有 `EmitDefault()` 与 `PublishDefault()` 保留，继续表示八函数兼容包。两种发布方式必须复用同一个内部发布事务，不能复制目录创建、字节校验和冲突处理代码。

## 默认构建策略

`FAvidScriptEditorCSharpBuildService` 仅在以下条件同时成立时自动发布 Gameplay 包：

- 构建的是自定义 C# source；
- profile 没有显式指定 `binding_package_path`。

显式包路径始终优先，保证固定 SDK、CI 回放和项目级裁剪不受默认策略变化影响。旧的内置 ActorLifecycle 示例仍可保持自身无生成包依赖的兼容流程。

## 性能与后续裁剪

P43.2 先建立完整可用闭环。由于 executable reference source 当前会把整个 facade 投影到 Guest IR，单个脚本可能携带全部 115 个 import。该行为正确但不是最终体积目标。

后续阶段应根据 Roslyn 实际符号使用集合，从同一 Profile 派生每脚本 binding slice，再让 descriptor、facade、Guest IR 和运行时包使用同一裁剪结果。裁剪必须是生成式分析，不能回到手写 API 白名单。
