# P43.3B 最小运行时 Binding Package 实施报告

> 状态：已完成
> 引擎：源码版 UE5.8，`C:\UnrealEngine`
> 平台：Win64 Editor；移动端适配仍按后续阶段推进

## 1. 阶段结论

P43.3B 已完成“完整编译授权 + 最小运行时能力”的双包闭环。

自定义 C# 脚本仍能看到 Gameplay Profile 生成的 115 个 UE API，Roslyn 可以正常分析不可达 helper 中的合法 API；正式产物只携带生命周期 export 实际可达的 API。以 `GeneratedBindingLifecycleScript` 为例：

| 层级 | 声明数量 | 实际使用数量 |
| --- | ---: | ---: |
| Authorization Binding Package | 115 | 2 |
| Runtime Binding Package | 2 | 2 |
| Guest IR / WASM 动态 UE import | 2 | 2 |
| Runtime cached invocation plan | 2 | 2 |

相较 P43.3A，Runtime 不再加载完整 115 项 package。该样例少创建 113 个无用 import/plan，运行时绑定表规模下降约 98.3%。热路径仍使用不可变 ordinal 和缓存调用计划，没有增加 Tick 期字符串查找、JSON 解析或 UE 反射遍历。

## 2. 用户侧写法

脚本作者不需要手工维护 API 表，也不需要为普通自动模式指定 package：

```csharp
using System.Runtime.InteropServices;

namespace AvidScript;

public static class PlayerScaleScript
{
    [UnmanagedCallersOnly(EntryPoint = "avid_on_begin_play")]
    public static void BeginPlay()
    {
        UE.Self.SetActorScale3D(new FVector(2.0f, 3.0f, 4.0f));
    }

    [UnmanagedCallersOnly(EntryPoint = "avid_on_tick")]
    public static void Tick(float deltaSeconds)
    {
        FVector scale = UE.Self.GetActorScale3D();
        UE.Self.SetActorScale3D(new FVector(scale.X + deltaSeconds, scale.Y, scale.Z));
    }

    [UnmanagedCallersOnly(EntryPoint = "avid_on_end_play")]
    public static void EndPlay() {}

    [UnmanagedCallersOnly(EntryPoint = "avid_on_timer")]
    public static void OnTimer(int callbackId, int timerHandle) {}

    [UnmanagedCallersOnly(EntryPoint = "avid_on_event")]
    public static void OnEvent(int eventId, float value) {}

    [UnmanagedCallersOnly(EntryPoint = "avid_on_gameplay_event")]
    public static void OnGameplayEvent(
        int eventType,
        int primaryId,
        int secondaryId,
        int objectSlot,
        int objectGeneration,
        float x,
        float y,
        float z) {}
}
```

Editor 构建后，BeginPlay、Tick、EndPlay、Timer 和事件入口仍进入 UE 生命周期；上例最终只注册 `GetActorScale3D` 与 `SetActorScale3D` 两个动态 UE import。

## 3. 架构分层

### BuildService：策略与生命周期

`FAvidScriptEditorCSharpBuildService` 负责：

1. 规范化 profile、路径和默认值；
2. 决定自动双遍、显式单遍或零运行时包策略；
3. 发布完整 Gameplay authorization package；
4. 管理唯一 bootstrap 目录、最终旧产物清理和所有返回路径的临时目录回收；
5. 组合 bootstrap、Slice Service 与 final build。

BuildService 不再拼接 PowerShell 参数，不直接执行进程，不解析 C# 文本，也不序列化 Binding Descriptor。

### BuildInvoker：单次构建执行

`FAvidScriptEditorCSharpBuildInvoker::BuildOnce` 只执行一次已经规范化的 config：

- 传递 authorization/runtime package 参数；
- 启动 PowerShell 构建；
- 读取结构化 report；
- 验证 manifest、WASM 和成功契约；
- 返回单次调用的 stdout、stderr、退出码和诊断。

Invoker 不选择 Gameplay Profile，也不决定是否切片。

### BindingSliceService：stable ID 切片

`FAvidScriptEditorCSharpBindingSliceService` 消费 bootstrap report 中的结构化 provenance：

- 校验 descriptor 路径、SHA-256、package 身份和声明数量；
- 校验每项 stable ID、ordinal、module、name 和 signature；
- 将 stable ID 映射回 `OwnerClass + UeFunction`；
- 复用现有 Reflection Descriptor Generator；
- 复用现有 `PublishDescriptor` 内容寻址发布事务；
- 重新解析结果并验证 stable ID 集合完全相同。

该服务不扫描 C#，不复制 descriptor renderer，也不复制 package publisher。

## 4. 三种构建路径

### 自动自定义脚本

1. 发布 115 项完整 authorization package；
2. 在 `Intermediate/AvidScript/CSharpBootstrap/<guid>` 执行 bootstrap；
3. 从 report 读取实际使用的 stable ID；
4. 发布最小 runtime package；
5. 正式构建继续使用完整 authorization facade，但将最小 package 写入最终 manifest；
6. 删除 bootstrap 目录。

实测自动模式执行两次构建，bootstrap 根目录结束后剩余 0 项。

### 显式 BindingPackagePath

显式项目 package 保持兼容行为：只执行一次构建，authorization 与 runtime 指向同一个 verified package，不做自动改写或切片。

### 零动态 UE import

bootstrap 使用集合为空时不生成“空 package”。正式构建传入 `OmitRuntimeBindingPackage`，并要求 Guest IR 中不存在任何 `avidscript.*` 动态 import。最终 manifest 不写 `binding_package`；只要出现一个动态 UE import，就以 `ASBI4303` 失败关闭。

## 5. 安全与一致性

- 实际动态 import 必须同时属于 authorization package 和 runtime package；
- runtime 与 authorization 必须具有相同 `package_name` 能力域；
- 同名 import 的 stable ID 与 signature 必须一致；
- 重复、非小写 64 位 SHA、未知 stable ID、ordinal 错配和 provenance 数量不一致全部拒绝；
- descriptor、reference source、package manifest 与最终 script manifest 继续执行 SHA-256 校验；
- 最终 manifest 的 descriptor hash 被篡改时，Runtime 仍返回稳定错误 `binding_package_hash_mismatch`；
- Runtime 只接收验证后的不可变 package，并从其中创建动态 import 与 cached invocation plan。

## 7. 当前可用边界

当前已经具备可执行闭环：C# 生命周期源码经过 Roslyn、Semantic、Guest IR 和 WASM Backend，生成 manifest；Runtime 加载最小 binding package，注册动态 UE import，并在 BeginPlay/Tick 等入口执行游戏逻辑。`FVector`、`AActor` proxy、反射生成 API、对象句柄、写权限和哈希拒绝均已进入该闭环。

它还没有达到 Puerts/UnLua 的完整产品成熟度。后续仍需补齐：

- P43.4 首遍语义分析缓存与双遍构建耗时优化；
- 增量编译、热重载和 package 生命周期/垃圾回收；
- 更完整的 UE 类型、容器、委托、异步和 latent 能力策略；
- Editor 诊断跳转、调试器、性能分析和项目模板；
- Cook/打包、移动端 AOT 约束与真机验证；
- API 兼容矩阵、版本迁移和稳定发布流程。

P43.4 的首要目标是复用 bootstrap 的完整语义结果，避免自动模式重复执行昂贵的前端与语义分析，同时保持本阶段已经建立的双包安全边界。
