# P43.5 内容寻址 Semantic Cache 架构

> 状态：设计与实施计划已锁定，Task 1 待实施

## 1. 目标

P43.4 已把一次自动自定义 C# 构建中的 Roslyn Frontend/Semantic 调用从两次降为一次，但下一次 Editor 构建仍会重新分析完全相同的源码。P43.5 的目标是建立项目级、跨 BuildService 调用的持久 Semantic Cache，让相同语义输入在热构建中不再启动 Frontend/Semantic。

目标调用次数：

| 构建路径 | BuildOnce | Frontend | Semantic | Guest IR | WASM Backend |
| --- | ---: | ---: | ---: | ---: | ---: |
| 自动 custom 冷构建 | 2 | 1 | 1 | 2 | 2 |
| 自动 custom 热构建 | 2 | 0 | 0 | 2 | 2 |
| 显式 package 冷构建 | 1 | 1 | 1 | 1 | 1 |
| 显式 package 热构建 | 1 | 0 | 0 | 1 | 1 |

Guest IR、WASM、runtime package 子集校验和正式发布继续执行。缓存只优化 Roslyn 语义前半段，不改变 Runtime 安全边界。

## 2. 方案比较

### 方案 A：不可变内容寻址条目

这是本阶段采用的方案。

缓存键由全部语义输入的规范 JSON 计算 SHA-256。每个键对应一个不可变目录，目录内保存 entry report、Frontend artifact 和 Semantic artifact。命中时使用 P43.4 的 prepared provenance 验证和双文件事务发布。

优点：

- 相同输入天然命中，不依赖可变索引；
- 并发构建可以竞争发布同一内容地址，并验证已有 winner；
- 输入变化产生新键，不会覆盖旧条目；
- 可以复用现有 fail-closed prepared 验证器；
- 后续可自然扩展到 Guest IR/WASM artifact promotion。

代价：需要完整定义工具链指纹，并在后续阶段增加容量治理。

### 方案 B：按脚本路径保存最后一次结果

每个 C# 源文件只有一个可变 cache slot。实现较少，但并发写、配置切换、package 切换和损坏恢复都需要额外锁与回滚，路径重命名还会丢失复用。该方案不适合作为成熟框架基础。

### 方案 C：常驻 Roslyn 编译服务

Editor 连接后台进程，复用 Roslyn Compilation 与程序集加载。理论热延迟最低，但需要进程拉起/退出、协议版本、崩溃恢复、日志、调试和平台适配。P43.5 先建立磁盘级可信缓存，后续 daemon 也必须服从同一 cache key 和 provenance 协议。

## 3. 缓存根与目录布局

默认缓存根：

```text
<Project>/Saved/AvidScript/CSharpSemanticCache/v1
```

条目布局：

```text
v1/
  ab/
    <64-char-cache-key>/
      entry.csharp.report.json
      semantic.frontend.json
      semantic.model.json
```

首两位分片避免单目录条目过多。缓存根、分片目录和条目路径都必须规范化并验证 containment。缓存不得写入插件源码目录、Content、Intermediate bootstrap 目录或最终可加载 artifact 目录。

条目发布使用同级 staging 目录和原子目录移动：

1. 在目标分片下创建唯一 staging；
2. 写入两个 artifact 和 entry report；
3. 重新读取并验证完整条目；
4. 原子移动到内容地址目录；
5. 如果并发 winner 已存在，验证 winner 与本次键及 artifact 完全一致后复用；
6. 任一失败清理本次 staging，不破坏已有条目。

## 4. Cache Key

cache key 是以下规范对象的 UTF-8 无 BOM JSON 的 SHA-256：

```json
{
  "schema_version": 1,
  "configuration": "Release",
  "target_framework": "net8.0",
  "dotnet_sdk_version": "8.0.416",
  "source": {
    "id": "project-relative/source/id",
    "sha256": "..."
  },
  "project_sha256": "...",
  "reference_sources": [
    {
      "ordinal": 0,
      "kind": "executable",
      "source_id": "reference:0:Generated.cs",
      "sha256": "..."
    }
  ],
  "authorization": {
    "package_name": "...",
    "package_hash": "...",
    "manifest_sha256": "...",
    "descriptor_sha256": "...",
    "reference_source_sha256": "..."
  },
  "toolchain_fingerprint": "..."
}
```

规范规则：

- JSON 字段顺序固定；数组保持编译器接收顺序；
- 路径转为项目相对正斜杠形式并使用稳定大小写规则；
- source、project 和 reference source 在查找前计算实际 SHA-256；
- 默认样例没有 authorization package 时写入显式空对象，不省略字段；
- 配置、目标框架和 SDK 版本必须进入键；
- key 只由输入决定，不包含时间、机器名、绝对缓存根或输出目录。

## 5. 工具链指纹

仅依赖 `frontend_version=1.0` 和 `semantic_version=1.5` 不足以失效缓存，因为实现可能在版本字段未变时修改。P43.5 使用源码闭包指纹：

- `global.json`；
- `Build/InvokeCSharpFrontend.ps1`；
- `Build/InvokeCSharpSemantic.ps1`；
- `Tools/AvidScript.CSharpFrontend` 下所有参与 SDK 默认编译的 `.cs` 与 `.csproj`，排除 `bin/obj`；
- `Tools/AvidScript.CSharpSemantic` 下所有参与 SDK 默认编译的 `.cs` 与 `.csproj`，排除 `bin/obj`。

每个文件以插件相对路径排序，指纹输入包含相对路径、字节长度和文件 SHA-256。SDK 版本单独进入 cache key，以覆盖 SDK Roslyn 二进制差异。

缓存 helper 可以读取工具链源码字节用于指纹，但不得解析用户 C# 文本、启动 dotnet、解释 Roslyn 语义或决定 binding package 策略。

## 6. Entry Report

缓存 entry report 保持为 P43.4 prepared helper 可验证的 schema 1 report 形状：

- `result=direct_abi_built`、`succeeded=true`；
- `output_root` 指向该内容地址条目目录；
- `source` 记录当前 source id 与 SHA-256；
- `binding_authorization` 记录完整 authorization identity 和 used imports；
- `artifacts.frontend_file/semantic_file` 只指向条目目录内文件；
- `frontend` 与 `semantic` 记录 schema/version/provenance/artifact SHA；
- 新增 `semantic_cache` 对象记录 cache schema、key 和 toolchain fingerprint。

缓存 report 不携带 manifest、WASM 或 runtime package。它不是可加载脚本 manifest，也不能被 Runtime 直接消费。

## 7. 构建数据流

### 冷构建

1. Build 脚本解析 source、project、reference sources 和 authorization package。
2. Cache helper 计算 toolchain fingerprint 与 cache key。
3. lookup 返回 miss。
4. 正常执行 Frontend 与 Semantic。
5. Guest IR、WASM 与所有正式 gate 成功后发布 immutable cache entry。
6. 自动模式 final 继续使用 P43.4 的本次 bootstrap prepared report。

缓存只在完整构建成功后发布，避免保存尚未通过 Guest IR/WASM 集成验证的工具链组合。

### 热构建

1. 计算相同 cache key。
2. lookup 读取 entry report 并执行 P43.4 全量 provenance 验证。
3. Frontend/Semantic 事务复制到当前 output root。
4. 跳过两个 Roslyn 进程，继续 Guest IR/WASM。
5. 自动模式 final 再复用本次 bootstrap report，不直接依赖持久缓存目录。

## 8. Report 与真实调用计数

正式 build report 新增稳定对象：

```json
"semantic_cache": {
  "enabled": true,
  "key": "...",
  "lookup": "miss",
  "entry_report_file": "",
  "entry_report_sha256": "",
  "published": true,
  "diagnostic_code": ""
},
"tool_invocations": {
  "frontend": 1,
  "semantic": 1,
  "guest_ir": 1,
  "wasm_backend": 1
}
```

`lookup` 只允许 `disabled`、`miss`、`hit`、`rejected`。`published` 与 lookup 分开，避免把“本次命中”和“本次冷构建后发布”混成一个状态。

BuildInvoker 不再根据参数推断 Frontend/Semantic 次数。进程启动成功后，它从结构化 report 读取 `tool_invocations`；启动前失败保持 0，失败 report 也必须记录已经实际发生的调用。BuildService 只聚合 bootstrap/final 计数，不解析 cache entry。

## 9. 错误与恢复

- cache miss：正常完整编译，不产生错误；
- entry schema/key/path/hash/provenance 无效：lookup=`rejected`，绝不复制该条目，记录稳定诊断后完整编译；
- corrupt entry 可移动时隔离到 cache root 下 `Corrupt`，再尝试发布新条目；
- corrupt entry 被占用时：当前正式构建仍可成功，但 report 记录 cache publish failure；
- staging 写入或并发发布失败：不影响已经成功的正式 manifest/WASM，记录 warning；
- 当前 source/authorization/toolchain 输入无法计算：禁用本次 cache 并执行完整编译，report 给出稳定原因；
- 任何 cache 失败不得降级为消费未验证 artifact。

诊断码固定为：

- `ASBI4501`：cache key 输入或 toolchain fingerprint 无效；
- `ASBI4502`：entry schema、key 或 provenance 无效；
- `ASBI4503`：cache root、entry 或 artifact 路径逃逸；
- `ASBI4504`：entry publication 或并发 winner 冲突；
- `ASBI4505`：损坏条目隔离或 staging 清理失败。

## 10. 测试策略

### Helper contract

- 相同输入两次计算完全相同 key；
- source、reference source、authorization、SDK、configuration 或任一 toolchain 文件变化都会改变 key；
- 合法 entry 命中并复制字节一致的 Frontend/Semantic；
- 路径逃逸、hash 篡改、key 篡改和 schema 篡改都返回 rejected；
- 并发发布同一 key 最终只存在一个完整条目；
- 第二文件/目录发布故障不留下半条目。

### Build integration

- 冷构建 `lookup=miss`、`tool_invocations=1/1`、`published=true`；
- 第二次相同构建 `lookup=hit`、`tool_invocations=0/0`；
- 修改 source 或 authorization 后重新 miss；
- 损坏缓存条目后 rejected 并完整重编，最终可加载产物仍成功；
- cache report/entry 不进入 runtime manifest。

### Editor 与 Runtime

- 自动冷构建总计 `Build=2 / Frontend=1 / Semantic=1`；
- 自动热构建总计 `Build=2 / Frontend=0 / Semantic=0`；
- 显式 package 热构建 `1/0/0`；
- authorization 115、runtime 2、WASM dynamic import 2、BeginPlay/Tick 行为不变；
- 完整 UE5.8 automation 保持零非成功结果。

## 11. 非目标

P43.5 不包含：

- Guest IR/WASM 持久缓存；
- 常驻 Roslyn daemon；
- 分布式或团队共享缓存；
- Android/iOS cache 兼容性；
- 自动 LRU/容量驱逐；
- Cook 或 packaged build cache。

容量治理、后台预热和跨机器共享需要先建立实际命中率、条目大小和损坏率指标，再作为独立阶段推进。
