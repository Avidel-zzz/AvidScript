# P43.5 内容寻址 Semantic Cache 完成报告

> 状态：已完成，并通过源码版 UE5.8 Win64 Editor 全量验证

## 1. 阶段目标

P43.4 已让自动 custom C# 构建的 final pass 复用同次 bootstrap 生成的 Frontend/Semantic 结果，但每次重新触发构建仍会启动一次 Roslyn Frontend 和 Semantic。P43.5 将这份经过 provenance 验证的语义结果提升为项目级、跨构建持久的内容寻址缓存。

目标不是缓存最终游戏模块，而是只复用与源码和编译工具链严格绑定的语义中间产物。Guest IR、WASM、authorization/runtime 子集校验、manifest 和正式发布每次仍重新执行，因此热缓存不会绕开最终可加载产物的安全门禁。

## 2. 已实现闭环

自动 custom C# 构建现在执行以下流程：

1. BuildService 发布完整的 engine gameplay authorization package。
2. bootstrap 根据源码、项目、reference source、authorization、配置和工具链计算 cache key。
3. cache miss 时执行 Frontend/Semantic；cache hit 时验证并复制不可变 entry 的两个中间产物。
4. bootstrap 无论 miss 或 hit，都重新执行 Guest IR、WASM 和完整发布门禁。
5. BuildService 根据实际可达 stable ID 发布最小 runtime binding package。
6. final pass 使用 P43.4 Prepared 协议复用 bootstrap 结果，不重复访问持久 cache。
7. final 重新执行 Guest IR、WASM、双包子集校验和正式 artifact 发布。
8. Editor 从 final 与 bootstrap 的结构化 report 汇总真实工具调用次数，并保留产生语义结果的 cache 审计信息。

这条链路已经在真实 UE 世界、WAMR 和生成反射 binding 上验证，不只是 PowerShell 文件复制测试。

## 3. Cache Key

Cache key 为 64 位小写 SHA-256，覆盖以下规范输入：

- C# source 的项目相对身份与实际文件哈希；
- `.csproj` 实际文件哈希；
- generated reference source 的身份与哈希；
- authorization package 的 package、manifest、descriptor、reference source 和 import 身份；
- `Release/Debug` configuration；
- `net8.0` 与固定 .NET SDK 版本；
- `global.json`、Frontend/Semantic Invoke 脚本及两个工具项目源码闭包的工具链指纹。

时间、机器名、绝对 cache root、output root 和 bootstrap 临时路径不会进入 key。相同语义输入跨 Editor 构建得到同一 key；源码、项目、authorization、reference source、配置或工具链任一变化都会产生新 key。

默认缓存根为：

```text
<Project>/Saved/AvidScript/CSharpSemanticCache/v1/<key-prefix>/<64-char-key>
```

## 4. 冷热构建计数

| 自动 custom 构建 | BuildOnce | Frontend | Semantic | Guest IR | WASM Backend |
| --- | ---: | ---: | ---: | ---: | ---: |
| 冷构建，cache miss | 2 | 1 | 1 | 2 | 2 |
| 热构建，cache hit | 2 | 0 | 0 | 2 | 2 |
| 显式 package 单遍，禁用 cache | 1 | 1 | 1 | 1 | 1 |

热路径完全跳过 Roslyn Frontend 与 Semantic，但仍生成新的 Guest IR、WASM、report 和 manifest。这里不使用本机墙钟时间作为性能承诺；稳定指标是结构化 report 中可复现的实际工具调用次数。

## 5. Report 与 Editor 事实来源

构建 report 新增：

- `tool_invocations.frontend`；
- `tool_invocations.semantic`；
- `tool_invocations.guest_ir`；
- `tool_invocations.wasm_backend`；
- `semantic_cache.schema_version/key/toolchain_fingerprint`；
- `semantic_cache.lookup`，仅允许 `disabled/miss/hit/rejected`；
- entry report 路径、SHA-256、publication 状态和稳定诊断。

`FAvidScriptFrontendReportReader` 对旧报告保持可读，但新 BuildInvoker 要求两组现代元数据完整、类型精确且非负。字段缺失、负数、非整数或未知 lookup 都返回 `report_contract_invalid`。PowerShell 启动前失败保持所有调用数为 0；已启动后的成功与结构化失败都透传真实 report 数值。

Invoker 已删除根据 `PreparedBuildReportPath` 猜测 Frontend/Semantic 次数的旧逻辑。BuildService 只负责 bootstrap/final 求和；final 的 cache lookup 为 disabled 时，最终结果保留 bootstrap 的 miss/hit/rejected 审计事实。

## 6. 不可变 Entry 与故障恢复

每个 entry 只包含：

- `semantic.frontend.json`；
- `semantic.model.json`；
- `entry.csharp.report.json`。

entry 不得包含或引用 Guest IR、WASM、manifest 等可加载产物。Runtime manifest 也不引用 cache 路径。

发布流程具备以下边界：

- 每个 key 使用跨进程独占文件锁；
- lock path、cache root、entry 和 artifact 路径逐段拒绝 reparse point；
- staging 使用短事务名，避免 Windows 深路径预算问题；
- staged report 写盘后重新读取真实 bytes；
- 重读对象必须与完整预期 report 的 canonical JSON 哈希完全相等；
- 路径、artifact SHA-256、source、authorization、module 和工具链 identity 在 atomic move 前全部验证；
- 并发 winner 必须重新经过完整 import 验证后才能复用；
- 损坏 entry 移入 `Corrupt` 隔离区，随后执行完整重编；
- 隔离或清理失败返回稳定诊断，不消费未经验证的 artifact。

稳定诊断范围为 `ASBI4501` 至 `ASBI4505`，分别覆盖 key/指纹、entry/provenance、路径、发布/winner 和隔离/清理失败。

## 7. UE 游戏逻辑实测

`AvidScript.Editor.BindingRuntime.GeneratedCSharpLifecycle` 连续执行同一 C# 游戏脚本的冷构建与热构建，并验证：

- 冷构建为 `2/1/1/2/2`，cache lookup 为 `miss` 且发布 entry；
- 热构建为 `2/0/0/2/2`，cache lookup 为 `hit` 且不重复发布；
- authorization package 保持 115 个生成绑定；
- runtime package 只保留 2 个实际可达绑定；
- 最终 WASM 只保留 2 个 `avid_ue_*` 动态反射导入；
- C# `BeginPlay` 通过生成的 `UE.Self` API 修改 Actor 的 `FVector` scale；
- C# `Tick` 通过 Runtime Session 和 live scheduler 继续读取并更新该 `FVector`；
- 热缓存生成的 WASM 仍可由 WAMR 加载并参与完整 UE 生命周期。

因此当前缓存不是孤立的编译器优化，而是已经接入可运行 C# 游戏脚本闭环。

## 9. 架构职责

- SemanticCache helper：只拥有 key、工具链指纹、entry 查找/发布、锁和损坏隔离。
- PreparedSemantic helper：只拥有 provenance 验证与 Frontend/Semantic 双文件事务复制。
- BuildCSharpActorLifecycle：拥有构建编排、真实调用计数、Guest IR/WASM 和正式发布。
- BuildInvoker：只启动一次 PowerShell，并读取严格结构化 report，不推断工具次数。
- BuildService：拥有 package 策略、bootstrap/final 生命周期、计数求和和 cache 审计聚合。
- Runtime：只消费最终 manifest、WASM 和不可变 runtime binding package，不依赖 Semantic Cache。

## 10. 当前边界与下一步

P43.5 没有实现 cache 驱逐、容量预算、Guest IR/WASM promotion、Cook/packaged build 或移动端验证，也没有常驻后台编译进程。这些边界不会阻止当前 Win64 Editor 使用 C# 编写并运行 `BeginPlay/Tick` 游戏逻辑。

下一阶段应优先改善可用性闭环：提供面向项目的 C# 脚本资产/配置入口、稳定的编译与 reload 反馈、热重载失败回滚，以及更完整的生成 UE API 类型体验；随后再进入 Cook 和移动端平台适配。
