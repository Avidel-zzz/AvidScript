# P43.4 Prepared Semantic 复用架构

> 状态：已完成，实测结果见 `P43.4_Prepared_Semantic_Reuse.md`

## 1. 目标

P43.3B 自动自定义脚本需要执行 bootstrap 与 final 两次完整构建。两遍使用相同源码和完整 authorization facade，只有 final 的 runtime binding package 不同，因此重复执行 Roslyn Frontend 与 Semantic 没有语义收益。

P43.4 的目标是：

- 保留 P43.3B 的双包安全边界；
- 保留 bootstrap 与 final 两次独立发布决策；
- final 复用 bootstrap 已验证的 Frontend/Semantic artifact；
- final 仍重新执行 Guest IR、WASM Backend、runtime package 子集校验和正式发布；
- 显式 package 单遍与默认样例构建不改变；
- 不引入跨进程常驻服务或持久缓存失效协议。

## 2. 方案比较

### 方案 A：复用 Frontend 与 Semantic

这是本阶段采用的方案。

bootstrap report 作为 prepared semantic bundle 的索引。final 构建读取该 report，验证源码、authorization package、artifact 路径和 SHA-256，再将 Frontend/Semantic artifact 原子复制到 final output，跳过两次 Roslyn 工具调用。Guest IR 与 WASM Backend 继续基于 final 路径下的 Semantic artifact执行。

优点：

- 直接消除重复 Roslyn 分析；
- final 仍重新生成 Guest IR/WASM，不会复用尚未经过 runtime slice 约束的可加载产物；
- 不改变 Semantic schema、Guest IR schema 或 Runtime manifest schema；
- prepared bundle 只在一次 BuildService 调用的唯一 Intermediate 目录内生存，失效边界清晰。

代价：final 仍执行 Guest/Backend，收益不是理论最大值。

### 方案 B：提升完整 bootstrap 产物

该方案复用 Frontend、Semantic、Guest IR 和 WASM，仅改写 final report/manifest。构建速度最快，但必须证明旧 WASM、inspection、Guest IR、runtime package 和最终发布事务完全同源，还需要新增完整 prepared artifact manifest 与原子提升协议。当前风险和改动面过大，留给后续阶段。

### 方案 C：持久内容寻址缓存

该方案按源码、编译器版本、authorization reference source 和配置哈希跨构建复用 Semantic。长期收益高，但需要缓存驱逐、工具链指纹、并发发布、损坏恢复和版本迁移。P43.4 先建立单次调用内的可信复用协议，再将其扩展为持久缓存。

## 3. 数据流

```text
完整 authorization package
          |
          v
bootstrap BuildOnce
  Frontend -> Semantic -> Guest IR -> WASM -> bootstrap report
          |                                 |
          |                                 +-- stable ID used set
          +-- prepared Frontend/Semantic provenance
                                              |
                                              v
                                  Runtime BindingSliceService
                                              |
                                              v
final BuildOnce(-PreparedBuildReportPath)
  验证并复制 Frontend/Semantic
  -> Guest IR
  -> WASM Backend
  -> authorization/runtime 双子集校验
  -> final report/manifest/WASM
```

bootstrap 目录在 final 返回后统一删除。final report 的 `artifacts.*` 和 manifest 只能引用 final output 下的复制产物；`build_reuse.prepared_report_file` 作为审计来源可以记录本次调用内的临时 bootstrap report 路径及其 SHA-256，但运行时不依赖该路径。

## 4. 组件边界

### PreparedSemanticBundle PowerShell helper

新增 `Build/AvidScriptCSharpPreparedSemantic.ps1`，只负责读取和验证 prepared report，输出已验证的 Frontend/Semantic 模型与源路径，并将两个 artifact 原子复制到 final 路径。

建议接口：

```powershell
Import-AvidScriptCSharpPreparedSemantic `
    -PreparedReportPath <bootstrap report> `
    -ProjectRoot <UE project root> `
    -ExpectedSourcePath <current C# source> `
    -ExpectedAuthorizationPackage <resolved package info> `
    -FrontendDestinationPath <final frontend artifact> `
    -SemanticDestinationPath <final semantic artifact>
```

返回对象至少包含：

- `FrontendModel`
- `SemanticModel`
- `PreparedReportPath`
- `PreparedReportSha256`

helper 不启动 dotnet，不解析用户 C# 文本，不决定 package 策略。

### BuildCSharpActorLifecycle

新增参数：

```powershell
[string]$PreparedBuildReportPath = ""
```

未传参数时保持现有完整构建。传入时：

1. 先按现有规则解析 authorization/runtime package；
2. 调用 PreparedSemantic helper；
3. 跳过 Frontend 与 Semantic 进程；
4. 从复制后的 final artifact 继续 Guest IR/WASM；
5. final report 新增 `build_reuse` provenance。

`build_reuse` 建议结构：

```json
{
  "prepared_report_file": "Intermediate/.../bootstrap.csharp.report.json",
  "prepared_report_sha256": "...",
  "frontend_reused": true,
  "semantic_reused": true
}
```

普通构建保留同一对象，但两个布尔值为 false，路径和哈希为空，便于 Editor 和测试稳定读取。

### BuildInvoker 与 BuildService

`FAvidScriptEditorCSharpBuildConfig` 增加 `PreparedBuildReportPath`。Invoker 只透传 `-PreparedBuildReportPath`，不解释复用策略。

BuildService 自动模式把 `BootstrapConfig.ReportPath` 传给 final config；显式 package、默认样例和单遍失败路径保持空值。BuildService 不读取 Frontend/Semantic JSON。

## 5. 可信复用条件

任一条件不满足都失败关闭，不静默退回完整 final 构建：

1. prepared report 必须存在、是 schema v1、`result=direct_abi_built` 且 `succeeded=true`；
2. prepared report 的源码路径与当前 `SourcePath` 规范化后相同；
3. 当前源码 SHA-256 必须等于 report source SHA-256；
4. `binding_authorization` 的 package name/hash、manifest/descriptor/reference-source SHA 必须与当前已解析 authorization package 完全一致；
5. Frontend/Semantic artifact 必须位于 prepared report 的 `output_root` 内，禁止路径逃逸；
6. 两个 artifact 的实际 SHA-256 必须等于 report 中记录值；
7. Frontend 必须 succeeded、schema/version 正确，源码 provenance 与当前源码一致；
8. Semantic 必须 succeeded、schema/version 正确，source/frontend provenance 与 Frontend 一致；
9. final destination 必须通过临时文件加同目录原子替换发布；
10. prepared report 不能与 final report 路径相同。

复用失败使用独立结果 `prepared_semantic_invalid`，诊断码从 `ASBI4401` 开始，便于与普通 Frontend/Semantic 编译失败区分。

## 6. 测试策略

### PowerShell contract

- 合法 prepared report：final 成功，`build_reuse.frontend_reused/semantic_reused=true`；
- 源码被修改：`ASBI4401` 失败；
- authorization package 改变：`ASBI4402` 失败；
- artifact hash 被篡改：`ASBI4403` 失败；
- artifact 路径逃出 prepared output root：`ASBI4404` 失败；
- final report/manifest/WASM 不得在失败时残留。

### Editor automation

- 自动 CustomProfile 的 `BuildInvocationCount` 仍为 2；
- 新增 `FrontendInvocationCount=1` 与 `SemanticInvocationCount=1`，证明 final 没有重复 Roslyn；
- 显式 package 仍为一次 Frontend/Semantic；
- authorization 115、runtime 2、WASM dynamic import 2 保持不变；
- bootstrap 目录结束后仍为 0 项。

### 完整回归

顺序运行 Frontend、GuestIr、Semantic、CSharpGuest、WasmBackend、BuildIntegration、BuildPublicationContracts、PowerShell parser、架构门禁、focused UE automation 和完整 `Automation RunTests AvidScript`。

## 7. 非目标与后续

P43.4 不做：

- 跨 Editor 会话的持久缓存；
- 复用 Guest IR 或 WASM；
- 修改 C# 语言表面或 UE API Profile；
- Cook/移动端缓存；
- 后台编译服务。

后续阶段可在 prepared semantic provenance 稳定后，将相同验证模型扩展为内容寻址持久缓存，再评估完整 artifact promotion。
