# P43.3B 最小运行时 Binding Package 架构

## 阶段目标

P43.3A 已把 WASM 动态 UE import 从 Gameplay Profile 的 115 个裁剪到脚本实际使用的 2 个，但运行时 manifest 仍加载完整 package，并创建 115 个 cached invocation plan。P43.3B 要让运行时 package、WASM import 和 invocation plan 使用同一份最小 binding slice，同时保留完整 Gameplay Profile 作为 C# 编译授权面。

## 方案比较

### 方案 A：编译授权 package 与运行时 package 分离

这是本阶段采用的方案。

- 完整 Gameplay package 提供完整 C# facade，负责 Roslyn 符号绑定和允许调用的 API 上界；
- 最小 runtime package 只包含生命周期 export 可达的 stable ID，负责最终 manifest 和运行时 invocation plan；
- 最终构建同时验证实际动态 import 是授权 package 与 runtime package 的子集；
- 显式指定的项目 package 继续同时承担授权与运行时职责，不进入自动切片。

该方案允许源码保留当前生命周期不可达的 helper。helper 可以引用完整 Profile 中的合法 API，但这些 API 不会进入 Guest IR、WASM 或运行时 package。

### 方案 B：第二遍只提供 slice facade

该方案实现较少，但会让不可达 helper 中的合法 API 因 facade 成员缺失而产生 Roslyn 编译错误。源码活性与 API 可见性被错误耦合，不适合作为成熟脚本方案。

### 方案 C：首遍构建后改写 manifest

该方案跳过正式重建，容易让 report、reference source hash、descriptor 和运行时 package 失去同源关系，也会把发布事务拆成难以验证的后处理步骤，因此不采用。

## 组件边界

### Frontend Report Binding Provenance

`FAvidScriptFrontendReportReader` 结构化读取 `binding_package.used_imports`，每项保留 stable ID、ordinal、module、name 和 signature，并保留对象存在标记、声明的 profile/used count。旧 report 没有该对象时继续按空 provenance 读取。

Reader 只负责数据契约，不负责生成 package。

### C# Binding Slice Service

新增独立 `FAvidScriptEditorCSharpBindingSliceService`：

1. 读取已验证的完整 descriptor；
2. 对 bootstrap report 中的 stable ID 去重并排序；
3. 要求每个 stable ID 都能映射到完整 descriptor 的 `owner_class + ue_function`；
4. 调用现有 descriptor generator 重新反射并验证当前 UE5.8 函数；
5. 调用现有 emitter 的通用发布入口，复用内容寻址与并发复用事务；
6. 验证新 descriptor 的 stable ID 集合与请求集合完全一致。

Slice Service 不解析 C#、Semantic 或 WASM，不复制 descriptor 序列化和 package 发布逻辑。

### C# Build Invoker

从现有 BuildService 中抽出单次 PowerShell 构建执行与结果验证，形成私有 `FAvidScriptEditorCSharpBuildInvoker`。它只接收完全规范化的 build config，并负责：

- 创建输出目录；
- 启动 PowerShell；
- 读取结构化 report；
- 验证 success contract、manifest 与 WASM 存在；
- 把失败映射到统一 `FAvidScriptEditorCSharpBuildResult`。

它不决定使用完整 package、slice package 或自动两阶段流程。

### C# Build Service

`FAvidScriptEditorCSharpBuildService` 只保留策略编排：

- 默认 ActorLifecycle：维持单次构建，不需要动态 package；
- 自定义源码且显式 `BindingPackagePath`：维持单次构建，不自动改写项目 package；
- 自定义源码且未显式指定 package：进入自动两阶段切片。

## 两阶段数据流

1. Editor 发布或复用完整 `avidscript.engine.gameplay` package；
2. 使用完整 package 在独立 bootstrap output 下执行首遍构建；
3. bootstrap report 产出 `used_imports[].stable_id`；
4. Slice Service 从完整 descriptor 生成并发布最小 runtime package；
5. 最终构建继续使用完整 facade 做 Semantic 分析，同时使用最小 runtime package 做动态 import 授权；
6. 最终 script manifest 只引用最小 runtime package；
7. Runtime 只加载 slice descriptor，并只创建实际需要的 invocation plan；
8. bootstrap 目录在成功和失败路径都被删除。

最终 report 同时记录：

- `binding_authorization`：完整 Profile package 与 115 个授权 import；
- `binding_package`：最小 runtime package 与实际 import；
- `used_imports`：最终命中的 runtime stable identity。

## 零动态 Binding

若 bootstrap report 的动态 stable ID 集合为空，则不生成空 descriptor。现有 descriptor/runtime package 契约要求至少一个 binding，强行放宽会扩大不必要的 schema 变化。

最终构建改为：

- 继续使用完整 authorization facade 做 Semantic 分析；
- 明确设置“无 runtime binding package”；
- 要求 Guest IR 中不存在任何 `avidscript.*` import；
- 最终 manifest 不写 `binding_package`；
- Runtime 沿用现有无动态 package 路径。

## 失败关闭与原子性

- bootstrap stable ID 缺失、重复、格式非法或不属于完整 descriptor时，切片失败；
- runtime package 缺少任一实际动态 import 时，以独立诊断失败，不发布最终 manifest；
- 自动两阶段开始前删除旧的最终 manifest、report 和 WASM，避免 bootstrap 或切片失败后继续绑定旧产物；
- bootstrap 产物不写入最终 output root；
- 最终 manifest 只由第二遍正式构建发布；
- content-addressed package 冲突继续由现有 publisher 拒绝。

## 性能策略

P43.3B 先建立正确、可验证的双 package 闭环。自动模式会执行两次前端构建，但完整 Gameplay package 和最小 runtime package都可按内容哈希复用。

P43.4 将缓存首遍完整 Profile 的 Semantic/Guest 分析结果，并以 source hash、engine version、authorization package hash 和工具链版本组成 cache key，消除未变更脚本的重复分析。

## 验收标准

- GeneratedBindingLifecycle 最终 authorization import 为 115、runtime import 为 2；
- Runtime 加载的 package 与 invocation plan 数量为 2；
- WASM 动态 UE import 数量为 2；
- 不可达 helper 可以引用 Profile 中未进入 runtime slice 的合法 API；
- 未知 stable ID、runtime slice 缺失 import 和篡改 package 全部失败关闭；
- 显式 `BindingPackagePath` 保持单遍构建和原 package 身份；
- 源码 UE5.8 增量编译与完整 AvidScript 自动化通过。
