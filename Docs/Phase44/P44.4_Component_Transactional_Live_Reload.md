# P44.4 Component 事务式 Live Reload

> 状态：已完成。验证平台为源码版 UE5.8、Win64 Editor Development。

## 1. 本阶段交付

P44.4 把 P44.3 的“构建后首次绑定并运行”推进为运行中脚本切换：

1. `UAvidScriptComponent` 可以重新读取当前 manifest，并调用既有 `FAvidScriptRuntimeSession::ReloadModule`。
2. 候选 WASM 只有在 manifest、hash、ABI、exports/imports、实例化和 `BeginPlay` 全部成功后才成为 active runtime。
3. 候选失败时不调用 `ReleaseRuntime`，不关闭 Component Tick，不解绑 Actor gameplay delegates。
4. Editor 绑定服务把 manifest path 与 runtime 切换视为同一个提交：成功时提交新 path，失败时恢复旧 path。
5. C++ 调用方可取得完整 reload 结果；Blueprint 可使用简化的 bool 入口。

这使“编辑 C# -> Build And Bind -> 运行中替换”第一次形成了可直接用于游戏逻辑迭代的闭环。

## 2. Component API

### 2.1 C++ rich result

```cpp
FAvidScriptWasmReloadResult ReloadResult;
if (!AvidScriptComponent->ReloadConfiguredScript(ReloadResult))
{
    UE_LOG(
        LogTemp,
        Warning,
        TEXT("Reload rejected: %s | %s"),
        *ReloadResult.ErrorCategory,
        *ReloadResult.ErrorMessage);
}
```

`FAvidScriptWasmReloadResult` 的关键字段：

| 字段 | 含义 |
| --- | --- |
| `bSucceeded` | 候选 runtime 已成功接管 |
| `bReloadApplied` | 本次调用确实执行了 reload，而不是 initial load |
| `bRollbackPreservedLiveRuntime` | 失败后旧 runtime 仍保持 live |
| `PreviousModuleId` | reload 前 active module |
| `CandidateModuleId` | 候选 module |
| `ActiveModuleId` | 调用结束后的 active module |
| `ErrorCategory/ErrorMessage/NextAction` | 可稳定消费的诊断 |
| `RuntimeResult` | WAMR 生命周期、计数与性能结果 |

### 2.2 Blueprint 简化入口

`ReloadScript()` 已标记为 `BlueprintCallable`。它读取 Component 当前配置的 manifest path，成功返回 `true`，拒绝返回 `false`。

适合的 Blueprint 使用方式是：Component 预先绑定一个稳定 manifest path，外部构建流程原子发布新 manifest/WASM 后调用 `ReloadScript`。需要完整诊断时应使用 C++ rich result 或 Editor Build And Bind 结果。

## 3. Editor Build And Bind 事务

对已有 `UAvidScriptComponent` 调用 `ApplyManifestToActor` 时，服务先判断 runtime 是否正在运行：

| Component 状态 | 行为 |
| --- | --- |
| 不存在 | 先写 manifest path，再注册 Component，由 `BeginPlay` initial load |
| 已存在但不 live | 只更新 manifest path，等待下次 `BeginPlay` |
| 已存在且 live，候选成功 | reload runtime，提交新 path，标记 package dirty |
| 已存在且 live，候选失败 | 恢复旧 path，保留旧 runtime，不新增 package dirty |

绑定结果新增：

- `bReloadAttempted`：是否进入 live reload；
- `bReloadApplied`：候选是否已经接管；
- `RuntimeResult`：底层 runtime reload 证据；
- `ReloadRejected` 状态与稳定错误类别 `reload_rejected`。

因此 Editor 命令不会出现“属性已经指向坏 manifest，但内存里还运行旧模块”的半提交状态。

## 4. 运行时状态

`FAvidScriptComponentRuntimeStats` 新增：

- `SuccessfulReloadCount`；
- `RejectedReloadCount`。

`RuntimeStats.ScriptManifestPath` 表示 active runtime 已提交的 manifest。`GetScriptManifestPath()` 表示 Component 当前配置值；直接使用 C++/Blueprint reload API 时，失败候选仍可保留为配置值以便修复后重试。Editor 绑定事务会在失败时把配置值恢复到已提交 path。

成功切换后，新 runtime 从新的生命周期状态开始：

- 重新执行候选 `BeginPlay`；
- Tick、Timer 和 Event 的 runtime 计数从新实例重新开始；
- Component owner handle、Actor delegates 和宿主对象注册保持不变。

## 5. 验证证据

| 验证 | 结果 |
| --- | --- |
| UE5.8 增量编译 Runtime + Editor | 成功 |
| `AvidScript.Component` | 7/7 Success |
| `AvidScript.Architecture.Session` | 2/2 Success |
| `AvidScript.Editor.ComponentBinding` | 3/3 Success |
| `Build/CheckAvidScriptArchitecture.ps1` | 通过 |

新增真实用例覆盖：

1. Component 从 v1 成功切换到兼容 v2，`SuccessfulReloadCount=1`，v2 继续 Tick。
2. 候选 `BeginPlay` trap 被拒绝，`RejectedReloadCount=1`，旧 v2 module 和 Tick 保持有效。
3. live Editor binding 成功提交新 path 和 active module。
4. 坏 JSON manifest 返回 `reload_rejected`，恢复旧 path，旧 module 继续 Tick，原本干净的 Actor package 仍保持干净。

测试 fixture 直接生成最小 WASM、SHA-256 与 manifest，不依赖外部 D/C# 编译产物。

## 6. 当前边界

本阶段的“事务式”保证覆盖 runtime ownership、active module 和 Editor manifest binding，不伪装下列能力：

1. 不迁移 guest 静态字段、managed heap、coroutine continuation、Timer 或 Event 队列。
2. 候选 `BeginPlay` 已经执行的 UE host 写入没有对象快照回滚；若 guest 在写入 Actor 后 trap，runtime 会回滚，但此前的 Actor 副作用不会自动撤销。
3. 当前通过 Editor Build And Bind 或显式 `ReloadScript` 触发，不包含文件监听、防抖和自动重编译。
4. 当前验证基线为 PC Win64；移动端 runtime、Cook 和发布工作流仍在后续阶段。
