# Phase 56 融合调用帧实现与性能报告

## 结论

Phase 56 已完成 callback-epoch fused host cell、prepared VM export、lifecycle hot
result 与候选绑定的正式 benchmark 闭环。UE 语义、reload、事务和失败诊断合同保持，
完整 Automation 为 `317/317` 通过。

正式 evaluator 共报告 18 项门禁，12 项通过、6 项未通过。当前版本已经在两个
游戏帧 workload 上明显领先同机 Puerts 最快 lane，但还不能宣称在所有执行内核和
所有 UE 交互路径上全面领先：

- Small gameplay 的 Generated S1 为 Puerts static 的 `0.469x`，约快 `53.1%`。
- Dense gameplay 的 Data-Oriented lane 为 Puerts static 的 `0.513x`，约快 `48.7%`。
- lifecycle callback 为 `67.88 ns`，是 Puerts 对应路径的 `0.391x`。
- Wasmtime/V8 controlled-runtime P50 几何均值为 `0.977x`，P95 为 `0.996x`；
  平均值略领先，但尾延迟没有达到 `0.95x` 领导性目标。
- semantic reflection 路径仍为 Puerts reflection 的 `5.819x`，是下一阶段最重要
  的 UE 交互性能问题。

## 实现内容

### Callback-epoch fused host cell

Runtime 在每次宿主 callback 建立共享 receiver frame。Generated S1 scalar、
getter 和 setter 的 call site 在同一 callback epoch 内复用 receiver、class、
reload epoch 和 effect policy 证明；nested callback、reload、revoke 或 registry
revision 变化会强制重新验证。

DirectRead 与 DirectWrite 进入冻结 target 的直接路径，Journaled write 继续经过
既有事务 prepare 和回滚合同。正式样本的 fused fast-hit ratio 为
`0.999996`，每 callback revalidate 精确为 `1.0`，未观察到 journal slow-path
误入直接 workload。

### Prepared VM export

VM 公共接口增加 backend-neutral prepared export call。Wasmtime 使用稳定 entry
和 tombstone 管理已验证导出，prepared invoke 跳过重复 handle/slot 查找，同时保留
trap、host failure、unload 和 reentrant unload 语义。WAMR/mobile 当前显式回退到
普通 `Call`，不会静默改变结果。

物理分段测得 typed empty 的净跨界成本为 `4.08 ns`，但 prepared export 相对
generic export 的比值仅为 `0.995`，没有达到 `0.95` 目标。这说明 export lookup
并不是当前 callback 总成本的主要矛盾，后续应把优化重点移到 invocation frame、
结果传播和 Wasmtime store/call plumbing。

### Lifecycle hot result

`TickHot`、`DispatchEventHot` 和 `DispatchGameplayEventHot` 在成功路径不再复制
完整 observable snapshot、字符串与诊断数组；失败时仍物化完整错误信息。
Component、Scheduler 与 EventRouter 已接入该入口。callback P50 从 Phase 55 的
`212.23 ns` 降到 `67.88 ns`，低于本阶段 `150 ns` 目标。

### Benchmark 与真实性约束

physical ladder、micro、gameplay 和 12-kernel controlled-runtime 均绑定同一
候选 commit/tree。正式协议为 5 个独立进程，每进程 5 次 warmup、30 次 timed
sample；evaluator 同时检查候选身份、profile hash、路径计数、fallback、P50/P95、
跨进程 MAD 和物理分段重建误差。

被测运行时候选为 `d82ed7aa997758fa7f6983c6a6996999a467d283`。随后提交
`5e1455799a90845f278767538ef5fc1071ba7365` 只修正 evaluator 的 fused 样本筛选，
没有修改运行时代码，也没有重写原始证据。

## 转交 Phase 57

Phase 56 的机制闭环已经完成，以下性能缺口转交 Phase 57：

1. 对 semantic reflection 建立缓存化 invocation plan，减少重复 `ProcessEvent`
   参数布局、对象解析和结果封送。
2. 将 Generated S1 scalar/property 再降低约 `8%`，重点分析 host frame、
   result copy 与 Wasmtime call plumbing，不增加 fixture-specific API。
3. 针对 controlled-runtime 的 hashing、branch、SIMD 和 P95 抖动做 backend
   配置与代码生成归因，以真实游戏 workload 复验。
4. 重新评估 prepared export 的存在价值；若收益长期低于噪声，应简化其热路径，
   不为保留抽象而增加间接层。

这些事项是 Important 性能债务，不阻塞 Phase 56 的功能与语义交付，但会阻止
“全面性能领先”的发布声明。
