# P54.4 Crossing Fast Path 实施计划

## 1. 目标

P54.3 已证明 Wasmtime Cranelift JIT 与 Puerts V8 tiered JIT 在同一份纯
WASM 整数 kernel 上处于同一性能级别。P54.4 不再更换 PC 执行后端，而是
降低 C# Guest 调用 UE API 时的固定 crossing 成本。

本阶段的第一批优化只选择正式数据中成本高、语义边界明确、可由通用规则
覆盖的 ABI 类：

`instance + 2 x value scalar:i32 -> scalar:i32`

该 shape 同时覆盖性能夹具中的 `ReflectAddInt32` 与 `ReflectBatchAdd`。
实现不得按类名、函数名或 benchmark workload 分支。

## 2. 架构边界

新增独立的 `AvidScriptBindingFastPath` 私有组件，职责如下：

1. 在 binding package 加载时检查 descriptor 已解析出的 immutable plan；
2. 证明参数帧只包含可零初始化、无需析构的 `int32` 参数和返回值；
3. 将满足条件的 plan 绑定到同一个编译期 typed thunk；
4. 缓存参数和返回值在 UE 参数帧中的 byte offset；
5. warm call 使用 runtime instance 已有 scratch，不缓存可变 frame；
6. 保留 `ProcessEvent`，不绕过 Blueprint override、RPC/callspace 和 UE 调试语义；
7. 任一证明条件不满足时继续使用现有 reflection fallback。

ordinal、`UClass*`、`UFunction*`、`FProperty*` 和 ABI signature 已由现有
package plan 缓存。本阶段不增加第二套 name/ordinal map。

## 3. 正确性约束

typed thunk 之前仍必须经过现有公共 guard：

- ordinal 和 raw argument 数量；
- Guest Memory 可用性与边界；
- object slot、generation 和 `IsA`；
- write policy；
- candidate reload host-effect journal；
- scratch 大小和对齐。

首批不支持以下 shape：

- static UFUNCTION；
- ref/out；
- bool、enum、非 `int32` scalar；
- FName、object handle、struct；
- property get/set 和 BlueprintSetter；
- write/reload effect；
- 非平凡参数帧。

这些调用必须进入现有 reflection fallback，不能在运行时猜测或降级语义。

## 4. 实施批次

### Batch A：immutable plan 与 typed thunk

- 新增 fast-path plan、shape classifier 和静态 thunk；
- binding package load 记录 typed thunk 与 reflection fallback plan 数量；
- `Dispatch` 在公共 guard 后进入 thunk；
- warm call 不执行名称查找、property walk、kind switch、参数 TArray loop、
  `InitializeStruct` 或 `DestroyStruct`。

### Batch B：聚焦合同

- 两个不同的实例 UFUNCTION、相同 ABI shape 共享同一 thunk；
- 两个函数均返回正确结果；
- 不匹配 shape 继续由 reflection fallback 正确执行；
- stale generation 在进入 thunk 前被拒绝；
- package load 后 warm loop 的 class load/name lookup 增量为零。

### Batch C：真实性能复测

- 不修改 P54.3 C# workload、oracle、lane 和统计协议；
- 先运行缩小 diagnostic profile，确认真实 Wasmtime/WAMR crossing 正确；
- 再运行 5 fresh process、5 warmup、30 sample 的正式矩阵；
- 报告 `scalar_add_int32`、`batch_scalar` 的 P50/P95/MAD 前后变化；
- 若收益不显著，继续归因 Wasmtime callback、Runtime context 和
  `ProcessEvent` 内层 frame，不把无效优化包装成完成。

## 5. 完成门槛

- Automation 正确性失败数为零；
- architecture/static contracts 通过；
- 两个真实 UFUNCTION 共享 shape 的结构证据成立；
- unsupported fallback 与 stale generation 合同成立；
- 正式复测 7500/7500 样本正确；
- 中文报告明确收益、剩余成本和下一批优化方向。

## 6. 完成状态

- [x] Batch A：immutable plan 与 shape-based typed thunk；
- [x] Batch B：共享 thunk、fallback、stale generation 和 warm lookup 合同；
- [x] Batch C：诊断 profile 与 5 进程正式矩阵；
- [x] 默认关闭 dynamic host per-call timing，诊断模式可显式开启；
- [x] Runtime invocation context 缓存与 Wasmtime argument stack 精简；
- [x] UE5.8 no-clean 构建；
- [x] 两个目标 Automation 全部通过；
- [x] 7,500/7,500 正式 observation 正确；
- [x] 中文实施与基准报告。

P54.4 的有效正式收益为：`scalar_add_int32` P50 下降 5.09%，
`batch_scalar` 下降 3.04%，`property_get_set` 下降 22.80%。`scalar_noop`
与 `object_roundtrip` 本轮分别回退 4.58% 和 4.36%，已在报告中保留，不视为
阶段收益。P54.5 转向带资格证明的 native direct invocation。
