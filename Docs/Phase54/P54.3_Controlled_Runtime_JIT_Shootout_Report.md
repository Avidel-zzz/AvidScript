# P54.3 同 WASM 执行层 JIT 对 JIT 正式报告

## 1. 结论

本批次按同一份 WASM 字节、同一函数签名、同一 seed、同一计时边界，完成了 Puerts V8 WebAssembly JIT 与 AvidScript Wasmtime Cranelift JIT 的正式对照。

正式结果：

- Wasmtime / V8 跨进程配对 P50：`0.9992x`；
- Wasmtime / V8 跨进程配对 P95：`0.9835x`；
- PC 候选门槛：P50 与 P95 均不得大于 `1.05x`；
- 结果：`wasmtime_pc_default_gate_passed`。

因此，Wasmtime 45.0.0 + Cranelift JIT 在本固定整数 kernel 上与 Puerts 所带 V8 9.4.146.24 的 WebAssembly JIT 基本同档，并通过 AvidScript PC 默认执行层候选门槛。它没有证明 AvidScript 整套游戏脚本框架已经全面快于 Puerts；完整 UE binding 热路径仍由后续批次优化和验证。

## 2. 为什么这次对比公平

此前 WAMR interpreter 对 V8 JIT 只能说明解释器与 JIT 的执行层级差异，不能用于选择 PC 默认后端。本套件固定为：

| 项目 | 合同 |
| --- | --- |
| WASM | 三条 VM lane 使用 SHA-256 完全相同的 `controlled_runtime_kernel.wasm`；Native lane 执行等价 C++ oracle |
| WASM SHA-256 | `230aed5ae6bd816e7780e0519354b100f29d23908ff0e6c1f0b52af5d4c834f7` |
| 导出 | `run(i32 iterations, i32 seed) -> i32` |
| V8 lane | `WebAssembly.Module` / `WebAssembly.Instance`，缓存导出函数 |
| Wasmtime lane | Wasmtime 45.0.0，Cranelift JIT，缓存导出函数 |
| WAMR lane | WAMR 2.4.4 interpreter，仅作为移动端/解释器基线 |
| Native lane | UE C++ 等价 oracle |
| 计时边界 | 单次 cached export call |
| 计时区外 | compile、instantiate、export lookup、warmup |
| 每个 sample | 恰好一次 host 到 guest crossing，返回后独立 oracle 校验 |
| lane 顺序 | 按 process 与 sample 轮转，避免固定顺序漂移 |

三条 VM lane 的 `source_wasm_sha256` 与 `execution_artifact_sha256` 均相同；Native lane 绑定同一 kernel 合同与哈希，并执行独立等价 oracle。全部 lane 均为 `fallback_used=false`。

校准进程与 5 个 timed process 共 6 个不同 PID。600 条 observation 全部满足：

- `result == expected`；
- `correct=true`；
- 每条 lane 150 条；
- 每个 process/lane 单元 30 条；
- `correctness_failures=0`；
- `fallback_used=false`。

## 4. 稳定校准

校准目标为每个 sample 至少 5 ms。冻结迭代数来自三次确认中位数；冻结复测未稳定越过门槛时，迭代数加倍并重新确认。

| Lane | 冻结 iterations | 确认中位数 |
| --- | ---: | ---: |
| Puerts V8 WebAssembly JIT | 8,192,000 | 9.491 ms |
| AvidScript Wasmtime Cranelift JIT | 8,192,000 | 9.473 ms |
| AvidScript WAMR Interpreter | 512,000 | 5.225 ms |
| Native C++ Reference | 8,192,000 | 9.469 ms |

这一策略避免把正常计时抖动下的“刚好 5 ms”误当作稳定校准结果。

## 5. 跨进程统计

单位为 ns/iteration。每个进程先对自己的 30 个 sample 计算 P50、P95 与 MAD，再对 5 个独立进程做跨进程统计。

| Lane | process P50 median | process P50 P95 | process P95 median | process P95 P95 | process MAD median |
| --- | ---: | ---: | ---: | ---: | ---: |
| Puerts V8 WebAssembly JIT | 1.1780 | 1.2024 | 1.3670 | 1.4035 | 0.0167 |
| AvidScript Wasmtime Cranelift JIT | 1.1777 | 1.1986 | 1.2812 | 1.3445 | 0.0203 |
| AvidScript WAMR Interpreter | 10.4145 | 10.6322 | 11.9154 | 12.7777 | 0.1556 |
| Native C++ Reference | 1.1682 | 1.1925 | 1.3114 | 1.3356 | 0.0125 |

Wasmtime 与 V8 的配对比率先在每个 process 内计算，再跨 process 汇总：

| Gate statistic | Wasmtime / V8 | 上限 | 结果 |
| --- | ---: | ---: | --- |
| P50 | 0.9992x | 1.05x | 通过 |
| P95 | 0.9835x | 1.05x | 通过 |

WAMR interpreter 的跨进程 P50 中位数约为 Wasmtime 的 `8.84x`。因此 WAMR 适合作为无 JIT 平台与移动端兼容基线，但不应继续作为 PC 高性能默认候选。

## 6. 架构决策

Phase 54 由此得到以下决策：

1. PC 执行层继续采用 Wasmtime + Cranelift JIT 作为默认候选。
2. WAMR interpreter 保留为移动端、JIT 受限平台和故障回退候选，不用于证明 PC 性能领先。
3. 不因为单一整数 kernel 通过就宣布全面领先 Puerts。完整游戏脚本性能还取决于 C# frontend、generated binding ABI、UE 类型封送、对象句柄、事件派发与批调用。
4. 下一性能主线应进入 typed thunk / cached call plan，减少 `ProcessEvent`、参数帧和通用动态 ABI 的固定 crossing 成本。

## 7. 适用边界

本报告只回答“同一 WASM 内核交给 V8 WebAssembly JIT 与 Wasmtime Cranelift JIT，纯 cached export 执行是否同档”。它不覆盖：

- V8/Wasmtime/Native 每个 timed sample 各执行 8,192,000 次 kernel 循环，host call 与 cached export 边界成本被大幅摊薄，因此本结果不能代表短函数 crossing；
- V8 身份可确认是生产式 WebAssembly tiered JIT，但现有证据不记录每个 sample 当时位于 Liftoff 还是已 tier-up 的优化层，报告不使用“逐样本 TurboFan”口径；
- Native lane 的 `execution_artifact_sha256` 当前作为同一 kernel 合同标签使用，不是 PE/COFF 二进制摘要；Native 只提供 oracle，不参与 Wasmtime/V8 gate；
- C# 编译与 WASM 生成时间；
- VM 创建、模块编译与实例化时间；
- BeginPlay、Tick、Delegate 和热重载生命周期；
- FVector、UObject、Array、String、ref/out 等 UE ABI；
- GC、内存占用、长时运行抖动与移动端功耗；
- Puerts JavaScript frontend 与 AvidScript C# frontend 的语言层差异。

机器可读紧凑证据见 `P54_Controlled_Runtime_JIT_Shootout_Evidence.json`。原始 sample、日志与本机路径仅保留在 Git 外部正式 attempt 中。
