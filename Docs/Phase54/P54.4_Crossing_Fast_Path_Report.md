# P54.4 Crossing Fast Path 实施与正式基准报告

## 1. 阶段结论

P54.4 已完成第一批通用 crossing fast path，但结果同时证明了一件更重要的事：
PC 执行后端不应从 Wasmtime 换回解释器，也不能把当前差距归因于 Cranelift
不如 V8。

同一正式 C# WASM 的 `pure_integer` 控制项中：

| Lane | P50 | P95 | MAD |
| --- | ---: | ---: | ---: |
| Puerts V8 Reflection | 0.99 | 0.99 | 0.00 |
| Puerts V8 Static | 0.99 | 1.00 | 0.00 |
| AvidScript Wasmtime Cranelift JIT | 1.03 | 1.07 | 0.01 |
| AvidScript WAMR Interpreter | 59.26 | 60.27 | 0.39 |

单位为 ns/op。Wasmtime 与 V8 在该控制项中处于同一量级，WAMR 约慢两个数量级。
桌面端继续使用 Wasmtime Cranelift JIT；WAMR 保留为移动端、受限平台和禁止 JIT
环境的兼容后端。

## 2. 已实现内容

### 2.1 Shape-based typed thunk

新增独立的 `AvidScriptBindingFastPath` 私有组件。binding package 加载时按结构
证明并绑定首个通用 shape：

`instance + 2 x value int32 -> int32`

该规则不包含 benchmark、类名、函数名或 stable id 特判。两个不同 UFUNCTION
共享同一静态 thunk。计划缓存：

- `UFunction*`；
- 参数帧大小与对齐；
- 两个参数的 frame byte offset；
- 返回值的 frame byte offset；
- 返回值 Guest Memory 参数位置；
- 编译期 thunk function pointer。

warm call 不再执行参数 property loop、kind switch、`InitializeStruct` 或
`DestroyStruct`。ordinal、对象 generation、`IsA`、write policy、reload effect
journal、Guest Memory 边界和 scratch 边界仍由公共 dispatcher 统一检查。

### 2.2 显式动态调用计时策略

此前每次 dynamic host import 都无条件读取两次高精度时钟并累计
`HostImportCallMs`。这会让生产调用为诊断功能持续付费。

P54.4 新增 `EAvidScriptDynamicHostCallTimingPolicy`：

- `Disabled`：生产默认值，不读取逐调用高精度时钟；
- `PerCall`：诊断显式开启，保留逐调用耗时和 timed call count。

host import 调用计数、最后输入、最后结果和失败信息在两种模式下都继续记录。
该优化没有更改 workload 的 operation count、host crossing count 或校验 oracle。

### 2.3 Runtime context 与 Wasmtime callback

- `FAvidScriptBindingInvocationContext` 在 `SetHostContext` 时生成并缓存，不再在每次
  dynamic crossing 中重建六个字段；
- Wasmtime callback 的 64 单元栈数组改为只写入实际 argument count，不再预清零
  全部 512 bytes；
- Wasmtime backend 仍为 45.0.0 Cranelift JIT，fallback 关闭。

## 3. 正确性验证

UE5.8 源码版 `AvidTPSTemplateEditor Win64 Development` no-clean 构建通过。
以下两个目标 Automation 在同一 Editor 进程中全部成功：

- `AvidScript.Editor.BindingRuntime.TypedThunk`；
- `AvidScript.Runtime.DynamicHostCallTimingPolicy`。

验证覆盖：

- 两个不同 int32 UFUNCTION 共享同一 shape thunk；
- thunk 返回值分别为 42 和 29；
- float shape 正确回退 reflection；
- stale generation 在 Guest Memory 写回前被拒绝；
- warm dispatch 不增加 class load 或 reflected name lookup；
- 默认生产策略不采样时钟；
- 显式诊断策略记录 timed dynamic call。

## 5. 数据解释

`scalar_add_int32` 和 `batch_scalar` 命中 typed thunk，P50 分别下降 5.09% 和
3.04%。收益真实但有限，因为 thunk 仍保留 `ProcessEvent`；UE 内部仍会分配
virtual-stack frame、复制参数帧并调用 native exec thunk。

`property_get_set` 每轮有两次 dynamic crossing，不命中本批 typed UFUNCTION
shape，但默认关闭逐调用时钟后下降 22.80%，且跨进程 MAD 仅 0.28 ns。这说明
per-call telemetry 是可观的固定成本。

`scalar_noop` 和 `object_roundtrip` 分别回退 4.58% 和 4.36%。本阶段不把它们
包装成优化成果，也不宣称 P54.4 对所有 shape 普遍加速。object lane 的 ownership、
borrow 和 handle 语义仍是独立热点。

与 Puerts 的剩余差距仍然很大：

- `scalar_add_int32` 对 Reflection 为 6.82x，对 Static 为 24.98x；
- `batch_scalar` 对 Reflection 为 6.64x，对 Static 为 23.58x；
- `property_get_set` 对 Reflection 为 2.36x，对 Static 为 3.87x。

因此“换掉 Wasmtime”不是当前正确动作。纯计算控制项已经排除了 Cranelift 作为
主要瓶颈；主差距来自 VM host callback、动态 ABI、对象解析和 UE invocation。

## 6. P54.5 方向

下一阶段建立两级 UFUNCTION 调用模型：

1. `semantic_process_event`：完整保留 Blueprint override、RPC/callspace、interface、
   event 和自定义 ProcessEvent 语义，继续作为全覆盖 fallback；
2. `qualified_native_direct`：仅对加载期能够证明为 final native、非网络、非 event、
   非 interface 且参数帧安全的函数，调用缓存的 UHT native exec thunk，绕过
   `ProcessEvent` 的第二层 frame。

资格证明必须由通用 function flags 和 immutable plan 生成，不能手写 API，也不能按
benchmark 函数名放行。首轮会用同一 UFUNCTION 同时跑 semantic/direct 两条 lane，
先证明结果、错误边界和 host count 等价，再讨论是否扩大 shape 覆盖。

机器可读结果见 `P54.4_Crossing_Fast_Path_Benchmark_Evidence.json`。
