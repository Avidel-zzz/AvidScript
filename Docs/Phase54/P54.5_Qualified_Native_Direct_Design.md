# P54.5 Qualified Native Direct 设计

## 1. 背景

P54.3 的同一 WASM 控制实验和 P54.4 的正式 C# 五通道矩阵已经证明：

- Wasmtime Cranelift JIT 与 Puerts V8 JIT 的纯整数执行处于同一量级；
- P54.4 typed thunk 消除了 property walk、通用 frame lifecycle 和逐调用计时；
- `scalar_add_int32` 仍为 713.14 ns/op，Puerts Reflection 为 104.59 ns/op，
  Puerts Static 为 28.54 ns/op；
- typed thunk 仍调用 `UObject::ProcessEvent`，UE 会创建第二层 virtual-stack frame、
  复制参数帧，再进入 UHT native exec thunk。

P54.5 的目标不是更换 VM，而是为满足严格资格条件的 native UFUNCTION 增加一个
独立、显式、可回退的 direct invocation 语义层级。

对 Puerts 源码的并行审计确认：普通 native、非网络、非 Ubergraph 的 Puerts
Reflection 调用也会构造 `FFrame` 并进入 `UFunction::Invoke`；Puerts Static 才是
C++ 成员函数指针直调。因此 P54.5 的同层目标是 Puerts Reflection fast，Puerts
Static 只作为后续 generated-native binding 的性能上界。

## 2. 方案比较

### 方案 A：继续优化 ProcessEvent typed thunk

优点是完整保留 Blueprint override、RPC、callspace、Actor ProcessEvent guard 和调试
语义。缺点是 P54.4 已经移除外围主要通用成本，剩余上限受 UE 内部第二层 frame 限制。

### 方案 B：运行时调用 UHT native exec thunk

通过 `UFunction::Invoke` 和手工构造的 compiled-in `FFrame`，复用 UHT 已生成的参数
读取、native method 调用和返回值写入逻辑。它不需要按 API 手写 wrapper，也不需要
重新编译生成插件，能够在 immutable plan 中按通用规则缓存。

代价是它绕过 `ProcessEvent`，因此不能假装与完整反射语义等价。自定义
`ProcessEvent`、Actor 初始化 guard、网络 callspace 和 Blueprint event 等行为必须
通过资格规则排除或由调用方显式接受。

### 方案 C：生成强类型 C++ 直接 wrapper

理论性能最高，可像 Puerts static binding 一样直接调用 C++ 方法。它要求定位 owner
header、处理 overload/default/ref/out、访问控制、模块依赖、UHT 增量编译和热重载，
本质上是新的静态绑定编译流水线。该方案保留给后续阶段，不与 P54.5 混合。

P54.5 选择方案 B。方案 A 永久保留为全覆盖 fallback，方案 C 作为后续上限。

| 层级 | UE 终点 | Puerts | AvidScript |
| --- | --- | --- | --- |
| S3 | `ProcessEvent` | Reflection slow | `SemanticProcessEvent` |
| S2 | `UFunction::Invoke` | Reflection fast | `QualifiedNativeDirect` |
| S1 | C++ 成员函数直调 | Static binding | 后续 generated-native |
| S0 | `FProperty` 地址读写 | Reflection/Static property | cached property |

## 3. 两级调用语义

### 3.1 `SemanticProcessEvent`

默认模式。行为与当前实现一致：

- 调用 `UObject::ProcessEvent`；
- 保留 Blueprint override、event、RPC/callspace、interface 和 Actor guard；
- 支持所有当前 descriptor 已接受的 UFUNCTION shape；
- 是不合格 direct plan 的确定性 fallback。

### 3.2 `QualifiedNativeDirect`

显式 opt-in 模式。只有 immutable plan 在 package load 时通过全部资格证明才进入
direct thunk，否则仍执行 `SemanticProcessEvent`。调用方不会得到“调用失败”，但
instrumentation 必须能区分 direct hit 和 semantic fallback，避免静默误判性能能力。

该模式明确不承诺执行自定义 `ProcessEvent` 副作用。它准确对标 Puerts Reflection
fast 的 native UFUNCTION 层级，不能被描述为 Puerts Static 同层能力。

## 4. 首批资格规则

首批仍只覆盖 P54.4 已证明的 shape：

`instance + 2 x value int32 -> int32`

除现有 trivial frame 证明外，native direct 必须同时满足：

1. descriptor 对该 binding 显式发布 `dispatch_mode=qualified_native_direct`；
2. `UFunction` 同时具有 `FUNC_Native`、`FUNC_Final` 和 `FUNC_Public`；
3. native function pointer 非空；
4. 不具有 `FUNC_Net`、`FUNC_Event`、`FUNC_BlueprintEvent`、`FUNC_Delegate`、
   `FUNC_MulticastDelegate`、`FUNC_Exec`、`FUNC_Static`、
   `FUNC_BlueprintAuthorityOnly`、`FUNC_BlueprintCosmetic` 或 `FUNC_EditorOnly`；
5. owner 不是 interface，且不是 Blueprint 生成类；
6. `GetSuperFunction()==nullptr`，function 没有 script bytecode；
7. 禁止 `FUNC_NetValidate`、`FUNC_UbergraphFunction`、`FUNC_DLLImport`、
   `FUNC_HasOutParms`、`FUNC_HasDefaults` 和全部 `FUNC_NetFuncFlags`；
8. `NumParms==3`，`ParmsSize==PropertiesSize==12`，没有 ref/out、默认参数、
   非平凡参数、局部属性或 reload/write effect；
9. 三个 `FIntProperty` 的 UFunction offset 严格为 `0/4/8`，property chain 严格为
   input、input、return，且 init/post-construct/destructor link 为空；
10. 调用发生在 Game Thread，且不处于 GC、PostLoad 或 intra-frame debugging；
11. target 实际 class 与 plan owner class 完全相等，不能只依赖 `IsA`。

任一条件失败都只产生 `SemanticProcessEvent` plan，不允许运行时猜测。
仅凭 function flags 不构成授权，因为 flags 不能证明不存在自定义
`ProcessEvent` 副作用。

`AActor::ProcessEvent` 自身包含 Actor 初始化、CallInEditor、GC 和 delegate guard。
descriptor 对 Actor function 发布 direct authorization 时，含义是调用方明确接受
跳过这些 S3 语义，不是框架证明 Actor 没有自定义 ProcessEvent。报告和 provenance
必须记录 owner kind，禁止把该选择描述为无损优化。

## 5. 组件边界

### 5.1 `AvidScriptBindingFastPath`

扩展现有组件，不创建第二套 binding cache：

- `FFastPathPlan` 同时保存 shape 和可用 invocation mode；
- `TryBuildFastPath` 完成 trivial frame 与 native-direct 资格证明；
- ProcessEvent thunk 与 NativeInvoke thunk 共享参数读取、frame 初始化和返回写回；
- direct thunk 构造 `FFrame(Target, Function, Frame, nullptr, ChildProperties)`，
  强制 compiled-in property chain，再调用 `UFunction::Invoke`；
- direct plan 使用 `GetOffset_ForUFunction()` 证明固定 `0/4/8` layout；P54.4
  ProcessEvent plan 的 internal offset 不能直接充当 direct-frame 证明；
- public dispatcher 的安全 guard 不移动到 thunk 内。

### 5.2 Descriptor authorization

binding selection profile 的 class selection 增加 `native_direct_functions`。resolver
要求它是已接受 function selection 的子集，并把授权发布为 descriptor binding 的
`dispatch_mode=qualified_native_direct`。其他 binding 继续发布
`cached_process_event`。

该字段是语义授权，不是手写 API 实现。它参与 selection hash、canonical identity、
package hash 和 manifest provenance。使用该字段的 profile/schema 升级到 v6，
descriptor 升级到 v8；旧 profile 不声明该字段时继续生成 v7 descriptor，身份与
行为保持原样。

P54.5 中，该授权还表示项目声明目标函数使用标准 UHT exec thunk，并明确接受跳过
owner 继承链上的自定义 `ProcessEvent`。框架无法仅从运行时 `UFunction` flags
证明 `CustomThunk` 或 ProcessEvent override 不存在；未经项目授权的第三方/Engine
函数不得自动进入 direct。

### 5.3 Invocation policy

`FAvidScriptBindingInvocationContext` 增加调用策略，Runtime 的
`FAvidScriptWasmHostContext` 负责在 `SetHostContext` 时缓存该策略：

- 默认 `SemanticProcessEvent`；
- benchmark 或明确的项目配置可请求 `QualifiedNativeDirect`；
- policy 是 runtime/session 属性，不写入每个 API 的手工 allowlist。

descriptor authorization 与 runtime policy 必须同时成立。前者回答“这个 API 是否
允许绕过 ProcessEvent”，后者回答“这个 session 是否请求 direct tier”。

### 5.4 Diagnostics

package instrumentation 增加：

- qualified native-direct plan count；
- semantic-only plan count。

warm invocation instrumentation 增加：

- native-direct dispatch count；
- requested-direct-but-fallback count。

动态调用结果记录实际 dispatch tier，Runtime 复用现有 host-call counter 累计 direct
hit/fallback。公开查询能够返回 ordinal 的 shape 和资格结果，但不暴露 `FFrame`
或 native pointer。

## 6. 数据流

1. descriptor parser 和 reflection resolver 生成现有 function plan；
2. selection resolver 验证并发布 descriptor authorization；
3. fast-path classifier 证明 scalar shape；
4. native qualifier 检查 authorization、function flags、owner、script 和 frame；
5. runtime dispatch 完成 ordinal、Guest Memory、handle generation、`IsA` 和 policy guard；
6. policy 请求 direct 且 plan qualified 时进入 NativeInvoke thunk；
7. 否则进入 ProcessEvent typed thunk；
8. 两条路径都从相同 frame offset 写回相同 Guest Memory 地址；
9. backend 继续收到相同 success/failure ABI 和 actual dispatch tier。

## 7. 错误与回退

- 资格不满足：加载成功，生成 semantic-only plan；
- 非 Game Thread 请求 direct：拒绝 direct，并报告明确 category，不在错误线程调用
  `ProcessEvent` 作为掩盖；
- GC、PostLoad 或 intra-frame debugging 期间请求 direct：同样 fail closed，不先调用
  callspace probe，也不在同一错误线程回退；
- frame、Guest Memory 或 stale generation 错误：沿用现有失败 category；
- UHT exec thunk 设置 abort state：direct 调用失败并保留可诊断信息；
- direct 运行时不得因某次数据值切换到不同 API 实现。

## 8. 验证

### 8.1 结构与语义

- 两个显式授权的不同 final native UFUNCTION 共享 direct shape；
- ProcessEvent 与 NativeInvoke 对相同输入产生相同返回值；
- policy 默认值只走 ProcessEvent；
- 显式 direct policy 命中 qualified plan；
- 未授权函数以及 float、ref/out、event、network、interface、Blueprint owner 和
  非 final 函数回退；
- exact-class、UFunction offset、property chain 和标准 frame 证明失败时回退；
- stale generation、Guest Memory 越界和错误线程不会执行 native thunk；
- package load 后 warm call 不发生 name/property lookup。

### 8.2 性能

保持正式 C# workload、WASM、oracle、operation count 和 host count 不变，报告：

- Wasmtime `SemanticProcessEvent`；
- Wasmtime `QualifiedNativeDirect`；
- Puerts Reflection；
- Puerts Static；
- Native C++。

Puerts Static 的 fixture binding 改为直接绑定同一个 `Reflect*` C++ 方法，而不是
少一层的 `Native*` helper。报告按 S2 比较 AvidScript direct 与 Puerts Reflection；
在完成 generated-native S1 lane 前不得宣称击败 Puerts Static。

首批最低有效门槛：

- `scalar_add_int32` direct P50 相对 P54.4 的 713.14 ns/op 至少下降 15%；
- direct P50 目标低于 500 ns/op；
- process P50 的跨进程 P95 不回退超过 5%；
- direct 对 Puerts Reflection 的 P50/P95 只有同时领先至少 5% 且差值大于
  `2 x MAD` 时才能宣称同层领先；
- 7,500 条正式 observation 全部正确；
- `pure_integer` 控制项变化不超过 10%；
- host crossing count 和 operation count 与 P54.4 完全一致。

若未达到门槛，阶段报告继续拆分 Wasmtime callback、`FFrame` 和 registry 成本，不把
direct mode 包装成完成。

## 9. 非目标

- 不为 benchmark fixture 或单个函数名添加特判；
- 不手写 FVector、Actor 或其他 UE API wrapper；
- 不在本阶段覆盖 ref/out、object ownership 或 struct；
- 不把 direct mode 宣称为完整 ProcessEvent 语义；
- 不把 Actor direct authorization 宣称为无损语义等价；
- 不把 S2 direct 的结果宣称为击败 S1 Puerts Static；
- 不删除或弱化现有 reflection fallback；
- 不更换 Wasmtime，也不把 WAMR interpreter 纳入 PC headline。
