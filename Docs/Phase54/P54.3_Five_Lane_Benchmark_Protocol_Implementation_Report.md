## 2. 协议与实现

### 2.1 Canonical five-lane contract

正式 profile 只接受以下五个输出 lane：

1. `native_cpp`
2. `puerts_v8_reflection`
3. `puerts_v8_static`
4. `avidscript_wamr_interpreter`
5. `avidscript_wasmtime_jit`

`avidscript_wamr` 不会出现在 schema v2 profile、request、result 或 aggregate 中。合同测试保留对该旧 id 的负向覆盖，防止新 Phase 54 结果回退到旧命名。

profile 以 `canonical_json_utf8_sha256_v1` 锁定 `lane_catalog`。PowerShell 与 C++ 均按字段名 ordinal 排序、数组原序、JSON 标准转义、UTF-8 无 BOM 和 invariant 数字格式生成同一 canonical representation。lane identity 排除自身 `lane_identity_sha256` 后计算；catalog identity 对包含 lane identity 的完整数组计算。sidecar、独立 result validator 与 C++ request ingestion 均重新计算每条 lane identity 和 catalog identity，外层声明不能自证。

五份 schema 均以 `prefixItems` 固定五个 lane 的精确顺序，并以 `items: false` 拒绝额外项；交换或重复任一 lane 都不能通过 schema。

### 2.2 AvidScript provenance

每个 AvidScript observation 均携带：

- backend id 与 runtime version
- execution mode
- artifact format 与 artifact SHA-256
- source WASM SHA-256
- target triple
- runtime build identity
- runtime artifact SHA-256
- fallback used
- lane identity SHA-256

Runner 使用 `FAvidScriptRuntimeSession::SetBackendSelectionForTesting` 显式选择：

- WAMR：`Wamr / Interpreter / WasmBytecode / bAllowFallback=false`
- Wasmtime：`Wasmtime / Jit / WasmBytecode / bAllowFallback=false`

WAMR 的 backend info 绑定编译期 `interp=1,fast_interp=1,aot=0,jit=0,fast_jit=0` 与实际链接静态库 SHA-256；不再从通用 `Interpreter` mode 推导 fast-interp。Wasmtime 在 DLL 加载边界读取并计算实际 staged/managed DLL SHA-256，先与 Build.cs 锁定工件比对，再发布 `wasmtime-v45.0.0;cranelift=1;dll_sha256=...`。runtime 在 backend `Load` 后刷新 `ActiveBackendInfo`，因此 result 携带的是加载边界观测值。

初始化后以 runtime 返回的实际 `FAvidScriptVmBackendInfo` 与 catalog 逐字段比对。实际 backend、mode、artifact、target、runtime build identity、runtime artifact SHA-256 或 fallback 任一不符都会使进程失败，不能仅凭请求 lane 名或 profile 声明推断身份。

### 2.3 Shared adapter and runner

两个 AvidScript lane 由同一个 `FAvidScriptLane` adapter 实现，并使用相同 manifest、WASM 输入、workload 调用与 checksum 路径；差异仅为显式 backend selection 与该 lane 的预期 provenance。生产 `RuntimeSession` 默认值未改动，benchmark 测试选择只存在于 Harness 路径。

五通道 runner 使用五行平衡顺序，并继续按 lane 独立校准和冻结 iteration count。每个 sample 携带 `seed` 与 lane-specific `expected_checksum`，validator 先逐样本检查 oracle；只有 `seed` 和 `iterations` 都相同的 observation 才执行跨 lane checksum 比较。五条 lane 使用不同 iteration count 的合法 fixture 通过，错误 expected checksum fixture 被拒绝。
