# P54.3 五通道基准协议与 Runner 集成实施报告

## 1. 范围

本批次完成 Task 4A，即实施计划 Task 4 的 Step 1-4：

- 将 Phase 53 三通道协议升级为 schema v2 五通道协议。
- 新增 `avidscript_wamr_interpreter` 与 `avidscript_wasmtime_jit` 两条正式输出通道。
- 让两条 AvidScript 通道复用同一个 adapter/workload，仅注入显式 backend selection。
- 在 request、calibration、process result、raw result 与 aggregate 中贯通 lane catalog、catalog hash、lane identity 与实际 backend provenance。
- 增加错误 backend、mode、artifact、target、runtime identity 与 fallback 的拒绝路径。
- 保留每通道独立校准与 Phase 53 workload 语义。

本批次没有启动 5 process x 30 sample 正式矩阵，没有生成正式 benchmark 制品，也不作任何性能领先结论。固定等价 WASM kernel 与真实 C# frontend output 已作为不同 `wasm_workload_kind` 保留在协议中，归因矩阵留给 Task 4B。

## 2. 协议与实现

### 2.1 Canonical five-lane contract

正式 profile 只接受以下五个输出 lane：

1. `native_cpp`
2. `puerts_v8_reflection`
3. `puerts_v8_static`
4. `avidscript_wamr_interpreter`
5. `avidscript_wasmtime_jit`

`avidscript_wamr` 不会出现在 schema v2 profile、request、result 或 aggregate 中。合同测试保留对该旧 id 的负向覆盖，防止新 Phase 54 结果回退到旧命名。

profile 以 `ordered_json_utf8_sha256_v1` 锁定 `lane_catalog`。catalog 覆盖 runtime、execution tier、adapter、WASM workload kind、source WASM、execution artifact、compiler identity/flags、runtime build config/identity、target、CPU feature policy、backend id、execution mode 与 fallback。sidecar 对模板求值后计算 catalog SHA-256，并在每个阶段做结构相等与 hash 一致性校验。

### 2.2 AvidScript provenance

每个 AvidScript observation 均携带：

- backend id 与 runtime version
- execution mode
- artifact format 与 artifact SHA-256
- source WASM SHA-256
- target triple
- runtime build identity
- fallback used
- lane identity SHA-256

Runner 使用 `FAvidScriptRuntimeSession::SetBackendSelectionForTesting` 显式选择：

- WAMR：`Wamr / Interpreter / WasmBytecode / bAllowFallback=false`
- Wasmtime：`Wasmtime / Jit / WasmBytecode / bAllowFallback=false`

初始化后以 runtime 返回的实际 `FAvidScriptVmBackendInfo` 与 catalog 逐字段比对。实际 backend、mode、artifact、target、runtime identity 或 fallback 任一不符都会使进程失败，不能仅凭请求 lane 名推断身份。

### 2.3 Shared adapter and runner

两个 AvidScript lane 由同一个 `FAvidScriptLane` adapter 实现，并使用相同 manifest、WASM 输入、workload 调用与 checksum 路径；差异仅为显式 backend selection 与该 lane 的预期 provenance。生产 `RuntimeSession` 默认值未改动，benchmark 测试选择只存在于 Harness 路径。

五通道 runner 使用五行平衡顺序，并继续按 lane 独立校准和冻结 iteration count。sidecar merge 不再要求不同 lane 的 iteration count 相同，只要求 workload checksum 等价。

## 5. 结果

## 6. 剩余风险与 Task 4B

- 正式运行前需在具备完整 Puerts `WasmCore` 输出的 producer 环境重跑 UE Automation smoke。
- Task 4B 需运行 5 fresh process x 30 sample 正式矩阵，核验 7500 个正确样本、独立校准、warmup、cold start、RSS 与 raw aggregate SHA-256。
- Task 4B 必须同时测固定等价 WASM kernel 与真实 C# frontend output，分别归因 runtime/Cranelift 与 C# 到 WASM codegen。
- 只有正式矩阵完成后才能执行 5% 止损判定；在此之前不得声明 Wasmtime 性能领先或切换 PC 默认。
