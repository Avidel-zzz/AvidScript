# P3.2 Host Binding Overhead Benchmark

日期: 2026-07-02
状态: Done

## 范围

P3.2 为 AvidScript host binding 建立 smoke 级微基准, 目标是量化同一个 actor location 工作流中几条路径的相对成本:

- direct `AActor::GetActorLocation`
- `FAvidScriptObjectRegistry::ResolveObject<AActor>`
- `FAvidScriptActorBinding::GetActorLocation`
- `FAvidScriptActorBinding::SetActorLocation`

本阶段不做 packaged/shipping 性能报告, 不做移动端实机测试, 不把结果作为最终预算。它只为后续 generated typed calls、batching、WASM import bridge 提供同一台机器上的可重复参考线。

## 实现

修改:

- `Source/AvidScriptRuntime/Public/AvidScriptRuntimeBenchmark.h`
- `Source/AvidScriptRuntime/Private/AvidScriptRuntimeBenchmark.cpp`

新增:

- `Source/AvidScriptRuntime/Private/Tests/AvidScriptHostBindingBenchmarkTests.cpp`

新增结构:

- `FAvidScriptHostBindingBenchmarkOptions`
- `FAvidScriptHostBindingBenchmarkResult`

新增 API:

```cpp
FAvidScriptRuntimeBenchmark::RunHostBindingBenchmark(Options, Result)
```

实现创建临时 `AvidScriptHostBindingBenchmarkWorld`, spawn 一个带 root component 的 actor, 注册到 `FAvidScriptObjectRegistry`, 然后按 warmup + sample 多轮循环测量每次操作的平均耗时。统计继续复用 P3.1 的 `FAvidScriptBenchmarkStats`, 输出 `Count/MinMs/MaxMs/AvgMs/P50Ms/P95Ms`。

## 初步观察

在当前 Editor/NullRHI smoke 条件下, registry resolve 与 binding get 都在亚微秒级, binding set 更高但仍低于 1 微秒量级。direct get 触及当前最小测量下限 `0.000100ms`, 因此只能作为下限参考。

这支持后续方向: 高频脚本 API 仍应优先 generated typed calls 和 batching, 但当前 host-side registry/binding wrapper 本身还不是明显瓶颈。P3.3 的 WASM import bridge 会进一步暴露 guest->host crossing 成本。

## 风险

- 当前数据来自 Editor/NullRHI Development, 不是 packaged/shipping。
- `IterationsPerSample=100` 是 automation smoke 口径, 不是正式 profiling 口径。
- direct get 接近计时下限, 后续若要做正式性能报告, 需要提升 iteration、固定 CPU 状态并独立导出 CSV/JSON。
- 尚未覆盖批量读写、反射路径、Blueprint path 或 WASM import crossing。
