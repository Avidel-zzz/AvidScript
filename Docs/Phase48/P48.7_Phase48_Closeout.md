## 当前能力

### C# 游戏逻辑

- 使用静态字段保存 gameplay 状态，并支持 bool、int、float、比较、逻辑运算和分支控制流；
- 实现 `BeginPlay`、`Tick`、`EndPlay`、`OnTimer`；
- 直接实现 `OnBeginOverlap`、`OnEndOverlap`、`OnHit`、`OnInput`，统一低层 event router 由编译器生成；
- 通过 `[AvidStateContract]`、`[AvidPersist]`、`[AvidTransient]` 和 `[AvidStateAlias]` 描述热重载状态；
- 构建失败不发布候选，manifest 或运行时候选失败时保留旧 WASM。

### UE 交互

- EngineGameplay profile 当前覆盖 Actor、ActorComponent、SceneComponent、PrimitiveComponent、Pawn 和 Controller 的授权反射表面；
- 普通 UE API 继续经过统一 descriptor、生成 facade、reachability slice 和缓存的 `ProcessEvent` invocation，不为每个函数新增 VM enum 或 WAMR wrapper；
- UObject 引用使用 slot/generation，不把裸指针暴露给 WASM；
- `FVector`、`FRotator`、`FTransform`、标量、bool、对象句柄和只读对象属性已经进入通用路径；
- `FName` value/const-ref 输入映射为 C# `string`，支持严格 UTF-8、范围、NUL、长度和 guest address 校验；
- 公共 `UE.SetTimer` / `UE.CancelTimer` 映射到运行时 timer service。

### 可玩样例

`Samples/CSharp/PlayablePickup/PlayablePickupScript.cs` 已验证：

1. `BeginPlay` 初次加载沿用 Actor 配置，成功热重载时根据迁移状态重建 timer；
2. `Tick` 持续旋转 Actor；
3. `OnBeginOverlap` 使用 `ActorHasTag("Player")` 过滤玩家；
4. 成功拾取后隐藏并关闭碰撞；
5. 3 秒 timer 后恢复；
6. 已收集状态下以相同 `ModuleId` 成功热重载，迁移一个 `Collected` 状态槽，保持 host 状态并由新 runtime timer 恢复；
7. 无效热重载后旧 runtime 继续执行。

## 产物与性能证据

PlayablePickup 使用 EngineGameplay 的 342 项授权 package，Roslyn reachability 和 binding slice 最终只发布 5 个可达反射 binding：

- `GetActorRotation`
- `SetActorRotation`
- `ActorHasTag`
- `SetActorHiddenInGame`
- `SetActorEnableCollision`

最终 WASM manifest 共 8 个 required imports：5 个动态反射 import、`owner_get_slot`、`owner_get_generation` 和 `timer_set_once`。未使用的 `timer_cancel` 不进入 guest module。

真实 WAMR 测试记录当前 host crossing 基线：

| 调用 | Host crossing |
| --- | ---: |
| 一次未收集状态的 `Tick` | 6 |
| 一次成功的 Player `BeginOverlap` | 8 |

反射解析发生在 `FAvidScriptBindingPackage::LoadDescriptor`：owner class、`UFunction*`、`FProperty*`、参数/返回值计划和 frame scratch 均在 package load 时构建。dispatch 通过 ordinal 直接读取缓存的 invocation plan，热路径只解析对象句柄、编组参数并调用 `ProcessEvent`，不按函数名重新查找反射成员。

这组 crossing 数是当前正确性基线，不代表已经达到最终性能目标。后续可通过缓存 `UE.Self` 句柄或编译器局部公共子表达式消除来降低 owner getter crossing，但必须先保持对象 generation 与生命周期语义正确。

## 独立代码审查

Phase 48 整体审查范围为 `ec9fecb..29752e0`，首次审查发现一个 Important 和一个 Minor：

- 可玩样例的旧 `BeginPlay` 会覆盖已迁移的 `Collected`，且旧 runtime 卸载后不会自动保留 timer；
- Semantic control-flow 测试的失败消息仍显示旧 schema `6/1.6`。

修复后增加了同一 `ModuleId` 下的成功 reload 端到端覆盖，显式断言 migration attempted/applied、迁移一个状态槽、候选 BeginPlay 重建一个 timer，以及 3.1 秒后的 Actor 状态恢复。复审结论为 `APPROVED`，没有遗留 Critical 或 Important finding。

## Phase 49 输入

Phase 49 应优先解决“可用于多个小型 Demo”的 API 覆盖与对象创建闭环，而不是继续逐个手写 API：

1. 项目级 reflected API profile 生成与变更检测；
2. Actor/UObject Spawn、Destroy、ownership 和 World 上下文；
3. `FHitResult` 与通用 struct/object marshalling 扩展；
4. 容器、委托和异步事件的生命周期安全 ABI；
5. 一次性 timer 的剩余时长迁移与更复杂 scheduler 状态合同；
6. PC Development/Shipping 打包闭环，再进入移动端适配。

Phase 48 已经提供“能写并运行一段真实游戏逻辑”的核心证据；Phase 49 的目标应是把这个单一玩法闭环扩展成可持续开发小型游戏 Demo 的项目工作流。
