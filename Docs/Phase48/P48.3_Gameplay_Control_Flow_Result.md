# P48.3 Gameplay 控制流与状态结果

## 状态

已完成。

P48.3 验证并固化了真实游戏逻辑所需的短路条件、比较、`if/else if`、早退、静态状态读写和热重载迁移。现有通用 compiler 已能覆盖这些形状，本阶段没有为单个玩法新增 production lowering 分支，也没有手写 UE API。

## C# 游戏逻辑

正式 `ActorLifecycle` 样例新增两个 gameplay 状态：

```csharp
private static bool HasActiveOverlap;
private static int LastInputActionId;
```

- `OnBeginOverlap` 使用 `HasActiveOverlap || !otherActor.IsValid` 早退，重复进入不会再次执行位置写入。
- `OnEndOverlap` 只结束当前有效 overlap，并把状态恢复为 `false`。
- `OnInput` 比较 `ActionId` 与 `LastInputActionId`，相同 action 的重复事件是 no-op。
- 原有 `ElapsedSeconds += deltaSeconds` 继续验证跨 Tick 状态。

这些逻辑直接写在 C# 脚本中，通过 P48.2 的编译器生成事件路由进入 UE Runtime。

`CSharpGuestAdvancedTests` 新增真实 C# source regression，覆盖：

- `!`、`&&`、`||`、`==`、`!=`、`<`；
- `if/else if`、块内状态写入和提前 `return`；
- `AActor.Slot` 与 `FVector.Z` 字段读取；
- 自然 `OnBeginOverlap` 与自动生成的唯一 `avid_on_gameplay_event`；

该回归首跑即通过，说明通用控制流和 backend 已具备所需能力，因此没有修改 `CSharpControlFlowLowerer`、`CSharpOperationLowerer` 或 `WasmFunctionCompiler`。

## 真实 WAMR 行为

UE5.8 `SourceAdapterArtifactLifecycleSmoke` 使用正式生成的 `actor_lifecycle.wasm`：

1. 第一次 BeginOverlap 修改 Other Actor 位置。
2. 使用不同 payload 再次派发 BeginOverlap，Actor 位置保持不变。
3. EndOverlap 清除 overlap 状态，随后 Hit 仍正常执行。
4. 第一次 Input 修改 owner Actor 位置。
5. 同一个 `ActionId` 使用不同 payload 再次派发，Actor 位置保持不变。
6. compatible reload 成功迁移三个状态槽，迁移字节数为 9。

RED 日志 `C:\tmp\AvidScript_P48_3_RUNTIME_RED.log` 精确失败于重复事件未被抑制和旧状态槽数量。GREEN 日志 `C:\tmp\AvidScript_P48_3_RUNTIME_GREEN3.log` 为 1/1 Success、非成功 0，并包含 Queue Empty、TestExit、`RequestExitWithStatus(1, 0, ...)`；进程退出码为 0。

## 剩余边界

- 本阶段验证的是单线程脚本实例内状态，不引入 async/await、Task 或多线程 guest 执行。
- 对复杂容器、异常、LINQ 和托管堆对象的支持不在当前 direct ABI 范围。
- 下一阶段仍需加入 `FName` descriptor，才能显著扩大常用 UE 函数的自动覆盖。

## 下一步

P48.4 为反射 binding descriptor 增加 `FName`，并在生成 C# facade 上提供现代字符串入口，而不是要求脚本作者手写 name table 或逐函数 adapter。
