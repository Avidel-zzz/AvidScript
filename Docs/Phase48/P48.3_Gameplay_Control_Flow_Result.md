# P48.3 Gameplay 控制流与状态结果

## 状态

已完成审查修复。

本次修复只调整 `ActorLifecycle` 样例的状态语义和其正式 WAMR 回归。没有新增手写 UE API，也没有改动 C# lowering 或 WASM backend。

## C# 游戏逻辑

样例现在保存以下可迁移状态：

```csharp
private static AActor ActiveOverlapActor;
private static bool HasActiveOverlap;
private static bool HasPreviousInput;
private static int LastInputActionId;
private static int LastInputTriggerEvent;
```

- `OnBeginOverlap` 先拒绝无效 handle；只有当前 actor handle 相同时才抑制重复 Begin。不同 Actor 的 Begin 会更新当前来源。
- `OnEndOverlap` 必须与当前保存的 actor handle 匹配，不能结束其他 Actor 的 overlap。
- `OnInput` 通过独立的 `HasPreviousInput` 标记区分“未收到过输入”和 `ActionId == 0`；只有 `ActionId` 与 `TriggerEvent` 都相同才是重复输入。
- `AActor.Matches` 同时比较 slot 与 generation，保持现有对象 handle 身份模型。

## 真实 WAMR 行为证据

正式 `BuildCSharpActorLifecycle.ps1 -DisableSemanticCache` 生成 `actor_lifecycle.wasm` 后，UE5.8 `AvidScript.Guest.CSharp.SourceAdapterArtifactLifecycleSmoke` 通过现有 WAMR 路径执行，验证了：

1. 第一条 `ActionId == 0` 输入会产生位置写入。
2. 相同 action、不同 trigger 的输入会执行；相同 action 和 trigger 的再次输入是 no-op。
3. 两个不同 Actor 的 BeginOverlap 都会执行；旧 Actor 的 EndOverlap 不会结束当前 Actor；当前 Actor 的 EndOverlap 会执行。
4. reload 前六个 state slot 都被写为非默认值；reload 后逐 slot 读取并逐字节比较，全部保留。
5. reload 后，当前 Actor handle 和输入重复键仍驱动预期的 no-op 或 EndOverlap 行为。

RED 日志 `C:\tmp\AvidScript_P48_3_RuntimeTest_RED.log` 记录了旧样例在 3 slot、不同 Actor Begin、以及首个 `ActionId == 0` 输入上的失败。最终 GREEN 日志 `C:\tmp\AvidScript_P48_3_RuntimeTest_GREEN3.log` 显示发现 1 项、`Result={Success}`、Queue Empty、TestExit 和 `RequestExitWithStatus(1, 0, ...)`。

## 剩余边界

- 样例只保存一个“当前 overlap 来源”。它能避免不同 Actor 的 Begin/End 混用，但不是可同时保留任意数量 overlap 来源的集合实现。
- 本阶段仍只覆盖单线程脚本实例，不引入 async/await、Task 或多线程 guest 执行。
- 复杂容器、异常、LINQ 和托管堆对象仍不在当前 direct ABI 范围。
