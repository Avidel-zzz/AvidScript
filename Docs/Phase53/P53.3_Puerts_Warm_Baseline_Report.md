## 2. 校准修正

首版 runner 为每个 workload 共享一次迭代数。最快的 Native lane 在多个 workload 上需要 8,192,000 次迭代才能达到 5 ms，这会迫使 WAMR 执行相同次数的高成本 crossing，单个进程运行 16 分钟仍无法完成。

正式基线改为 `workload x lane` 独立校准：

- 每条 lane 的计时区间均达到最低时长；
- request 冻结二维 iteration matrix，5 个测量进程使用同一矩阵；
- 每条 lane 用自身迭代数生成 Native oracle；
- 跨 lane 只比较 `ns/op`，不比较未归一化总时长；
- 相同 workload、seed、sample index 和 Williams lane 顺序保持不变。

修正后 1 x 5 诊断矩阵耗时 26.6 秒，正式 5 x 30 矩阵耗时 152.5 秒。

## 4. 结论

### 最接近

- `vector_value`：相对 Reflection 慢 1.13x；
- `vector_ref_out`：相对 Reflection 慢 1.44x；
- `callback_tick`：相对两条 Puerts lane 慢约 2.5x。

这些结果说明 FVector 反射封送本身在 Puerts 中也占据主要成本，AvidScript 的固定 crossing 开销被较重的结构体工作稀释。

### 主要差距

- `scalar_noop`、`scalar_add_int32`、`property_get_set`、`object_roundtrip` 和 `batch_scalar` 呈现约 1.2 到 1.8 微秒的 AvidScript 固定成本；
- `pure_integer` 暴露 WAMR interpreter 与 V8 JIT 的执行层级差距，不应通过 fixture 专用优化掩盖；
- 标量与对象工作负载说明 P53.4 应优先拆解通用 import dispatcher、binding plan、Guest Memory、handle resolve 与 ProcessEvent 成本。

## 5. P53.4 入口

P53.4 不为 benchmark 编写专用 API。优化必须位于正式 VM、Bindings、Runtime 或生成器路径，并至少覆盖一类通用调用：

1. 先采集 scalar/property/object 的 CPU 分层数据；
2. 将约 1.2 微秒固定成本拆为 VM import、dispatcher、plan、marshal、ProcessEvent 和 owner handle；
3. 优先优化可同时影响 scalar、property、object 与 batch 的共享路径；
4. 用同一 commit provenance 结构和同一 10 项 workload 复测；
5. 单独记录 WAMR interpreter 的纯脚本差距，后续评估 AOT/JIT backend，禁止把 V8 JIT 与解释器结果描述为同级执行模式。

Cold 启动和稳定内存不参与本轮 warm 排名，将随 P53.4 的 CPU/Insights 采集补齐，并在 P53.5 closeout 中单独报告。
